# 작업 절차

작업 크기에 맞춰 진행한다. 작은 변경에 별도 계획서나 장문의 보고서를 강제하지 않는다. 읽기 전용 진단은 변경 단계로 확대하지 않는다.

## 1. 작업 전 확인과 pull

먼저 현재 checkout에서 확인한다.

```bash
git status --short
git branch --show-current
git rev-parse HEAD
git remote -v
git branch -vv
```

- 새 구현 작업은 사용자 변경이 없는 `dev` checkout에서 `git pull --ff-only origin dev`로 최신화한 뒤 [이름 규칙](rules/collaboration.md)에 맞는 브랜치를 만든다.
- 별도 worktree가 필요하면 기존 checkout을 임의로 전환하지 않는다. `git fetch origin` 후 최신 `origin/dev` 커밋을 확인하고 그 커밋에서 작업용 worktree·브랜치를 만든다. 이 경우 원격 최신화는 fetch로 수행했다는 사실을 보고한다.
- 기존 작업을 이어갈 때는 해당 브랜치와 upstream을 확인한 뒤 `git pull --ff-only`한다. 기존 feature 브랜치를 `dev`로 바꿔 작업을 잃지 않는다.
- upstream이 없는 로컬 브랜치는 `git fetch origin` 후 기준 브랜치와 차이를 확인한다. `pull origin dev`로 다른 작업을 임의 병합하지 않는다.
- 미커밋 변경, 분기, 충돌로 동기화가 막히면 원인부터 확인한다. 임의 reset·변경 삭제·자동 stash를 하지 않고 기존 변경을 보존한다. 안전한 별도 worktree로 진행할 수 있으면 활용한다.
- 읽기 전용 진단이나 사용자가 특정 커밋·오프라인 작업을 지정한 경우 분석 대상을 pull로 바꾸지 않는다. 원격 확인·동기화하지 못했다면 기준 커밋과 이유를 알린다.

## 2. 진단과 범위 결정

- 요청한 결과, 현재 코드·설정·호출 흐름·테스트를 먼저 확인한다. API·이벤트 관련 작업은 [계약 규칙](rules/contracts.md)을 함께 적용한다.
- 원인과 필요한 변경을 연결한다. 구조 변경·업무 동작 변경·외부 계약 변경을 구분하고 요청 범위를 넘는 작업은 별도 제안으로 남긴다.
- 긴 작업은 기준 커밋·기존 변경·현재 단계·검증 상태를 중간에 알린다.

## 3. 변경과 검증

- [코드](rules/code.md)·[테스트](rules/tests.md) 기준에 따라 필요한 부분만 변경한다. 형식 정리와 무관한 업무 규칙 변경을 섞지 않는다.
- [도구](tooling.md)의 명령 중 영향에 맞는 검사를 실행한다. 기존 테스트를 우선 사용하고 필요한 검증만 추가한다.
- 테스트 이동 전후 시나리오·선택 경로를 확인한다. 태그 외에도 환경 조건과 실제 실행 수·스킵 여부를 확인한다.
- 도구가 실행되지 못했거나 캐시 결과를 재사용한 경우 실제 재실행과 구분한다. 기본 빌드 성공을 외부 환경 전체 검증으로 보고하지 않는다.

## 4. 리뷰와 결과 전달

- 기능 오류, 계약 영향, 가독성, YAGNI, 책임·의존 경계, 테스트 누락과 중복을 검토한다. [코드 기준](rules/code.md)에 따라 이름만으로 의도가 읽히는지, 긴 주석이 코드의 복잡함을 대신 설명하고 있지는 않은지도 확인한다.
- [협업 규칙](rules/collaboration.md)에 따라 커밋·PR 전에 독립 리뷰를 받고, 지적의 근거를 확인해 필요한 수정을 반영한다.
- 이슈·커밋·PR은 해당 [템플릿](README.md#템플릿)으로 작성하고 사용자가 요청한 Git 작업까지만 진행한다.
- 완료 보고는 변경 이유·결과·검증·미확인·계약 변경 여부와 저장 상태를 간결하게 전달한다. 리뷰만 요청받았다면 로컬 변경과 리뷰 결과를 전달하고 종료한다.
