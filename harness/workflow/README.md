# 작업 흐름

작업 크기와 현재 단계에 맞춰 적용한다. 아래 흐름을 매번 처음부터 반복하거나 별도 계획서·보고서를 만들 필요는 없다. 필요한 문서는 [진입점](../../AGENTS.md)에서 선택한다.

## 시작과 동기화

- 변경 전 브랜치·기준 커밋·미커밋 변경을 확인한다. 기존 작업을 이어갈 때는 upstream에서 `git pull --ff-only`로 동기화하고, 새 작업은 최신 기준 브랜치에서 시작한다.
- 별도 worktree나 upstream 없는 브랜치는 `git fetch origin` 후 기준 브랜치와 차이를 확인한다. 기존 사용자 변경을 보존하고, 분기·충돌이 있으면 임의 reset·변경 삭제·자동 stash 대신 상태에 맞는 방법을 선택한다.
- 읽기 전용 질문·진단이나 특정 커밋·오프라인 작업은 동기화로 대상을 바꾸지 않는다. 같은 작업을 이어가는 대화마다 pull을 반복할 필요는 없다. 원격 변경 확인이 필요할 때 다시 동기화한다.

## 변경과 검증

- 관련 코드와 근거를 먼저 확인하고 요청 범위 안에서 변경한다. 분석 요청을 임의의 구현으로 확대하지 않는다. API·이벤트 작업은 [계약 규칙](contracts.md)을 따른다.
- 변경 영향에 맞는 검증을 선택한다. [도구 안내](../tooling.md)는 명령 참고자료이며 모든 명령을 실행하는 체크리스트가 아니다. 필요한 검증을 판단하기 어려우면 관련 코드·테스트부터 확인한다.

## 리뷰와 전달

- 변경 대상의 규칙으로 자체 점검한다. 독립 리뷰는 [Git·리뷰 기준](#git-작업과-리뷰)에 따라 필요할 때 선택하며, 확인된 결함을 수정하면 해당 변경을 다시 점검한다.
- 결과는 변경 이유와 결과, 검증과 남은 한계, 계약 변경 여부, 저장 상태를 간결하게 전달한다. Git 작업은 사용자가 허용한 범위까지만 수행한다.

## 커밋과 PR을 나누는 기준

| 구분 | 기본 단위 |
|---|---|
| 커밋 | 하나의 의도를 설명하고 검증·되돌리기 영향을 판단할 수 있는 변경 |
| PR | 하나의 문제나 목표에 대해 리뷰하고 병합 여부를 결정할 수 있는 변경 묶음 |

- 커밋 구성은 작업자가 판단한다. 구현·테스트를 함께 묶거나 TDD의 실패 테스트와 구현을 나누는 방식 모두 허용한다.
- 검증은 최종 PR 변경을 기준으로 한다. 각 중간 커밋의 빌드·테스트 통과나 특정 커밋 분할 방식을 일률적으로 요구하지 않는다.
- PR은 관련 커밋 여러 개를 포함할 수 있다. 변경 이유·위험·되돌릴 시점이 다르고 독립적으로 검증·병합할 수 있다면 별도 PR로 나눈다.
- 파일 수·줄 수를 절대 기준으로 삼지 않는다. 리뷰어가 목적과 영향을 한 흐름으로 따라갈 수 있는지 판단한다. 무관한 작업을 합치거나, 하나의 변경을 이해하기 어렵게 잘게 나누지 않는다.
- 서로 의존하는 PR은 base 브랜치나 이슈 연결로 관계가 드러나면 충분하다. 별도 설명이 있어야 적용할 수 있는 경우에만 선행 PR·호환성·적용 순서를 덧붙인다.

예를 들어 하네스 구축과 기존 코드 정리는 목적과 검증이 달라 별도 PR로 나눌 수 있다. API 필드 변경에 필요한 구현·테스트·계약 수정은 같은 PR에서 관리할 수 있으며, 커밋 구성은 작업 흐름에 맞게 선택한다.

## Git 작업과 리뷰

- 커밋 전 사용자 변경이 섞이지 않았는지 staged diff를 확인하고 이동 파일의 추가·삭제 누락을 점검한다.
- 독립 리뷰는 변경의 위험도와 필요에 따라 선택한다. 커밋·PR 전 필수 단계로 두거나 리뷰 증빙·미수행 보고를 일률적으로 요구하지 않는다.
- 확정된 결함을 처리하고 변경된 부분은 다시 점검한다. 병합을 요청받으면 최신 HEAD와 기존 필수 검사 상태를 확인하고, 리뷰가 필요한 변경이면 함께 확인한다.
- 이 규칙은 이슈 생성·커밋·푸시·PR·병합을 자동으로 허용하지 않는다. 사용자가 요청한 범위에서 수행하고 이미 허용한 작업에 같은 확인을 반복하지 않는다.
- 로컬 변경 후 리뷰만 요청받았다면 그 상태로 결과와 위치를 전달한다. PR·병합 금지 등 명시한 제한을 작업 종료까지 유지한다.

## 작업 단계에 연결하기

1. 요청 범위와 현재 상태를 확인하고 관련 코드·테스트·계약으로 원인을 진단한다. 복잡하거나 불확실한 작업만 계획·리서치를 추가한다.
2. 필요한 변경을 수행하고 [코드 기준](../quality/code.md)으로 이름·업무 흐름·새 추상화의 필요를 검토한다. API·이벤트 의미가 바뀌면 [계약 절차](contracts.md)를 함께 적용한다.
3. 변경 후 `python harness/verify.py --dry-run`으로 검사 대상·이유를 확인한다. PR 전체를 검증할 때는 `--base <기준 ref>`를 지정한다.
4. 같은 옵션에서 `--dry-run`을 빼고 검사를 실행한다. 선택되지 않은 의미 검증은 관련 테스트·계약 대조로 보완한다. 이미 같은 변경에서 실행한 검사가 충분하면 형식적으로 반복하지 않는다.
5. 실패하면 원인을 수정하고 관련 검사를 다시 실행한다. 환경 부재·미실행·스킵을 성공으로 바꾸지 않는다. 검사 뒤 diff가 바뀌면 해당 영향의 검증을 갱신한다.
6. 최종 diff와 검증을 바탕으로 허용된 결과를 전달한다.

분석 전용 요청에는 변경·검사 실행을 자동으로 붙이지 않는다. 문서만 바뀌면 링크·내용을 확인하고 Java 빌드를 형식적으로 실행하지 않는다. Git 동기화·커밋·PR·게시 권한은 각 단계의 기존 기준을 따른다.
