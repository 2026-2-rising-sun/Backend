# API·이벤트 계약 기준

API·이벤트를 변경하거나 관련 코드를 리뷰할 때 적용한다. 계약은 구현과 함께 읽고, 확인한 범위만 보고한다.

## API 필수 절차

- API 문서 원본은 `contracts/api/<서비스명>.yaml`이다. 서비스 리소스에 수동 복사본을 만들지 않는다.
- API 관련 변경 전 컨트롤러·DTO·검증·인증 설정과 해당 서비스 YAML을 함께 읽는다.
- 경로, HTTP 메서드, 요청 파라미터·본문, 응답 필드·타입·상태 코드, 인증·권한, 멱등성 등 외부 계약을 바꾸면 같은 변경에 YAML도 수정한다.
- 내부 패키지 이동·포맷·업무 구현만 바꾸고 외부 계약이 같다면 문서 내용을 억지로 바꾸지 않는다. PR에 계약이 바뀌지 않았다는 고정 문구를 요구하지 않는다.
- 기존 호출자를 깨는 삭제·이름·타입 변경은 먼저 영향을 확인하고 변경 이유를 기록한다.
- 조건부·개발용 컨트롤러와 누락 ID 처리 경로도 문서에 포함한다. 실행 조건과 오류 동작을 명시한다.
- API 변경 후 `.github/scripts/api/requirements.txt`의 의존성을 설치한 환경에서 `python .github/scripts/api/check_structure.py`를 실행한다. 경로·메서드 불일치를 무시하거나 예외 목록으로 숨기지 않는다.
- 새 매핑 방식 때문에 정적 검사가 해석하지 못하면 검사기와 회귀 테스트를 함께 보완한다.
- 정적 검사는 직접 선언한 Spring MVC 경로와 HTTP 메서드만 비교한다. DTO 스키마·실제 응답·인증 동작·런타임 조건의 일치를 보장한다고 보고하지 않는다.
- 문서의 스키마·업무 의미 정합성은 위 작업 절차로 확인한다. 응답 검증이나 전체 E2E를 새로 추가할 때는 사용자와 범위를 정한다.

검사 환경 준비와 관련 명령은 [도구](../tooling.md)를 참조한다. YAML 내용의 유효성이나 경로 검사가 통과해도 모든 실제 응답을 검증한 것은 아니다.

## 이벤트 필수 절차

- 원본은 [contracts/events](../../contracts/events)의 계약 파일이다. 토픽·키·이벤트명·버전·봉투·필드 의미·예시를 관리한다.
- 변경 전 생산자와 소비자의 직렬화·역직렬화, 호환성, 중복·순서 처리 영향을 확인한다. 계약 정의만으로 연동 완료라고 하지 않는다.
- 필드 이름이 비슷해도 의미를 확인한다. 이벤트 발생 시각과 엔티티 수정 시각처럼 의미가 다르면 편의상 합치지 않는다.
- 내부 구현만 바뀌고 계약이 같다면 계약 내용은 유지한다. 외부 계약이 바뀌면 해당 계약과 영향을 받는 구현을 함께 갱신한다.
- YAML 참조·스키마·예시 검사, 실제 직렬화 표본 검사, 런타임 전달·DB 반영 확인을 구분한다. 실행 명령과 전제는 [도구](../tooling.md)를 따른다.
- Outbox·Inbox·DLQ 등 추가 설계를 계약 수정에 자동으로 끼워 넣지 않는다. 요청 범위를 넘는 과제는 별도로 제안한다.
