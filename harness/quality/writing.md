# 이름과 설명 작성 기준

브랜치·이슈·커밋·PR을 만들거나 리뷰할 때 적용한다. 동기화 절차는 [작업 절차](../workflow/README.md)에 있다.

## 이름 규칙

| 대상 | 형식 | 예시 |
|---|---|---|
| 이슈 | `[TYPE][scope] 한국어 작업 제목` | `[REFACTOR][commerce] 주문 생성 책임 정리` |
| 브랜치 | `type/#번호-영문-slug` | `refactor/#240-order-creation` |
| PR | `type(scope): 한국어 변경 내용 (#번호)` | `refactor(commerce): 주문 생성 책임 정리 (#240)` |
| 커밋 | `type(scope): 한국어 변경 내용` | `refactor(commerce): 주문 금액 계산 분리` |

- 타입은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `build`, `ci`, `perf`, `revert`. 이슈는 대문자를 사용하며 버그 타입은 기존 이슈 관례인 `BUG`를 쓴다.
- scope는 `shopping`, `commerce`, `live`, `member`, `notification`, `common`, `infra`. 여러 서비스의 공통 변경과 하네스 변경은 `common`을 사용한다.
- 브랜치 slug는 영어 소문자와 하이픈을 사용한다. 이슈가 연결된 작업은 브랜치·PR의 이슈 번호를 일치시킨다.
- 브랜치 slug는 쉬운 영어로 작업 대상이나 목적이 드러나게 짧게 쓴다. slug는 하이픈으로 구분한 영어 단어를 최대 5개까지 사용하되, 의미가 전달되는 범위에서 적은 단어를 권장한다. 타입과 이슈 번호는 단어 수에 포함하지 않는다. 이슈 제목 전체·구현 세부·불필요한 서비스명이나 날짜를 붙이지 않는다. 글자 수를 맞추기 위한 알아보기 어려운 축약도 피한다.
- 작업을 구분하기 어려운 포괄적인 이름과 긴 나열은 피한다. 구분에 꼭 필요한 단어만 추가한다.
- 기본은 관련 이슈 연결이다. 사용자가 이슈 생략 또는 로컬 작업만 요청하면 임의로 이슈를 만들지 않는다. 이 경우 `docs/backend-harness`, `docs(common): 백엔드 팀 하네스 구성`처럼 번호를 생략한다.
- 이슈 생성 전 로컬 준비 브랜치도 번호 없는 형식을 사용한다. 나중에 이슈를 만들었다고 기존 브랜치가 이미 번호 규칙을 따랐다고 보고하지 않는다.
- 기존 브랜치는 컨벤션 적용만을 위해 이름을 바꾸지 않는다. `dev`와 `main` 사이 통합 PR은 브랜치 형식 비교를 생략하고 실제 연결할 이슈가 있을 때만 번호를 넣는다.

## 설명 작성 필수 기준

- 설명은 한국어로 쓴다. 이슈는 “왜 이 작업을 하는가”, PR은 “어떻게 해결했고 무엇을 선택했는가”에 답한다.
- 이슈에는 현재 문제·영향, 작업이 필요한 이유, 원하는 결과와 완료 조건을 쓴다. 구현 방법을 미리 확정하거나 아직 하지 않은 작업을 완료한 것처럼 쓰지 않는다. 필요한 제약과 제안은 확정된 결정과 구분한다.
- PR은 변경 내용과 검증 결과를 한눈에 파악할 수 있게 쓴다. 짧은 변경 목록과 검증만으로 충분하면 그 형식을 사용한다.
- 설명 순서·제목·표·목록 구성은 자유롭게 선택한다. 중요한 선택이나 제약이 있을 때만 이유를 덧붙이고, 형식을 맞추려고 배경 설명을 늘리지 않는다.
- 중요한 선택이 있을 때만 이유와 감수한 비용을 쓴다. 단순 변경에 억지 트레이드오프나 설계 결정을 만들지 않는다.
- 확인하지 않은 성능·안정성 효과를 주장하지 않는다. 검증 성공·실패·스킵·미실행을 구분한다.
- 템플릿의 안내 주석·빈 항목·무관한 고정 링크를 최종 본문에서 제거한다. 선택 항목은 해당할 때만 사용한다.
- 커밋·PR 제목과 본문은 최종 diff를 기준으로 갱신한다. 작업 도중의 대화나 폐기한 접근은 중요한 판단 근거가 아니라면 생략한다.

## 간략하고 자연스럽게 쓰는 판단 기준

- 첫 문장과 설명 순서는 고정하지 않는다. 한 문장에는 한 가지 내용을 담고 익숙한 표현을 쓴다.
- 추상적인 개선 효과나 평가 대신 실제로 달라지는 동작을 쓴다. 같은 뜻을 반복하거나 불필요한 구현 용어로 설명하지 않는다.
- 작은 이슈는 필요한 이유와 완료 조건, 작은 PR은 해결 설명 한두 문장과 검증 결과면 충분하다. 복잡한 변경만 판단에 필요한 배경·영향을 더하고, 내용이 겹치는 항목은 합친다.
- 검증은 확인한 동작·결과와 중요한 실패·스킵·미검증 범위를 간결하게 쓴다. 테스트 개수나 검사 목록만으로 효과를 설명하지 않는다. 환경 차이가 결과 해석에 영향을 주면 명시하고, 긴 명령어·로그는 재현이나 실패 판단에 필요할 때만 첨부하거나 링크한다.
- 작성 후 각 문장이 작업 이유·해결 방법·중요한 판단·검증 범위를 이해하는 데 필요한지 확인한다. 없어도 판단이 같으면 삭제하거나 합친다. 필요한 제약과 미검증 사실은 짧게 쓰기 위해 생략하지 않는다.

## 템플릿 선택과 내용

| 대상 | 기본 구조 | 원본 |
|---|---|---|
| 기능 이슈 | 필요한 이유→목표 동작→완료 조건 | [기능](../templates/issue-feature.md) |
| 버그 이슈 | 증상·영향→재현→기대·실제→완료 조건 | [버그](../templates/issue-bug.md) |
| 리팩토링 이슈 | 현재 문제·필요성→개선 목표·유지할 동작→완료 조건 | [리팩토링](../templates/issue-refactor.md) |
| PR | 해결 방법·결과→선택 이유·트레이드오프(선택)→검증 | [PR](../templates/pull-request.md) |
| 커밋 | 변경 제목→이유·영향(선택)→이슈(선택) | [커밋](../templates/commit-message.md) |

템플릿은 참고용이며 항목·순서·분량을 강제하지 않는다. 계약 변경이나 선행 작업이 실제 적용에 영향을 주면 필요한 내용만 짧게 남긴다. 계약이 바뀌지 않았다는 고정 문구나 별도 의존성 항목은 요구하지 않는다. `Closes`·`Refs` 사용과 이슈 종료 시점은 담당자가 작업 흐름에 맞게 판단한다.
