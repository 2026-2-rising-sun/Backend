# 협업과 작성 기준

브랜치·이슈·커밋·PR을 만들거나 리뷰할 때 적용한다. 동기화 절차는 [작업 절차](../workflow.md)에 있다.

## 이름 규칙

| 대상 | 형식 | 예시 |
|---|---|---|
| 이슈 | `[TYPE][scope] 한국어 작업 제목` | `[REFACTOR][commerce] 주문 생성 책임 정리` |
| 브랜치 | `type/#번호-영문-slug` | `refactor/#240-order-creation` |
| PR | `type(scope): 한국어 변경 내용 (#번호)` | `refactor(commerce): 주문 생성 책임 정리 (#240)` |
| 커밋 | `type(scope): 한국어 변경 내용` | `refactor(commerce): 주문 금액 계산 분리` |

- 타입은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `build`, `ci`, `perf`, `revert`. 이슈는 대문자를 사용하며 버그 타입은 기존 이슈 관례인 `BUG`를 쓴다.
- scope는 `shopping`, `commerce`, `live`, `member`, `notification`, `common`, `infra`. 여러 서비스의 공통 변경과 하네스 변경은 `common`을 사용한다.
- 브랜치 slug는 영어 소문자와 하이픈을 사용한다. 이슈가 연결된 작업은 브랜치·PR의 이슈 번호를 일치시킨다.
- 기본은 관련 이슈 연결이다. 사용자가 이슈 생략 또는 로컬 작업만 요청하면 임의로 이슈를 만들지 않는다. 이 경우 `docs/backend-harness`, `docs(common): 백엔드 팀 하네스 구성`처럼 번호를 생략한다.
- 이슈 생성 전 로컬 준비 브랜치도 번호 없는 형식을 사용한다. 나중에 이슈를 만들었다고 기존 브랜치가 이미 번호 규칙을 따랐다고 보고하지 않는다.
- 기존 브랜치는 컨벤션 적용만을 위해 이름을 바꾸지 않는다. `dev`와 `main` 사이 통합 PR은 브랜치 형식 비교를 생략하고 실제 연결할 이슈가 있을 때만 번호를 넣는다.

## 설명 작성 필수 기준

- 설명은 한국어로 쓴다. 첫 문장에서 문제나 필요한 이유를 말하고, PR은 변경 후 동작까지 연결한다.
- 파일·클래스·메서드를 추가한 순서대로 나열하지 않는다. 리뷰어가 판단할 문제·결과·중요한 선택·검증을 남긴다.
- 중요한 선택이 있을 때만 이유와 감수한 비용을 쓴다. 단순 변경에 억지 트레이드오프나 설계 결정을 만들지 않는다.
- 확인하지 않은 성능·안정성 효과를 주장하지 않는다. 검증 성공·실패·스킵·미실행을 구분한다.
- 템플릿의 안내 주석·빈 항목·무관한 고정 링크를 최종 본문에서 제거한다. 선택 항목은 해당할 때만 사용한다.
- 커밋·PR 제목과 본문은 최종 diff를 기준으로 갱신한다. 작업 도중의 대화나 폐기한 접근은 중요한 판단 근거가 아니라면 생략한다.

## 간략하고 자연스럽게 쓰는 판단 기준

짧은 PR은 문제와 변경을 한두 문장으로 설명하고 검증 결과를 덧붙이면 충분하다. 복잡한 변경은 계약·설정·적용 순서·중요한 트레이드오프를 필요한 만큼 추가한다. 문장마다 같은 의미를 반복하거나 “효율적이고 견고한 구조를 구현했습니다” 같은 평가를 붙이지 않는다.

**피할 예**

> 테스트 클래스를 이동하고 package와 import를 수정했습니다. DisplayName을 추가하여 가독성과 유지보수성을 향상했습니다.

**권장 예**

> 로그인 HTTP 테스트가 Member 루트에 모여 있어 관련 코드를 찾기 어려웠다. 인증 컨트롤러 패키지로 옮기고, 테스트 목록에서 검증 의도가 보이도록 한국어 설명을 추가했다.

**중요한 선택이 실제로 있는 경우**

> PostgreSQL 테스트가 기존 테스트를 상속하는 구조는 유지했다. 준비 코드 중복을 줄이지만 부모 테스트 변경이 함께 영향을 주므로, 이동 후 두 실행 경로를 확인했다.

마지막 문장도 실제로 검증했을 때만 쓴다. 미실행이면 그 사실과 이유를 쓴다. 위 예시의 선택을 모든 리팩토링에 그대로 적용하지 않는다.

## 템플릿 선택과 내용

| 대상 | 기본 구조 | 원본 |
|---|---|---|
| 기능 이슈 | 필요한 이유→목표 동작→완료 조건 | [기능](../templates/issue-feature.md) |
| 버그 이슈 | 증상·영향→재현→기대·실제→완료 조건 | [버그](../templates/issue-bug.md) |
| 리팩토링 이슈 | 현재 문제→개선 방향·유지할 동작→완료 조건 | [리팩토링](../templates/issue-refactor.md) |
| PR | 문제와 변경→중요한 판단·영향(선택)→검증 | [PR](../templates/pull-request.md) |
| 커밋 | 변경 제목→이유·영향(선택)→이슈(선택) | [커밋](../templates/commit-message.md) |

이슈는 요청·완료 조건을 설명하며, 아직 하지 않은 작업을 완료한 것처럼 쓰지 않는다. PR의 검증에는 계약 변경 여부도 짧게 명시하고, 변경이 있으면 영향 항목에서 호출자·적용 순서를 설명한다. `Closes`는 실제 완료한 이슈, `Refs`는 관련·후속 이슈에 사용한다.

## Git 작업과 리뷰

- 커밋은 이해하고 검증할 수 있는 변경 단위로 구성한다. 사용자 변경을 섞지 않도록 staged diff를 확인하고 이동 파일의 추가·삭제 누락을 점검한다.
- 커밋·PR 전에는 작성자와 별개의 검토자가 변경을 리뷰한다. 팀원 또는 사용 가능한 독립 리뷰 도구를 활용하고, 리뷰를 받지 못하면 자체 점검과 구분해 보고한다.
- 확정된 결함을 처리하고 변경된 부분은 다시 검토한다. 병합을 요청받으면 최신 HEAD의 리뷰와 기존 필수 검사 상태를 다시 확인한다.
- 이 규칙은 이슈 생성·커밋·푸시·PR·병합을 자동으로 허용하지 않는다. 사용자가 요청한 범위에서 수행하고 이미 허용한 작업에 같은 확인을 반복하지 않는다.
- 로컬 변경 후 리뷰만 요청받았다면 그 상태로 결과와 위치를 전달한다. PR·병합 금지 등 명시한 제한을 작업 종료까지 유지한다.
