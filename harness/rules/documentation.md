# 문서 기준

문서를 작성·수정·정리하거나 결과를 보고할 때 적용한다.

## 원본 위치

| 내용 | 원본 |
|---|---|
| AI 작업 기준·작성 템플릿 | `harness/` |
| API·이벤트 계약 | `contracts/api/`, `contracts/events/` |
| 공유 기능명세·설계·협업 문서 | [팀 프로젝트 Notion](https://app.notion.com/p/3e9226545d1581989a9edefd9da775c4) |
| 패키지·파일 역할 등 코드 읽기 안내 | 요청 시 기존 `docs/code-guide/` 활용 |
| 포맷·빌드 실행 설정 | 실제 Gradle·EditorConfig 설정 |

코드 가이드는 팀 공유 설계 문서와 용도가 다르다. 현재 [gitignore](../../.gitignore)는 `docs/**/*.md`를 제외하므로 작성 전에 추적·공유 범위를 확인한다. 파일을 로컬에 저장한 것과 팀에 공유한 것을 구분하고 임의로 강제 추가하지 않는다.

## 필수

- 한국어로 작성하고 원본을 복제하기보다 링크한다. 관련 변경이 생기면 같은 작업에서 해당 설명도 갱신한다.
- 확인된 사실·검증 결과·제안·미확정을 구분한다. 팀 정책을 임의로 확정하지 않고 미결정 항목은 `팀 논의 · 미확정`으로 표시한다.
- 코드 근거는 해당 파일·심볼과 필요한 줄 위치를 제시한다. 줄 번호·실행 결과·현재 상태는 직접 확인한 기준으로 쓴다.
- 외부 문서를 수정할 때는 현재 내용을 조회하고 필요한 부분을 수정한 뒤 재조회해 반영을 확인한다. 하위 문서와 기존 내용은 보존한다.
- 요청하지 않은 외부 게시물·상시 작업 기록을 생성하지 않는다. 실제 작성·저장·공유한 범위만 보고한다.

## 진단과 완료 보고

진단은 `제목 → 부제 → 설명 → 실제 예시` 순서로 문제와 근거를 연결한다. 예를 들어 “테스트 실행 범위 — PostgreSQL 단독 태그의 제외” 아래 선택 설정과 해당 테스트를 함께 제시한다. 작은 질문에는 이 구조를 짧은 문단으로 표현해도 된다.

완료 보고에는 변경 이유와 결과, 실제 검증·스킵·미실행, API·이벤트 계약 변경 여부를 담는다. 로컬 파일·커밋·PR·병합 여부를 구분한다. 장기 작업은 기준 커밋·기존 변경·진행 단계·저장 상태를 중간에 알린다. 이슈·PR·커밋 설명은 [협업 기준](collaboration.md)을 따른다.
