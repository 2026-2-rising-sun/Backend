# 코드 기준

코드 작성·수정·리뷰에 적용한다. 테스트의 별도 기준은 [테스트](tests.md)를 따른다.

## 필수

- 직접 작성하는 설명·주석·Javadoc·내부 진단 및 검증 메시지는 한국어로 쓴다. 클래스·메서드·변수·패키지·태그·오류 코드·상태값은 영어 식별자를 유지한다.
- 기존 운영 로그와 라이브러리 원문은 유지한다. 예외·검증 메시지가 API 응답에 노출되면 [계약](contracts.md)과 호출자 영향을 확인한다. 한국어 정리를 이유로 기존 외부 메시지를 일괄 변경하지 않는다.
- 기존 포맷 설정을 사용한다. 실행 방법은 [도구](../tooling.md)를 따른다.
- 구조 정리 중 트랜잭션 경계·잠금 순서·멱등성·실패 복구·업무 정책을 의도 없이 변경하지 않는다.

## 가독성과 주석의 판단 기준

- 이름에 업무 의미를 담고, 순서대로 따라갈 수 있는 제어 흐름을 우선한다. 의미 없는 축약·압축된 조건문·불필요한 중첩을 피한다.
- 메서드는 이름으로 설명할 수 있는 작업 단위가 있을 때 나눈다. 한 줄을 숨기거나 계층을 통과시키기 위한 분리는 피한다.
- 주석은 코드만으로 알기 어려운 이유·제약·순서 의존성을 짧게 설명한다. 동작을 그대로 번역하거나 모든 메서드에 형식적인 Javadoc을 붙이지 않는다.
- 주석으로 긴 설명을 해야 이해되는 코드는 그대로 넘기지 않고 재검토한다. 모호한 이름, 섞인 책임, 복잡한 조건·중첩, 숨은 상태 변경을 먼저 확인하고 현재 작업 범위에서 코드를 단순하게 만든다.
- 주석을 줄이려고 의미 없는 메서드·계층을 추가하지 않는다. 잠금 순서·외부 제약·실패 복구처럼 코드만으로 드러나지 않는 이유는 남긴다. 상세 배경은 관련 명세·설계 문서로 연결하되, 코드 이해에 필요한 핵심 제약은 가까이에 둔다. 줄 수 자체를 제한하거나 필요한 설명을 지우지 않는다.

```java
// 피할 예: 재고를 정렬한다.
// 권장 예: 동시 주문의 잠금 순서를 맞춰 교착 위험을 줄인다.
items.sort(comparing(Item::productId));
```

## 이름의 판단 기준

- 변수·필드·매개변수는 담는 값의 업무 의미를, 클래스는 맡은 책임을 드러낸다. `data`, `info`, `manager`처럼 범위가 모호한 이름보다 현재 문맥에서 구체적인 이름을 쓴다.
- 같은 업무 개념에는 같은 용어를 쓴다. 기존 도메인·계약 용어를 먼저 확인하고, 서로 다른 개념을 같은 이름으로 뭉치지 않는다.
- 메서드는 무엇을 하는지 드러나는 동사로 짓는다. 조회처럼 보이는 이름에 저장·삭제·외부 전송을 숨기지 않는다. 불리언은 `isExpired`, `hasStock`, `canCancel`처럼 참일 때의 의미가 읽히게 하고 이중 부정을 피한다.
- 수량·금액·시간은 값의 의미와 단위를 구분한다. 타입으로 단위가 명확하지 않으면 `timeoutMillis`, `amountWon`처럼 이름에 드러낸다. 컬렉션은 복수형으로, 맵은 `ordersById`처럼 값과 키 관계가 보이게 짓는다.
- Java 클래스는 `UpperCamelCase`, 메서드·변수·필드는 `lowerCamelCase`, 상수는 `UPPER_SNAKE_CASE`, 패키지는 소문자를 따른다. `id`, `url` 등 통용되는 약어는 허용하되 임의의 축약과 타입 접두사는 피한다.
- 이름을 문장처럼 늘이거나 주변 문맥을 반복하지 않는다. 이름에 여러 역할을 나열해야 한다면 책임이 섞였는지 먼저 확인한다. 이름을 맞추기 위한 새 클래스·추상화는 만들지 않는다.
- 외부 DTO 필드·JSON 키·DB 컬럼·이벤트 필드 이름 변경은 단순 내부 정리가 아니다. [계약](contracts.md)과 저장 데이터·호출자 영향을 확인한다. 무관한 기존 이름을 일괄 변경하지 않는다.

아래는 문맥에 맞게 적용할 예시이며 특정 접미사를 강제하지 않는다.

| 모호한 이름 | 의도를 드러낸 이름 | 드러내는 의미 |
|---|---|---|
| `cnt` | `remainingStock` | 남은 재고 수량 |
| `timeout` | `timeoutMillis` | 숫자 시간값의 단위 |
| `process(order)` | `cancelOrder(order)` | 수행하는 업무 동작 |
| `OrderHelper` | `OrderPriceCalculator` | 주문 금액 계산이라는 책임 |

## YAGNI·책임·공통화의 판단 기준

- 현재 요구에 필요한 만큼 구현한다. 미래 확장만을 위한 인터페이스·설정·계층·범용 도구를 미리 만들지 않는다.
- 외부 경계나 실제 구현 차이를 분리할 이유가 있을 때 추상화를 도입한다. 여러 변경 이유가 섞인 책임은 분리하되 줄 수 자체를 기준으로 삼지 않는다.
- 모양이 비슷한 코드보다 의미와 변경 이유가 같은 코드를 공통화한다. 서비스 고유 업무 규칙은 해당 서비스가 소유한다.
- 공통 모듈 변경 전 소비 서비스를 확인한다. 공통 엔티티·삭제 정책 변경 전 대상 엔티티, ID·시간·삭제/복구 동작, 조회·유일성·API·이벤트 영향을 조사한다.

## 패키지의 판단 기준

- 업무 도메인 아래 `controller`, `service`, `repository`, `entity`, `dto`를 기본으로 필요한 역할만 둔다. 빈 폴더와 형식적인 계층을 만들지 않는다.
- 외부 서비스 호출은 `client.shopping`처럼 대상과 책임이 드러나게 배치한다. 서비스 내부 구현을 다른 서비스가 직접 참조하도록 연결하지 않는다.
- 서로 다른 책임이 섞인 `util`, `common`, `manager`를 편의상 늘리지 않는다. 공통 코드도 구체적인 역할이 드러나는 이름을 쓴다.
- 기존 구조를 전면 교체하지 않는다. 현재 흐름을 읽고 변경 대상에 필요한 이동만 수행한다.
