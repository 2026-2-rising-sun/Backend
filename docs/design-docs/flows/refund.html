현재 dev: 기존 사용자 환불

정책0 실행 주문은 #390에서 삭제된 옛 RefundIntakeService가 접수했고 지금은 409로 거절한다. 새 주문서의 사용자 환불을 이 입구가 제공한다고 해석하지 않는다. 소유권·원결제 성공·확정 시각부터 168시간 미만·대상·누적 금액·멱등 원문을 확인한다. 항목 전체 환불 계약이며 신규 수량 환불 완료를 뜻하지 않는다.

출발 도착 조건·처리
legacy PAID refund_request PROCESSING 원결제 HTTP 조회는 Core TX 밖에서 하고 잠금 아래 연결을 재검증한다. 대상·금액·전달 원문을 저장한다.
영속 REFUND 전달 삭제됨(#390) 정책0 주문의 환불 요청은 409이고 Payment를 호출하지 않는다. 정책0 환불 대상 조회는 LEGACY_REFUND_UNAVAILABLE을 돌려준다. 정책1 주문서 환불은 Kafka 요청·결과 경로를 쓴다.
PROCESSING UNKNOWN 유효한 미확정 결과를 보존하고 재전달·조회한다. 시간 경과만으로 실패로 확정하지 않는다.
PROCESSING/UNKNOWN SUCCESS 검증된 성공 대상만 REFUNDED로 바꾸고 SKU 재고를 복구한다. 중복 결과는 다시 복구하지 않는다.
PROCESSING/UNKNOWN FAILED 확정 실패만 반영하며 성공 재고 복원을 하지 않는다.
일부 항목 환불 묶음 PAID 유지 모든 자식 주문이 REFUNDED일 때만 묶음도 REFUNDED가 된다.

현재 서비스 application.yml의 commercecore.refunds.api-enabled와 execution-enabled는 true다. 코드 생성자의 기본 false와 구분한다. dev Payment의 기존 내부 환불 실행 API는 삭제됐고, 새 주문서 환불은 Kafka 요청·결과 경로(아래 결과 계약)로 Payment가 실행한다(이슈 #385·#370·#386, PR #394~#396). 구 Mock 시나리오·과거 테스트 성공은 현재 Payment 실행 증거가 아니다.

현재 dev: 종료 주문의 늦은 승인

새 주문서가 보상 없이 EXPIRED/CANCELLED/FAILED로 닫힌 뒤 승인 사실을 확인하면 주문을 되살리지 않는다. 새 주문서가 FAILED가 되는 경우는 Payment가 결제를 CANCELED로 끝낸 경우뿐이다. 승인 거절은 주문을 FAILED로 끝내지 않고 PENDING_PAYMENT로 되돌린다(#418). PaymentRelayService는 KafkaRefundService.compensateLocked로 core_refund_intent(purpose SYSTEM_COMPENSATION, reason LATE_APPROVAL)와 commerce.refund.requests.v1의 RefundRequested Outbox를 같은 TX에 저장한다. Payment가 이 요청을 실행하고 payment.refund.results.v1의 RefundResultRecorded로 결과를 보낸다. Core는 구 payment.refund-results.v1을 구독하지 않는다(#390). 환불 결과는 CommonRefundResultConsumer가 받아 KafkaRefundService가 core_refund_intent 원요청과 대조해 반영한다. 옛 late_approval_refund·payment_relay_refund 행은 지우지 않은 과거 기록이고 새 늦은 승인은 쓰지 않는다.

Payment의 요청 consumer와 결과 producer는 #385로 dev에 있다. Kafka 발행·계약 검사는 Payment 접수나 금전 환불 완료가 아니다.

사용자 환불과 시스템 보상의 분리

사용자 요청과 시스템의 결제 미확정을 같은 취소 상태로 취급하지 않는다.

구분 현재 구현 완료 전제
사용자 환불 주문 상태는 PAID·PARTIALLY_REFUNDED를 유지하고 진행은 refund_request가 가진다. 성공 수량에 따라 REFUNDED/PARTIALLY_REFUNDED 원요청·금액·대상과 맞는 결과만 반영
시스템 보상 그 승인 시도의 접수부터 600초 처리 기한에 닿은 PAYMENT_CONFIRMING만 COMPENSATION_PENDING(사유 APPROVAL_UNKNOWN). 명시적 UNKNOWN은 기한까지 조회를 이어 간다 전환 TX에서 재고·쿠폰을 한 번 해제(savepoint). SUCCEEDED/NO_CHARGE 결과로 CANCELLED가 되며 다시 해제하지 않는다. 전환 때 해제하지 못한 주문만 이때 해제
공통 요청/결과 commerce.refund.requests.v1 → payment.refund.results.v1 dot 토픽과 purpose·금액·판매자별 원문을 실제 provider가 함께 구현
종료 뒤 승인 보상 없이 닫힌 주문만 주문 부활 없이 LATE_APPROVAL 보상을 요청한다. 이미 보상 중이면 승인 사실만 남기고 기존 요청으로 수렴한다 주문당 보상 1건은 Core가 fence 확인으로 지킨다. 요청 ID는 UUID다. 원결제 ID 연결과 결과 원문 검증 유지

결과 계약 (#384)

Payment 결과 계약은 payment-refund-results.yaml이다. 구 payment.refund-results.v1·RefundExecutionResolved 계약은 이 계약으로 바뀌었다.

출발 도착 조건·처리
Core RefundRequested Payment 환불 PROCESSING commerce.refund.requests.v1, 키 orderRef. 고객 환불(USER_REFUND)과 시스템 보상(SYSTEM_COMPENSATION)이 같은 토픽이다. refundRequestId로 한 번만 접수하고 원문을 저장한다.
Payment 환불 RefundResultRecorded payment.refund.results.v1, 키 orderRef. payload는 요청 원문 그대로에 executionId(UUID, 요청당 고정)·resultVersion(1부터)·status·refundedAmount·resolvedAt·nextActionAt(null)·failureCode를 더한다.
요청 필드 계약 paymentId는 USER_REFUND·SYSTEM_COMPENSATION 모두 필수다. 사유는 USER_REFUND의 CUSTOMER_REQUEST, SYSTEM_COMPENSATION의 APPROVAL_UNKNOWN·LATE_APPROVAL만 쓴다.
결제 없음·불일치 FAILED 결과 돈을 움직이지 않는다. failureCode PAYMENT_NOT_FOUND·PAYMENT_MISMATCH.
같은 ID·같은 본문 저장 결과 재발행 같은 resultVersion·같은 payload, 새 eventId. 결과가 아직 없으면 보내지 않는다.
같은 ID·다른 본문 결과 없음 Payment가 REQUEST_CONFLICT 수신으로 기록하고 ERROR 로그. Core가 원문과 다른 결과를 거부해 파티션이 막히는 것을 피한다(#389).
시스템 보상 FAILED 더 높은 버전 SUCCEEDED·NO_CHARGE 시스템 보상만 허용한다. NO_CHARGE는 failureCode: NO_CHARGE, 환불 금액 0.
결과 불명 결과 없음 Payment는 UNKNOWN을 보내지 않는다(status는 SUCCEEDED·FAILED·NO_CHARGE). 확정될 때 보낸다. nextActionAt은 항상 null이다.
미승인 종료 NO_CHARGE 시스템 보상만 쓴다. failureCode: NO_CHARGE, 환불 금액 0.

Payment의 요청 consumer와 결과 producer는 #385로 dev에 있다. Core는 paymentId 없는 보상 요청을 만들지 않는다. Payment 파서는 #402에서 계약만 받는다(paymentId 필수, 사유 3개). 계약 밖 요청은 결과를 만들지 않고 DLT로 보낸다. 이 문서의 계약 검사는 실제 토스 환불 완료를 증명하지 않는다.
