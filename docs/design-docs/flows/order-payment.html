주문·결제 서비스 간 흐름

전체 관계도 1

화살표 번호는 아래 관계·처리 조건표의 행 순서입니다. 배치는 실행 순서가 아닙니다.

새 주문서 경로는 결제창 준비와 실제 승인을 나눈다. 준비 동안 생성부터600초 PENDING을 유지하고 인증 후 승인 접수에서 PROCESSING 별도600초를 시작한다. 기존 공개 legacy 경로도 유지한다. Payment 실행·원장은 Payment 서비스가, 주문·재고·쿠폰과 전달 기록은 CommerceCore가 소유한다.

기준: 2026-11-27 dev ba9be27c(#416~#418 머지 뒤). 새 주문서 결제 HTTP 중계와 legacy 공개 입구가 함께 남아 있다. 기존 Mock 내부 결제·환불 API는 Payment에서 삭제됐지만 새 생성·승인·조회 어댑터는 별개다. 구 호출의 실패를 새 결제 경로 전체의 403으로 일반화하지 않는다. 보상 대기와 환불 흐름은 환불 흐름에서 설명한다.

새 계약 경로

결과를 받는 주 경로는 Core 복구 루프의 1초 폴링(Payment HTTP 조회)이다. payment.execution.results.v1의 PaymentApproved는 보조 경로다.

Payment 환불 결과 Core 환불 상태 payment.refund.results.v1의 RefundResultRecorded를 core_refund_intent 원요청과 대조해 반영. 구 payment.refund-results.v1 구독은 #390에서 삭제됨

보상 대기와 재고 사본

처리 기한(승인 접수부터 600초)까지 결과를 모르면 주문을 COMPENSATION_PENDING(보상 대기)으로 바꾸고 SYSTEM_COMPENSATION 환불 요청을 보낸다. 명시적 UNKNOWN만으로는 보상하지 않고 기한까지 조회를 이어 간다. 보상 대기로 바꾸는 TX에서 재고·쿠폰 예약을 한 번 해제한다(payment_group.compensation_released_at, V118). 해제가 논리적으로 실패하면 JDBC savepoint까지만 되돌리고 보상 요청은 커밋한 뒤, 보상 완료(SUCCEEDED 또는 NO_CHARGE)로 CANCELLED가 될 때 다시 해제한다. 락 타임아웃·SQL 오류처럼 트랜잭션 밖으로 나간 예외는 보상 요청까지 롤백하고 다음 기한 판정에서 다시 시도한다. 보상 결과는 예약을 다시 해제하지 않는다. 보상 대기 주문은 되살아나지 않는다.

보상 행은 완료 뒤에도 정상 승인 재개를 막는 영속 fence다. 보상이 있는 주문은 승인 API 재진입, 결제창 열기, 전달 재송신, 구매자 취소, 만료 판정, 사용자 환불 접수를 모두 거절하거나 건너뛴다. 보상됐거나 닫힌 주문의 남은 승인 전달은 dispatch 때 TIMEOUT(ORDER_CLOSED)으로 닫아 복구 루프가 계속 집지 않게 한다.

회원의 진행 중 주문 제한은 결제 대기(PENDING_PAYMENT)와 결제 확인 중(PAYMENT_CONFIRMING) 주문에만 걸린다. 보상 대기 주문이 있어도 같은 회원은 새 주문을 만들고 결제할 수 있다. 두 주문의 재고·쿠폰 예약은 서로 섞이지 않는다. 이 제한은 PurchaseGuard.requireNoActive, 부분 unique 인덱스(V117), PaymentRelayService.active가 함께 지킨다. 보상 대기 주문은 활성 주문 조회에 나오지 않는다. provider 부재·계약 불일치·paymentId 복구 차단이 남아 있다.

예약·소진·해제·환불 복원으로 바뀐 재고는 SKU dirty revision을 올리고 기본 60초 배치가 Catalog로 보낸다. Catalog 재고는 표시 정보이며 이 주문 처리의 원본 검증·잠금을 대신하지 않는다. CDC 경로와 최종 검증 범위를 따른다.

남은 구현 갭

갭 영향 처리

기존 경로와 이행

정책0(legacy) 주문의 PAYMENT/REFUND 전달과 Payment 호출 경로는 #390에서 삭제됐다. 옛 주문 생성 API는 Frontend #89 전환 전까지 남지만 그 주문은 결제되지 않고 만료된다. 정책0 주문의 환불 요청은 409이고 환불 가능 조회는 LEGACY_REFUND_UNAVAILABLE을 돌려준다. 옛 late_approval_refund·payment_relay_refund 테이블과 기존 행은 지우지 않았다. 새 늦은 승인은 이 테이블에 쓰지 않고 core_refund_intent로 보상을 요청한다. 같은 주문에 옛 payment_relay_refund 행이 있으면 보상 요청 생성이 예외로 막혀 승인 반영 TX 전체가 롤백되므로 별도 복구가 필요하다. 과거 번호/기한/금액/기존 null 처리기한을 임의 재작성하지 않는다. 토스 테스트 환경의 주문 → 승인 → 부분·전체 환불 확인은 #367에 기록했다. 운영 결제·배포와 과거 미확정 거래의 운영 대사는 후속이다.

알려진 테스트 공백: 정책0 주문 환불 409, 옛 payment_relay_refund 행이 있을 때 늦은 승인 롤백은 단언하는 테스트가 없다.
