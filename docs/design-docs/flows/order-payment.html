화살표 번호는 아래 관계·처리 조건표의 행 순서입니다. 배치는 실행 순서가 아닙니다.

새 주문서 경로는 결제창 준비와 실제 승인을 나눈다. 준비 동안 생성부터600초 PENDING을 유지하고 인증 후 승인 접수에서 PROCESSING 별도600초를 시작한다. 기존 공개 legacy 경로도 유지한다. Payment 실행·원장은 팀원 소유이며 Core는 주문·재고·쿠폰과 전달 기록을 소유한다.

기준: 2026-11-20 dev d42c3b787f12b716789d35c8df37dd63a2b42ddc. 새 주문서 결제 HTTP 중계와 legacy 공개 입구가 함께 남아 있다. 기존 Mock 내부 결제·환불 API는 Payment에서 삭제됐지만 새 생성·승인·조회 어댑터는 별개다. 구 호출의 실패를 새 결제 경로 전체의 403으로 일반화하지 않는다. 보상 대기와 환불 흐름은 환불 흐름에서 설명한다.

보상 대기와 재고 사본

승인 응답 유실·명시적 UNKNOWN 또는 종료 주문의 늦은 승인이면 주문을 COMPENSATION_PENDING(보상 대기)으로 바꾸고 SYSTEM_COMPENSATION 환불 요청을 보낸다. 보상 대기 동안 재고·쿠폰 예약은 보존하고, 검증된 완료 결과(SUCCEEDED 또는 NO_CHARGE)를 받아 CANCELLED로 확정할 때 한 번만 해제한다. 처리기한 만료의 EXPIRED 즉시 해제와 보상 완료 후 해제는 다른 경로다.

회원의 진행 중 주문 제한은 결제 대기(PENDING_PAYMENT)와 결제 확인 중(PAYMENT_CONFIRMING) 주문에만 걸린다. 보상 대기 주문이 있어도 같은 회원은 새 주문을 만들고 결제할 수 있다. 두 주문의 재고·쿠폰 예약은 서로 섞이지 않는다. 이 제한은 PurchaseGuard.requireNoActive, 부분 unique 인덱스(V117), PaymentRelayService.active가 함께 지킨다. 보상 대기 주문은 활성 주문 조회에 나오지 않는다. provider 부재·계약 불일치·paymentId 복구 차단이 남아 있다.

예약·소진·해제·환불 복원으로 바뀐 재고는 SKU dirty revision을 올리고 기본 60초 배치가 Catalog로 보낸다. Catalog 재고는 표시 정보이며 이 주문 처리의 원본 검증·잠금을 대신하지 않는다. CDC 경로와 최종 검증 범위를 따른다.

기존 경로와 이행

legacy PAYMENT/REFUND 전달은 기존 requestId/원문을 유지한다. 기존 0원 경로도 유지하며 새 계약의 양수 제약은 새 order-sheets에만 적용한다. legacy의 late_approval_refund(REQUIRED)와 새 원결제용 payment_relay_refund(REQUESTED)는 별개다. 과거 번호/기한/금액/기존 null 처리기한을 임의 재작성하지 않는다. Frontend 호출자 전환과 SDK 대역 브라우저 검증은 확인했다. 실제 위젯 설정·실SDK/실PG·실환불 및 과거 미확정 거래의 운영 대사는 후속이다. 사용자는 이를 구분해 CommerceCore 범위의 dev 병합을 승인했으며 이번 통합은 운영 결제·배포 완료를 뜻하지 않는다.
