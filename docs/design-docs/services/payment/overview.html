Payment

전체 관계도 1

화살표 번호는 아래 관계·처리 조건표의 행 순서입니다. 배치는 실행 순서가 아닙니다.

책임: 결제·환불 실행, PG(토스) 연동, 원장, 결과 Outbox.

결제 재설계(#337)가 진행 중이다. 결제 1차(결제 생성·승인·결과 불명 복구·만료)와 환불 요청 접수(#385)는 구현했고, 환불 실행부터는 새 설계에만 있다. 현재 코드 절은 지금 코드에 있는 것만 적는다.

현재 코드 (결제 1차)

결제 재설계의 V4 스키마와 Commerce용 내부 API 3개(결제 생성·결제창 다시 열기·조회)가 있다. 토스 결제 클라이언트(승인·조회·취소, 결과 4분류)와 승인 처리 서비스(ApprovalService·PaymentOutcomeService)가 있다. 승인 처리는 검증·APPROVING 전환을 커밋한 뒤 트랜잭션 밖에서 토스를 부르고, 결과를 상태·pg_call·승인 분개·PaymentApproved outbox에 한 트랜잭션으로 반영한다. 승인 API(ApprovalController)는 검증·APPROVING 전환 뒤 토스 호출·반영을 가상 스레드에 넘기고 최대 8초(payment.approval.response-wait)만 기다려, 넘으면 202 PENDING으로 답한다. 결과 불명 복구·만료 스케줄러 3개(ApprovingSweeper: APPROVING 3분 정체 → UNKNOWN, UnknownPaymentPoller: UNKNOWN을 토스에 조회해 확정·마감 30분 뒤 ERROR 로그, PaymentExpiryJob: 만료된 CREATED → CANCELED)가 payment.recovery.enabled(기본 켜짐)일 때 돈다. 분산 락은 없고 조건부 UPDATE로 한 번만 반영한다(#349). 기존 Mock 결제·환불 코드는 #347에서 지웠다.

  • API: API HTML · 계약 YAML. X-Service-Token(commercecore)만 허용하고, 허용 목록(/v1/internal/payments, …/{orderRef}, …/{orderRef}/checkouts, …/{orderRef}/approval) 밖의 /v1/internal/**는 403이다.
  • 결제 키는 orderRef다. 같은 orderRef 생성은 INSERT … ON CONFLICT DO NOTHING의 영향 행 수로 판단하고, 결제창은 CREATED·만료 전 조건부 UPDATE로 회차를 올린다. 상세는 #348 설계서.
  • DB: ERD 설명 · 관계도

  • 결과 이벤트: 계약 YAML. PaymentApproved(키 orderRef, 토픽 payment.execution.results.v1)로 교체했다(호환 깨짐). CommerceCore는 주문서 결제 중계(/v1/order-sheets, HttpPaymentRelayClient)로 새 내부 API를 부르고 PaymentApproved를 소비한다. 옛 HttpPaymentClient 경로는 #347에서 지운 API를 부르므로 동작하지 않는다.

  • 서비스 간 흐름: 주문·결제 · 환불

시각 자료

범위와 불변조건

상태는 setter로 바꾸지 않고 이전 상태 조건부 UPDATE로만 바꾼다. 0행이면 다시 읽어 판단한다. 토스 호출은 DB 트랜잭션 밖이고, 호출 전에 APPROVING과 호출 기록(pg_call, 결과 UNKNOWN)을 먼저 커밋한다. 토스 결과를 한 번이라도 모르면 CREATED로 되돌리지 않는다. 승인 분개와 PaymentApproved outbox는 APPROVED로 바꾸는 UPDATE가 1행일 때만 같은 트랜잭션에서 쓴다. 토스에서 승인됐는데 우리 결제를 APPROVED로 바꿀 수 없으면 CANCELED로 선점한 뒤 토스 응답의 paymentKey로 전액 취소한다. 이미 승인된 결제는 취소하지 않는다. 복구·만료 스케줄러는 분산 락 없이 돌고, 같은 행을 여러 인스턴스가 집어도 조건부 UPDATE라 한 번만 반영된다.

전이

출발 도착 조건·부수 효과
신규 CREATED 결제 생성. 같은 orderRef는 ON CONFLICT DO NOTHING 영향 행 수로 판단한다. 첫 결제창 {orderRef}-1.
CREATED CREATED 결제창 다시 열기. 만료 전일 때만 pg_order_id를 다음 회차로 바꾼다.
CREATED APPROVING 승인 검증 통과. WHERE status='CREATED' AND pg_order_id·amount·buyer_id 일치 AND expires_at > now(). 동시 요청은 한 건만 1행이다. 같은 트랜잭션에서 paymentKey 저장, pg_call(CONFIRM, UNKNOWN) 기록.
APPROVING APPROVED 토스 성공이고 응답(DONE·orderId·totalAmount·paymentKey)이 DB 값과 맞다. 승인 분개(PG 보관금/구매자 예수금)와 PaymentApproved outbox를 함께 쓴다.
UNKNOWN APPROVED 같은 승인 반영 함수(applyDone). 불명 뒤 재호출이 성공했거나 조회기가 DONE을 확인했다. 주문이 이미 닫혔어도 같다. 동시에 반영해도 1행만 바뀌고 나머지는 다시 읽어 APPROVED면 끝낸다.
APPROVING CREATED 첫 호출이 거절이거나 토스에 가지 않았다. approving_at과 pg_order_id를 비운다. 같은 결제창으로 다시 승인하면 STALE_CHECKOUT이라 새 결제창이 필요하다.
APPROVING UNKNOWN 첫 호출이 불명이고, 같은 멱등 키로 1번 더 부른 결과도 성공이 아니다. 첫 조회 10초 뒤, 조회 마감은 payment.recovery.check-deadline(30분) 뒤.
APPROVING UNKNOWN 정체 스위퍼. approving_at이 3분(approving-stuck-after) 넘게 지났다(승인 처리 중 서버 종료 등). 바로 조회(next_check_at = now()), 마감 30분 뒤. 바깥 AND status='APPROVING'으로 동시 실행에도 한 번만 바뀐다.
UNKNOWN UNKNOWN 조회기. 조회 차례가 되면 토스를 부르기 전에 다음 조회를 예약해 선점한다(WHERE status='UNKNOWN' AND next_check_at <= now(), 0행이면 다른 인스턴스가 집음). 간격은 불명이 된 뒤 지난 시간이 40초 미만 30초, 100초 미만 1분, 이후 5분이고 마감을 넘기지 않는다. 조회 결과가 IN_PROGRESS 등·거절·보내지 않음·불명이면 유지하고 마지막 토스 상태를 pg_status에 남긴다. PARTIAL_CANCELED는 사람 확인 ERROR 로그.
UNKNOWN UNKNOWN 조회 마감이 지났다. next_check_at = NULL로 조회 대상에서 빼고(1행일 때만) payment.recovery.deadline ERROR 로그를 1번 남긴다. 토스를 부르지 않는다. 이후는 거래 대사가 맡는다.
APPROVING CANCELED 토스 성공인데 응답이 맞지 않아 보상 취소한다. 토스 취소 전에 CANCELED로 선점하고(조건부 UPDATE 한 번), 취소가 성공이 아니면 CANCELED로 두고 사람 확인용 ERROR 로그를 남긴다(자동 재시도 없음).
UNKNOWN CANCELED 같은 보상 취소. 조건은 status IN ('APPROVING','UNKNOWN','CREATED'). 0행이고 결제가 APPROVED(이후)면 토스 취소를 부르지 않는다.
CREATED CANCELED 같은 보상 취소(토스는 승인했는데 우리 결제가 이미 CREATED로 돌아간 경우).
UNKNOWN CREATED 조회 결과 ABORTED·EXPIRED. approving_at·pg_order_id·next_check_at·check_deadline_at을 비운다. 새 결제창으로 다시 결제한다. WHERE status='UNKNOWN'.
UNKNOWN CANCELED 조회 결과 CANCELED(전액 취소). 분개 없이 닫고 WARN 로그. WHERE status='UNKNOWN'.
CREATED CANCELED 만료. expires_at < now()인 CREATED를 묶음으로 닫는다. 분개·이벤트 없음. 승인 시작(expires_at > now())과 같은 행을 노려도 한쪽만 1행이다.

Payment 환불 실행

환불 요청 접수(#385)와 고객 환불 실행(#370)이 있다. RefundRequestListener가 commerce.refund.requests.v1을 받아 RefundRequestParser로 봉투·키·요청 ID·목적·금액을 확인하고, 해석할 수 없으면 commerce.refund.requests.v1.payment.dlt로 보낸다(RefundConsumerConfiguration: DB 장애만 무한 재시도, 그 밖은 5회 재시도 뒤 DLT). RefundIntakeService는 refund_request_id로 한 번만 접수하고 원문을 저장한다.

  • 결제가 없거나 paymentId가 없거나 다르면, 또는 같은 결제에 진행 중인 시스템 보상이 있으면 돈을 움직이지 않고 FAILED 결과를 같은 트랜잭션의 outbox로 payment.refund.results.v1에 보낸다.
  • 같은 요청·같은 본문은 저장한 결과를 그대로 다시 보낸다. 다른 본문은 refund_request_conflict에 기록하고 결과를 보내지 않는다.
  • 유효한 요청은 PROCESSING으로 접수하고 RefundIntakeService.execute의 목적별 분기에서 끝난다. 시스템 보상(#386) 실행이 붙기 전까지 보상 요청은 토스 취소를 부르지 않고 결과도 보내지 않는다.
  • 고객 환불 실행(TossUserRefundExecutor): claim으로 선점하고, 결제 행 잠금 안에서 상태·판매자 주문·누적 한도를 검사한 뒤 UNKNOWN으로 예약해 커밋하고 트랜잭션 밖에서 토스 취소를 부른다. PROCESSING은 토스에 가지 않은 상태, UNKNOWN은 갔을 수 있는 상태다. UNKNOWN은 결제 조회의 cancels[]에서 요청별 취소 사유로 자기 취소를 찾고, 없으면 같은 멱등 키(refund_request_id)로 다시 요청한다. 조회 마감이 지나면 UNKNOWN으로 멈추고 payment.refund.deadline ERROR 로그를 남긴다. 전체 0원 요청은 결제 상태만 확인하고 토스·분개·결제 변경 없이 SUCCEEDED(0)로 답한다.
  • 성공 반영(RefundSettlement.settle): 한 트랜잭션에 환불 SUCCEEDED·결과 outbox, 결제 환불액·상태, refund_item, LED-REFUND-01 분개를 쓴다. 환불 행 조건부 UPDATE가 먼저라 동시 호출도 한 번만 반영하고, 결제 UPDATE가 0행이면 전체를 롤백한다.
  • 실행 공용 기반: execute는 목적별로 UserRefundExecutor(refund/service/user, #370)와 CompensationExecutor(refund/service/compensation, #386)를 부른다. 보상 쪽 구현(PendingCompensationExecutor)은 아직 로그만 남긴다. 확정 결과는 RefundResultService.record(조건부 UPDATE + 같은 트랜잭션 outbox, 시스템 보상만 FAILED 뒤 재확정)로, 재처리는 RefundRepository.findDue(목적별, next_attempt_at이 지난 PROCESSING·UNKNOWN)와 claim(선점)으로 한다. 토스 부분 취소는 TossPaymentsClient.cancel(…, cancelAmount)다.
  • execute는 이번에 새로 넣은 행에서만 불린다. 같은 요청을 다시 받아도, 커밋 뒤 execute 전에 죽었거나 execute가 예외를 던져도 다시 불리지 않는다. 끝나지 못한 PROCESSING은 실행 PR의 재처리 스케줄러(REF-EXEC-01)가 집어야 한다.
