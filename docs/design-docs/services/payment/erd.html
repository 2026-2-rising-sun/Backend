Payment DB ERD

전체 관계도 1

화살표 번호는 아래 관계·처리 조건표의 행 순서입니다. 배치는 실행 순서가 아닙니다.

코드 삭제됨: 아래는 #347에서 지운 Mock 구현의 기록이다. 테이블은 아직 남아 있고 #348의 V4 마이그레이션에서 지운다. 새 설계는 Payment 도메인 홈에 있다.

기준: e5a1b66bf3b06a971b1242dd02bd623e717c2902의 코드·계약 조사. #330의 미커밋 문서 변경을 포함하며 업무 코드 변경은 없다. 실제 DB·HTTP·Kafka·PG 실행 검증은 별도다.

시각 자료

전체 CREATE/ALTER 순서를 대조한 테이블·핵심 키·관계 요약이다. 전체 열 타입·인덱스·CHECK와 데이터 이관 SQL은 아래 원본을 따른다. 운영 DB에 적용된 실제 스키마를 조회한 결과는 아니다.

테이블

테이블 핵심 키·열 DDL 근거
payment_attempt PK id; UQ request_id, payment_id; order_id; payment_group_id; amount; status; retry_count; lease_token/lease_until V1
mock_gateway_result PK/FK attempt_id; outcome; authorized_at V1

event_outbox PK id; UQ event_id; payload; published_at; claim_token/lease_until; next_attempt_at V2 · V3

관계

출발 도착 구분·조건
mock_gateway_result.attempt_id payment_attempt.id 물리 FK · Mock 제공자 결과
refund_execution.payment_id payment_attempt.payment_id 물리 FK · 같은 Payment DB의 원결제
mock_refund_result.refund_request_id refund_execution.id 물리 FK · Mock 환불 결과
payment_attempt.order_id Core.orders.id 서비스 간 ID · FK 없음
refund_execution.core_refund_request_id Core.refund_request.id 서비스 간 ID · 유일키는 Payment 내부에서 보장

제약과 이관

retry_count는 0~3이며 lease_token과 lease_until의 NULL 여부가 같아야 한다. 식별자는 Core에서 전달받지만 서비스 간 FK는 없다. UNKNOWN 결과 조회와 실행 재시도 예산을 구분한다.
