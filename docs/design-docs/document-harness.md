# 문서 하네스 설계

상태: 구현 · 로컬 검증 완료
[제품 명세](../product-specs/document-harness.md) · [수용 기준](../requirements/document-harness.md) · [ADR](../adr/0001-document-harness.md)

## 작업 흐름

AGENTS에서 요청을 분류 → 필요한 가이드·모듈 지식·계약 읽기 → 코드로 진단 → 변경과 관련 문서 갱신 → 변경 선택기 기반 검사 → 워크로그에 결과 → 요구사항 확인 후 계획 완료 이동.

작은 문구 수정은 관련 규칙과 문서 검사·일일 기록으로 끝난다. 여러 서비스에 걸친 변경은 계획·계약·소유권 조사와 환경별 검증을 연결한다. 지속적인 책임 경계 변경은 ADR을 추가한다.

## 도구의 책임

- `check.sh` → `verify.py` → CI와 공유하는 변경 선택기. 결과는 호환성을 위해 `build/harness/`에 유지한다.
- `check-docs.sh` → `check_docs.py`: 로컬 링크·정적 앵커·요구사항 상태와 근거 참조 구조를 검사한다.
- API 생성기는 YAML과 공통 참조를 HTML에 표시한다. 설계 생성기는 MD의 테이블·관계·전이 표를 시각화한다. 재생성 결과와 저장된 HTML을 비교해 최신성을 확인한다.
- CI는 문서 링크와 API·설계 HTML 최신성을 항상 확인한다. 실행기·선택기·워크플로 변경은 관련 회귀·구문 검사로 확인한다.

완료 요구사항은 검증 방식·로컬 방법 링크·워크로그 근거와 확인한 수용 기준을 가져야 한다. 테스트라는 파일 이름만으로 증명을 인정하지 않는다. 상태 변화는 초안 → 진행 중 → 완료이며 막히거나 중단된 요구사항은 보류로 사유를 기록한다.

## HTML 검토 방법

파일 URL로 열고 외부 서버 없이 내용이 보이는지 확인한다. API 경로·요청·응답·인증·스키마 참조를 YAML과 대조한다. ERD는 키·관계·서비스 소유권, 상태도는 전이·조건·실패 경로를 같은 MD와 대조한다. 검색·접기·펼치기·원본 이동과 데스크톱/390px 화면을 확인한다.

자동 검사는 내용의 최신성·참조 구조를 다루고 의미의 정확성·운영 환경 동작을 보장하지 않는다. 실제 DB·Kafka·원격 CI는 수행한 경우에만 별도 근거로 기록한다.
