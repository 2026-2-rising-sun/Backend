## 장바구니 삭제는 별도 검토가 필요하다

**결제 성공 후 구매 대상으로 선택한 항목을 정리한다. 삭제 대상 연결과 동시 변경 처리 방식은 미결정이며 #340에서 검토한다.** 주문 생성 시 삭제하는 안은 채택하지 않는다.

예를 들어 A 2개·B 5개·C 8개에서 A/B만 선택하고 이후 편집하지 않았다면 성공 후 A/B를 정리하고 C는 남긴다. 결제 중 A 수량 변경, A 삭제 후 재추가, 성공 결과 재전송, 정리 실패·재시도의 처리는 아직 합의하지 않았다. 사용자가 직접 누르는 일반 삭제 API와 결제 결과에 따른 자동 정리를 구분한다.

현행은 Order의 `sourceCartItemId`·`sourceCartItemVersion`과 회원 ID를 이용해 일치하는 Cart 행만 삭제한다. Order의 정보량과 관리 부담을 줄이라는 사용자 의견을 보존한다. Cart 쪽 주문 ID 연결, 선택 행의 편집 제한, 별도 연결 테이블이나 새 버전 필드는 승인되지 않았다. 코디네이터의 1차 기술 결정에 따라 #340 보류 중에는 기존 Cart ID/version 기반 정리·환불 참조를 보존한다. 장기 대체 방식과 Order 목표 모델의 보존 위치는 별도 검토한다.

선택 환불은 주문에 남은 Cart ID를 사용한다. 참조를 제거하려면 환불 요청·조회·이전 주문의 호환성도 Order 담당과 검토해야 한다. #340을 분리했다는 이유로 현행 정리를 비활성화하거나 주문 필드를 먼저 제거하지 않는다.

## 확정한 동작과 모듈 책임

| 항목 | 확정 방향 | 근거 |
|---|---|---|
| 조회·조작 단위 | Product별로 묶어 표시하고 담긴 SKU별로 체크·수량 변경·삭제한다. 상품 전체 체크는 하위 SKU 선택이다. | Cart 권장안에 대한 사용자 답변: “1번은 너가 권장한댈로” |
| 재고 예약 | Cart 담기·조회는 예약하지 않는다. | “장바구니에 담아둔다고해서 재고가 예약되지는 않음” |
| 쿠폰 | 이번 설계 범위에서 보류한다. 기존 쿠폰 코드·계약 삭제를 뜻하지 않는다. | “일단 쿠폰은 신경쓰지 말고 진행할것” |
| 자동 정리 시점 | 결제 성공 후 선택 항목을 정리한다. | “장바구니는 결제 성공하면 정리해야함” |
| 상품·SKU | Product는 상품 표현 정보와 SKU 구성을, SKU는 옵션 조합별 판매 단위의 현재 가격·재고를 소유한다. | Product–SKU 및 SKU 통합 방향 인계 |
| 주문서 가격 | 주문서 화면 생성 시 Order를 만들고 당시 서버 현재 SKU 가격을 스냅샷으로 저장하여 표시·결제에 사용한다. | SKU 추가 확정 결정 인계 |
| 재고 원자성 | Order 상태 전이와 SKU의 available/reserved 변경을 동일 DB 트랜잭션에서 처리한다. 별도 예약 테이블을 만들지 않는다. | SKU 추가 확정 결정 인계 |
| 신규 판매 준비 | 신규 Product는 sale_enabled=false, 신규 SKU는 READY로 생성하고 판매자가 판매 시작을 선택한다. 기존 상품 상태는 유지한다. | 사용자 직접 확정 인계: “판매 준비 상태로 생성하고 판매자가 판매 시작을 선택” |

신규 생성만으로 구매 가능하다고 표시하지 않는다. Product 전체 판매 허용과 SKU 개별 상태를 함께 판단한다. READY로 수동 복귀하는 전이나 기존 행의 일괄 상태 변경은 추가하지 않는다. 재고 0에서 판매 시작을 요청한 경우의 표시/응답과 READY 항목의 Cart 담기 허용 여부는 이번 확정으로 확대하지 않는다.

Cart는 회원 소유 항목·수량과 선택 항목 조회를 맡는다. 상품 이름·이미지·설명·옵션 정보는 Product/SKU에서 얻고, 가격·재고의 원본을 Cart에 중복 저장하지 않는 방향을 권장한다. 거래 가능 여부의 최종 판단·가격 스냅샷·예약은 Order와 SKU 책임이다. Cart 조회 금액이 주문서의 저장된 금액을 덮어쓰지 않는다.

독립 Payment 서비스나 Catalog의 구조를 Cart에서 개편하지 않는다. 담당은 Order #331·Cart #332·Product #333·SKU #334이며 #340은 정리 정책의 검토 이슈다.

## 현행과 목표의 차이

| 영역 | 현행 코드 | 목표 또는 미결정 |
|---|---|---|
| 위치 | Cart 엔티티·서비스·저장소·컨트롤러가 `order` 패키지 안에 있다. | `cart` 패키지로 책임을 분리하는 구현안을 계획한다. 주문 상태 처리 파일은 Order 담당과 조정한다. |
| 항목 식별 | `memberId + productId` 유일성, `quantity`, `version` | 회원+SKU별 항목으로 전환한다. Product/Cart/SKU BIGINT·Long은 1차 기술 결정으로 고정했다. productId 중복 저장·마이그레이션 세부는 미결정이다. |
| 조회 응답 | `id/productId/quantity/version` 평면 목록 | 상품별로 묶은 SKU 항목과 현재가·표시 정보를 구성한다. 응답 필드·재고 공개 범위는 미합의다. |
| 추가·수량·삭제 | 중복 추가 409, 양수 수량, 소유 행 잠금. 결제 진행 여부에 따른 편집 제한은 없다. | SKU별로 적용한다. 중복 담기 누적·수량 상한·품절 항목 담기 정책을 임의 변경하지 않는다. |
| 주문서 | `/v1/cart/checkout`은 견적, `/v1/cart/orders`는 주문 생성 | 화면 생성 때 주문·스냅샷을 만든다는 합의에 맞춘다. 두 API의 유지·변경과 재진입 식별은 Order와 조율한다. |
| 성공 후 정리 | 주문의 Cart ID·버전과 일치할 때 삭제 | 시점은 유지한다. 새로운 연결·삭제 정책은 #340에서 결정한다. |

## 저장·조회·연계 초안

최소 저장 정보는 항목 ID, 회원 ID, SKU ID, 수량, 감사 시각이다. Product/Cart/SKU ID는 BIGINT·Java Long으로 유지하고 기존 Sales ID를 기본 SKU ID로 보존하는 이행을 우선한다. #340 보류 중 version과 정리·환불 참조도 보존한다. 키/FK·추가 연결 필드·이행 세부는 최종 DDL 확정 전 검토한다. 주문 UUID 방향을 다른 ID의 전면 교체로 확대하지 않는다.

조회는 회원의 Cart 항목을 읽고 필요한 SKU와 상품 정보를 일괄 조회하여 상품별로 묶는 방향을 권장한다. 항목별 개별 조회를 반복하지 않는다. SKU 담당은 `skuId/productId/현재가/available/reserved/개별 상태`를 제공하는 내부 포트를 제안했다. **이 필드를 외부 Cart 응답에 그대로 노출하는 계약은 아니다.** 정확한 타입·옵션 정보 제공자·미존재/판매 중지 항목의 표시와 구매 가능 판단은 연계 전에 맞춘다.

주문 전환 시 서버가 선택 항목의 소유권과 수량을 확인하고 Order 생성 흐름에 전달한다. 상품별 UI 묶음을 주문 단위나 품목 수로 임의 변환하지 않는다. Order의 동일 주문 재조회와 새 주문 생성을 구분하는 방식, 요청 재전송 키, 수량 변경 시 재작성 방식은 Order 담당과 결정한다. Cart에 별도 TTL·예약 상태를 추가하지 않는다.

### 통합 검토에 제시할 물리 스키마안

아래는 DDL 구현 전 검토 표다. ID 타입과 현행 정리·환불 참조 보존은 코디네이터의 1차 기술 결정으로 고정했고, 나머지 키·관계·이행 세부는 권장안이다. 사용자 업무 정책 합의와 기술 조정을 구분한다.

| 필드·제약 | 권장안 | 확정 전 조건 |
|---|---|---|
| `cart_item.id` | 현행 BIGINT IDENTITY PK·Java Long 유지 | 1차 기술 결정. 이번 범위에서 UUID 전환하지 않음 |
| `member_id` | 현행 VARCHAR(36) NOT NULL, 서버의 회원 UUID 사용 | Member 서비스 간 FK를 만들지 않음 |
| `sku_id` | BIGINT·Java Long, NOT NULL | 1차 기술 결정. 기존 Sales ID를 기본 SKU ID로 보존 우선, 충돌·매핑 불가 발견 시 재조정 |
| `quantity` | INTEGER NOT NULL, CHECK(quantity > 0) | 별도 구매 수량 상한을 이번 리팩토링에서 신설하지 않음 |
| `version` | 기존 BIGINT NOT NULL DEFAULT 0과 `@Version`을 #340 보류 중 유지 | 기존 정리·환불 참조 보존 원칙. 장기 제거/대체는 #340 결정 대상 |
| `created_at/updated_at` | 현행 TIMESTAMP WITH TIME ZONE 유지 | 기존 생성·수정 시각 보존 |
| 키·관계 | UNIQUE(member_id, sku_id), SKU에 논리 참조를 두는 안 | 물리 FK 유무는 통합 검토에서 정함. 무결성 확인·삭제 정책은 별도로 유지 |
| `product_id` | 이행 중 매핑용 유지, 최종적으로 SKU에서 얻어 중복 저장 제거 권장 | 구 API와 기존 행 이행 완료 전 제거하지 않음 |

Product 1:N SKU, SKU 1:N CartItem, 회원 1:N CartItem이며 회원당 같은 SKU는 한 행이다. 선택 여부·현재 가격·재고·주문 상태는 Cart의 저장 원본에 넣지 않는다. 새 주문 연결 필드나 연결 테이블은 #340 미결정이다.

### 트랜잭션·잠금·실패 처리안

- 추가는 회원+SKU 유일 제약으로 동시 중복을 막고 현행 중복 409 응답을 보존하는 안을 권장한다. 사전 조회만으로 유일성을 보장하지 않는다. 수량 변경·사용자 삭제는 회원 소유 행의 짧은 쓰기 트랜잭션과 잠금을 유지한다.
- Cart 조회는 잠금 없이 일괄 조회한다. 판매 중지·삭제·품절 항목을 자동 삭제하거나 수량을 재고에 맞춰 덮어쓰지 않고 표시 상태로 돌려주는 안을 권장한다. 오류 표현과 담기 허용 범위는 공통 조회 계약에서 확정한다.
- 주문서 생성은 같은 DB의 Order 트랜잭션 안에서 소유한 선택 행을 잠근 뒤 수량·버전을 다시 확인한다. Cart가 독립 커밋하거나 재고를 예약하지 않는다. 조회용 가격은 참고 값이고 Order가 SKU 원본을 다시 읽어 저장한다.
- 현행 생성·결제 결과는 회원 가드와 Cart를 재고보다 먼저 잠근다. 통합 권장 순서는 Order 측 회원/주문 보호 → Cart ID 정렬 잠금 → 필요한 Product 정렬 잠금 → SKU ID 정렬 잠금이다. Product/SKU 담당의 경로까지 포함해 역순 잠금이 없는지 조율해야 하며 아직 공통 확정 규칙은 아니다. Cart CRUD는 Cart 잠금 후 외부 호출·SKU 갱신을 하지 않는다.
- #340 보류 기간에는 결제 성공 결과를 처음 반영하는 Order 트랜잭션에 현재 ID·회원·버전 조건부 삭제를 참여시키는 안을 권장한다. 영향 행 0은 이미 삭제됐거나 변경된 행이므로 오류로 돌려 구매를 실패시키지 않는다. SQL 자체 오류는 상태·재고·정리를 함께 롤백하여 기존 결과 재처리 경로로 복구한다. 새 비동기 정리 큐는 추가하지 않는다.
- 확정 실패·취소·만료에는 성공 정리를 실행하지 않고, 결제 UNKNOWN을 실패로 간주하지 않는다. 결제 성공 뒤의 환불로 Cart를 자동 복원하는 새 정책도 추가하지 않는다. 바로 구매에는 Cart 정리 참조를 넘기지 않는다. Order 상태·재고 복구 정책은 해당 소유 모듈이 결정한다.

기존 참조 보존 원칙은 1차 기술 결정으로 고정했다. Order 목표 모델의 저장 위치·재진입 계약·공통 잠금 순서는 답변을 기다린다. 보존 원칙을 바꾸려면 #340의 관련 결정을 먼저 닫아야 한다.

## 정리 방식의 검토 대안

아래는 #340에서 비교할 대안이며 채택된 설계가 아니다.

| 대안 | 이점 | 비용·남는 문제 |
|---|---|---|
| 현행 ID·버전 비교 유지 | 결제 도중 변경하거나 새로 담은 행을 구분하는 기존 동작을 보존한다. | Order가 Cart ID·버전을 알아야 한다. 변경한 행은 결제 후에도 남는다. |
| Cart 쪽에 주문 연결 | Order의 Cart 전용 저장 정보를 줄일 수 있다. | 연결 수명·실패/만료 해제·복수 주문·편집 정책이 필요하다. 별도 필드만 옮겨 복잡도가 사라지는 것은 아니다. |
| SKU·수량으로 정리 | 주문 품목에 이미 있는 정보를 이용할 여지가 있다. | 같은 SKU를 다시 담거나 수량을 바꾼 행과 원래 선택을 구분하기 어렵다. 바로 구매와 재시도도 구분해야 한다. |

현재 정책을 유지할 수 있으면 모듈 분리 과정의 회귀 기준으로 삼는다. SKU 전환이나 Order 변경으로 유지가 불가능해지는 단계에서는 #340의 필요한 결정을 먼저 마친다. 이를 임의의 새 삭제 방식으로 우회하지 않는다.

## 이행·계약·산출물

기존 `productId`를 SKU로 바꾸려면 Product/SKU의 명시적 매핑이 필요하다. 여러 SKU 중 하나를 임의 선택하지 않는다. 기존 Sales ID 보존을 우선하되 충돌·매핑 불가는 근거와 함께 조정한다. 신규 판매 준비 기본값은 기존 Product/SKU 행에 일괄 적용하지 않는다. 구 API 병행 여부·Cart 데이터 이행 세부·Flyway 번호와 적용 순서는 미합의다. 적용된 마이그레이션은 덮어쓰지 않는다.

Cart 저장·CRUD·선택 잠금·조건부 성공 정리 포트는 Cart 담당, 공유 주문 서비스와 Core 환불 변경 조정 및 `contracts/api/commercecore-service.yaml` 최종 편집은 Order 담당이다. 각 담당은 변경 조각과 실제 의미를 제공한다. SKU 테이블·재고·sales-info 이벤트/다중 SKU Catalog 판매 사본의 최소 호환 변경은 #334, Product 제어/삭제 이벤트와 Catalog Product 사본의 최소 변경은 #333이 맡는다. 대표가·최저가·합산재고 정책과 신규 쿠폰 설계는 추가하지 않는다.

현행 ERD는 [CommerceCore erd.md](../../services/commercecore/erd.md)·[erd.html](../../services/commercecore/erd.html)에 이미 있다. 위 목표 스키마는 표 형태 초안이며 별도 Cart ERD.html은 아직 없다. 구현 때 Cart 변경분을 공통 ERD 원본에 반영하고 기존 생성기로 HTML을 갱신하는 안을 제안한다. 공유 ERD 편집 순서는 코디네이터가 조정한다. 현재 확정된 Cart에는 별도 업무 상태 전이가 없어 상태관리도.html은 만들지 않는다. #340에서 연결 수명이나 편집 제한 상태를 채택하면 다시 판단한다.

FigJam은 기존 여섯 개 Cart 노드를 보존하고 native spec `465:1282`에 기록했다. 구현 단계의 FigJam 편집은 사용자 추가 지시에 따라 코디네이터가 맡는다. Cart 담당은 코드/계약 변경 근거와 대상 node-id를 전달하며 같은 영역을 동시에 편집하지 않는다.

이후 코디네이터가 기존 Cart 노드의 표현을 SKU로 맞추고 [통합 흐름](https://www.figma.com/board/1lr73O8XYEhMGHAgWAEeOv/?node-id=482-1342)·[통합 근거](https://www.figma.com/board/1lr73O8XYEhMGHAgWAEeOv/?node-id=482-1345)를 추가했다. 해당 변경의 검증은 코디네이터 기록이며 Cart 구현 완료를 뜻하지 않는다.
