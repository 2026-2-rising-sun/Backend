# Order 상세설계

현재 PR343은 **CommerceCore 독립 범위**다. Payment 소유 코드·DB·API·이벤트·문서는 최신 dev 원본으로 되돌려 우리 추가분을 제외한다. 기존 금전 연동이 포함된 구현은 보존 ref `archive/order331-before-payment-scope-correction`의 `e08b8aea`에 남는다. 당시 실행 성공은 현재 축소 범위의 실행 성공이나 운영 검증이 아니다.

## 1. 사용자 확정과 이번 제공 범위

한 주문번호에 여러 SKU 구매 항목, 생성 당시 수량·가격·상품명·판매자·Cart 출처를 보존한다. 내부 OrderSheetService 생성은 Pending과 선점을 같은 Core 트랜잭션에 저장한다. Product 중지·삭제는 신규 주문만 차단하며 기존 선점 주문은 원래 기한 안 결제를 허용한다(2026-11-15 직접 확정).

최신 후속 요구는 PENDING 생성부터600초, PAYMENT_PROCESSING 실제 실행 진입부터별도600초다. 준비 데이터 생성이나 재전송으로 PROCESSING 기한을 시작/연장하지 않는다. PROCESSING 기한 초과를 PG 실패확정·즉시 재고해제로 간주하는 계약은 확정되지 않았다. #346의 새 상태/진입타이머·M2/M3 연동은 **미구현 후속**이다.

이번에는 내부 주문서 도메인의 PENDING600초·스냅샷·선점·로컬 취소/만료·재고 반환을 남긴다. 안전한 금전 어댑터가 없는 `/v1/order-sheets` 공개 API 추가 전체를 후속으로 분리했다. 다른 오류코드나503으로 기존 경로를 차단하는 정책을 새로 넣지 않는다.

## 2. 데이터와 물리 이행

논리 Order는 `payment_group`, 항목은 `orders`다. 기존 BIGINT PK·물리명·번호·금액·Cart ID/version·저장기한은 변경하지 않는다. V104의 독립 스냅샷·policy_version·refund_target_order.quantity·쿠폰 사용출처를 유지하고 신규 order_payment_closure 및 COMPENSATION 목적/참조 열은 이번 범위에서 제외했다. 새 모듈 간 FK는 추가하지 않는다.

내부 도메인만 policy1, 공개 legacy 생성은 기존 policy0과 기본 PT15M 설정이다. 과거 policy1/2 행을0으로 바꾸거나 기한을 줄이지 않는다. 기존 V104/Payment V4가 이미 적용된 보존 환경과 이번 축소 SQL의 새 검증 환경은 다르다. **이미 적용된 V104/진행 중 policy1/2 환경에 안전하게 배포 가능한 이행으로 주장하지 않는다.**

옵션 공급 계약은 보류라 selected_options_snapshot은null이다. 신규 구 API도 seller_id_snapshot을 생성 시 저장한다. 과거 NULL 주문의 새 환불 접수는 삭제 포함 불변 Product.seller_id만 조회하고 현재 상품명·가격으로 과거 스냅샷을 덮지 않는다. 상품행/소유자가 없으면 임의 추정하지 않으며 이미 완료된 NULL 환불행은 자동 재작성하지 않는다.

## 3. 생성·멱등성·잠금

내부 서비스 입력은 직접SKU 또는 Cart ID/version 중 하나다. Cart 선택100 제한과 직접SKU 무상한의 경로 차이를 유지한다. 공개 주문서 계약을 이번 PR에서 제공한다고 표시하지 않는다.

동일 회원·키·정규화 원문은 기존 스냅샷/기한을 재현하며 다른 입력은409다. 잠금 순서는 회원 가드 → Cart 출처 → Product ID순 공유 잠금 → SKU ID순 쓰기 잠금이다. 실패 시 주문/전체 선점은 함께 롤백한다. 내부 도메인의 기한은 DB 시각 기준600초다.

## 4. 공개 legacy 호환

기존 `/v1/orders`, `/v1/cart/checkout`, `/v1/cart/orders`, `/v1/payment-groups/**`와 환불 조회/접수는 기존 dev 계약을 유지하고 가격·재고만 SKU 원본으로 연결한다. 단일SKU 상품을 지원하며 복수SKU의 공개 주문은 후속이다.

공개 legacy의 기본15분·PAYMENT_CONFIRMING 중 예약 유지/만료 제외는 기존 동작이다. 이는 사용자10분 요구 철회나 새 승인된 정책이 아니라 **이번 PR에 미충족으로 남은 기존 경로**다. 이번에 새 policy2 생성과 결과불명600초 종료 확대는 제외했다. 내부 policy1은 legacy 조회·결제·환불 소유 조회에서 제외해 기존 공개 API로 금전 실행을 우회하지 않는다.

## 5. 로컬 만료·결제 후속

내부 도메인의 PENDING은 기한에 FAILED/EXPIRED 사유로 변경하고 SKU 예약을 한 번 반환한다. 로컬 만료는 외부 금전 성공/실패를 합성하지 않는다. 신규 결제 시작/결과/종료 통지·늦은승인 보상 어댑터는 제거 후속이며 PaymentApproved 또는 RefundRequested를 구현하지 않았다.

### 종료 뒤 성공 결과의 도달 조건

현재 축소 범위는 내부 policy1의 새 금융 실행 원문을 만들지 않는다. 기존 정책0 결과 처리만 기존 Payment 계약으로 소비한다. 이전 정책1/2의 진행 중 데이터 처리는 자동 변환/묵살하지 않으며 현재 PR의 배포 지원 범위가 아니다. 늦은 성공을 무보상 승인하는 신규 경로를 제공하지 않는다.

## 6. 수량 환불과 쿠폰 복원

사용자 U1은 단가 우선 `min(단가×이번수량, 항목실결제액−이전성공환불액)`이며4000×3/쿠폰2000은4000/4000/2000이다. OrderRefundAmounts의 독립 계산/경계 검사를 유지한다. U2는 주문당쿠폰한장·선택항목하나·누적전량성공 때 원 유효기간 복원이다. 이 규칙을 **실제 신규 수량환불 실행 완료**라고 쓰지 않는다. 공개 어댑터/Payment 계약은 M3 후속이다.

기존 legacy 환불은 기존 항목전체 계약과 Payment 호출을 유지하며 성공 재고 복구를 SKU에 연결한다. Payment 금전 성공과 Core 로컬 반영은 서비스별 트랜잭션이므로 Core 롤백을 금전 취소로 확대 해석하지 않는다.

## 7. Payment 담당 경계

Payment 소유 구현·DTO·V4·계약을 새로 확장하지 않는다. 최신 dev의 ADR0337은 채택된 팀원 목표이며 M1/M2/M3 구현 완료가 아니다. CommerceCore가 필요한 계약/타이머/중복·UNKNOWN·보상 요구는 [인계 문서](../../../exec-plans/active/331-order-audit-fixes/payment-handoff.md)에만 남긴다.

## 8. 검증 상태

보존된 기존 구현의 a68 전체1362 통과, 504의 CI740(외부Kafka2스킵), 최종 감사1376중1실패는 각 당시 증거다. 독립 seller/Cart 계약 보완0146dc83의 실제PG/PaymentHTTP8건 통과도 범위 정정 전 증거다. 현재 축소 소스의 새 검증은 보완 계획·2026-11-15 워크로그에서 구분한다. 실패·스킵·NO-SOURCE를 성공으로 합산하지 않는다.

## 9. 직접 합의와 구분하는 구현 선택

회원당 활성1건과 Payment 결과확정부터168h 미만 환불은 기존dev 제약이며 이번에 새로 직접 승인받은 정책으로 표시하지 않는다. Cart 담기 판매조건·0재고 판매시작·상품 전체중지 공개노출은 미답변이다. #340/#345/#346·공개 다중SKU/대표가/가격순·옵션은 후속/보류다. 실제 결제제공자·운영·배포·전체 정책 수용을 검증 완료로 표시하지 않는다.
