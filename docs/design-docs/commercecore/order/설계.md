## 1. 범위와 확정 정책

| 구분 | 내용 |
|---|---|
| 담당 | Order #331, Cart #332, Product #333, SKU #334. 별도 Price/Inventory/Payment 담당 PR은 없다. |
| Order | 주문과 주문항목, 주문서 금액 스냅샷, 생성·조회·기한·취소, 결제 결과의 업무 적용, 환불 대상/수량·금액 및 성공 결과 적용 |
| Product | 이름·이미지·설명과 Product–SKU 구성. Product 전체 판매허용 스위치·소프트 삭제를 소유. SKU 개별 판매 상태와 구분 |
| SKU | 현재 SKU 가격·available/reserved, 선점·확정·해제·복구. Order는 SKU 테이블을 직접 갱신하지 않고 같은 트랜잭션의 모듈 호출로 협력 |
| Payment 연계 | 실행 요청의 영속 전달·조회·결과 정규화. 독립 Payment 서비스/PG 구현을 이번 Order 작업으로 확대하지 않음 |
| 제외 | 배송/Fulfillment 실연동, 반품 검수, 정산, 상품 버전 이력, 별도 재고 예약 테이블, 결제 서비스의 UNKNOWN 정책 설계 |

확정한 정책은 다음과 같다.

1. 주문번호 하나에 여러 구매 항목을 매핑한다. 거래·가격·재고의 기준은 SKU다.
2. **주문서 화면 생성에 필요한 서버 요청에서 Pending 주문 생성 + 재고 선점 + 당시 상품·가격 스냅샷을 함께 수행한다.** 결제 버튼을 누를 때까지 주문 생성을 미루지 않는다.
3. 기존 주문은 저장한 가격을 따른다. 이후 SKU 가격 변경으로 재가격 산정하지 않는다.
4. Pending은 10분 후 실패 처리하고 예약을 해제한다. 늦은 결제 성공으로 주문을 되살리지 않으며 Payment에 실패한 주문임을 알린다.
5. 결제 완료 주문은 환불 성공 이벤트/응답을 확인했을 때 해당 취소를 확정하고 재고를 복구한다. 부분 환불을 지원한다.
6. 부분 환불은 쿠폰 사용 완료 상태를 유지한다. 주문 전체 환불 성공 시 쿠폰을 복원한다.
7. 쿠폰은 주문서 안에서 선택·변경한다. 상품/SKU 기준 적용 방향을 유지한다.
8. 별도 재고 예약 테이블 없이 Order의 적용 여부 판정과 SKU available/reserved 변경을 같은 DB 트랜잭션으로 처리한다.

Product 원본 명세를 다시 확인한 추가 합의도 반영한다. 옵션 없는 상품은 기본 SKU를 가지며, Product 전체 중지/재개는 SKU 개별 상태를 덮어쓰지 않는다. 옵션은 비정형 JSON·Catalog 관리 방향으로 정해졌고 저장 위치/입력·검증·거래 스냅샷 공급 경로는 후속 설계다. Order는 고정 옵션 테이블을 추가하지 않고, 공급 계약이 정해진 당시 표시 데이터를 복사한다. Product–SKU는 DB FK 없이 논리 참조하며 기존 Order FK 이행은 별도 조정한다.

2026-11-13 후속 사용자 확정: 신규 Product는 `sale_enabled=false`, 신규 SKU는 `READY`로 판매 준비 후 판매자가 시작한다. 등록만으로 주문 가능한 상태가 되지 않으며 기존 데이터의 상태는 보존한다. READY로 수동 복귀하는 정책까지 추가하지 않는다. 주문 생성은 Product 전체 허용과 SKU 판매 가능 조건을 모두 확인하되, 이미 생성된 주문의 해제/환불 복구를 현재 판매 상태로 막지 않는 설계안을 유지한다.

같은 날 코디네이터의 1차 기술 조정으로 Product·Cart 항목·SKU ID는 BIGINT/Java Long을 사용하고, 기존 Sales ID를 기본 SKU ID에 보존하는 이행을 우선한다. 충돌/매핑 불가 발견 시 재조정하며 Order ID/주문번호 전환으로 확대하지 않는다. 공유 `commercecore-service.yaml` 최종 편집자는 Order이고 각 담당이 자기 API/DTO 변경 조각을 제공한다. 이는 업무 정책 승인이나 구현 착수 메시지가 아니다.

## 2. 전체 흐름

1. 사용자가 구매할 SKU/수량을 선택하고 주문서에 진입한다.
2. 서버가 소유권·판매 가능 여부·현재 SKU 가격·재고를 확인하고 주문/항목 저장과 재고 선점을 원자적으로 커밋한다.
3. 응답의 주문번호·스냅샷·만료 시각으로 주문서를 표시한다. 화면의 시계나 이전 Catalog 가격은 주문 판단의 원본이 아니다.
4. 사용자가 주문서에서 쿠폰을 고른다. 설계안은 화면에서 예상 금액을 미리 계산하고 결제 버튼 시 서버가 최종 검증·저장하는 방식이다.
5. 서버가 기한·쿠폰·최종 금액을 검증하고 결제에 보낼 금액/요청을 고정한다. DB 커밋 후 Payment 연계가 요청을 전달한다.
6. 결제 성공을 기한 안에 반영하면 PAID와 SKU 예약 확정이 함께 커밋된다. 확정 실패·취소·만료는 예약 해제와 함께 종결된다.
7. 결제 후 환불은 주문항목과 수량으로 접수한다. 성공 확정 때만 환불 실적과 SKU 복구를 같이 커밋한다.

## 3. 논리 데이터 모델

`Order 1 — 1..N OrderItem`, `Order 1 — 0..N RefundRequest`, `RefundRequest 1 — 1..N RefundItem`, `OrderItem 1 — 0..N RefundItem`이다. OrderItem은 SKU를 식별하지만 주문 내역을 현재 Product/SKU에 조인해 재구성하지 않는다.

기존 `payment_group`의 구매 묶음 역할과 기존 `orders`의 항목 역할을 각각 Order와 OrderItem으로 표현한다. 기존 PK·물리명 보존 확장안이 채택됐으며 Core V104가 Order에 배정됐다. 새 주문번호는 UUID 문자열이고 내부 항목 ID/과거 주문번호는 보존한다. 신규 `/v1/order-sheets`의 policy_version=1과 기존 API/활성 주문의 policy_version=0을 구분한다.

### Order — 주문 단위의 상태와 결제 기준

| 필드 묶음 | 설계안과 제약 |
|---|---|
| `id`, `orderNumber`, `memberId` | 내부 PK, 외부에 표시하는 고유 주문번호, 인증된 구매자. memberId는 요청 본문을 신뢰하지 않음 |
| `status`, `failureReason` | 주문 상태와 실패 사유 분리. 만료는 FAILED + EXPIRED로 표현하는 안 |
| `createdAt`, `expiresAt` | 서버 생성 시각과 `createdAt + 10분`. 재조회·재시도·쿠폰 변경으로 연장하지 않는 안 |
| `creationKey`, `requestFingerprint` | `(memberId, creationKey)` 고유 제약. SKU/수량/구매자/장바구니 출처를 정규화한 생성 요청 비교값 |
| `currency`, `totalAmount`, `discountAmount`, `payableAmount` | KRW 원 단위 정수. 항목 합계와 일치하며 `payable = total - discount >= 0` |
| `checkoutRevision`, `version` | 사용자가 확인한 주문서 버전과 동시 갱신 제어. 금액 고정 이후 쿠폰 변경 거절 |
| `paymentRequestId`, `paymentStartedAt` | 결제 요청 상관관계·금액 고정 여부. Payment의 내부 상태를 Order enum으로 복제하지 않음 |
| `paidAt`, `closedAt` | 결과 반영/종결 시각. PG 승인 시각과 구별 |
| 쿠폰 식별·적용 항목·복원 적용 표식 | 기존 쿠폰 사용/예약 기록과 연결. 복원은 해당 주문의 사용 건에 한정하고 중복 결과를 차단 |

### OrderItem — SKU별 구매 이력

| 필드 묶음 | 설계안과 제약 |
|---|---|
| `id`, `orderId`, `skuId`, `productId` | 환불은 `orderItemId`로 식별. SKU가 여러 주문에 반복 등장해도 해당 구매 건을 구분 |
| `productName`, `skuCode`, `selectedOptions`, `sellerId`, 선택적 대표 이미지 | 생성 시 복사한 표시/추적 정보. 옵션은 당시 이름과 값까지 보관. Product/SKU에서 공급할 정확한 필드 계약은 조정 필요 |
| `quantity`, `unitPrice`, `totalAmount` | 수량·단가는 생성 후 불변. `total = unitPrice × quantity` |
| `discountAmount`, `payableAmount`, 쿠폰 적용 스냅샷 | 결제 요청 직전 확정하고 이후 불변. 원가 스냅샷과 쿠폰 선택 변경을 구분 |
| `sourceCartItemId`, `sourceCartVersion` | 원래 장바구니 항목의 조건부 정리를 위한 선택적 정보. 환불의 식별자로 사용하지 않음 |

설계안은 주문 안의 동일 SKU 중복 행을 거절하고 한 항목의 quantity로 표현한다. Cart가 같은 SKU를 여러 출처로 전달해야 한다면 합치기 전에 출처 보존 계약부터 조정한다. 주문서에서 SKU/수량 변경은 현재 범위에 자동 추가하지 않으며, 변경 시 명시적으로 기존 주문 취소 후 새 주문을 만드는 안이다.

### RefundRequest / RefundItem — 환불 업무 기록

기존 `refund_request`와 `refund_target_order`를 확장·이행하는 것을 우선 검토한다. 동일 목적의 신규 환불 저장소를 병렬로 추가하지 않는다. **환불 기록은 재고 예약 테이블이 아니다.**

| 엔티티 | 필드와 제약 |
|---|---|
| RefundRequest | `id`, `orderId`, `memberId`, `idempotencyKey`, `fingerprint`, `amount`, `status`, `requestedAt`, `resolvedAt`, `paymentRefundRequestId`. `(memberId, idempotencyKey)` 고유. 요청 대상/금액은 접수 후 불변 |
| RefundItem | `refundRequestId`, `orderItemId`, `quantity`, `refundAmount`. 동일 요청 내 항목 고유. 성공 환불 수량의 합은 구매 수량 이하 |
| 상태 분리 | Order는 PAID/PARTIALLY_REFUNDED를 유지하면서 환불 건이 처리될 수 있다. 환불 실행 결과 미확정은 그 건을 처리 중으로 유지하고 성공한 것처럼 재고를 복구하지 않음 |

환불 성공 수량/금액은 성공한 RefundItem 합계를 원본으로 삼는 안이다. 주문항목에 누적 카운터를 중복 저장하는 최적화는 실제 조회 비용이 확인되기 전 추가하지 않는다.

### 제약과 조회 경로 — 물리 DDL 전 검토안

- Order의 주문번호와 회원+생성 키, RefundRequest의 회원+환불 키, RefundItem의 요청+항목에는 고유 제약이 필요하다. 주문/환불의 요청 비교값은 항목 정렬과 수량을 포함한 정규화 형식을 버전과 함께 관리한다.
- 항목 quantity는 양수, 금액은 0 이상, 할인액은 원가 이하를 검증한다. 항목/주문 합계 및 누적 환불 한도처럼 여러 행에 걸친 불변조건은 Order 잠금 아래 검증한다. DB의 단일 행 CHECK만으로 보장한다고 설명하지 않는다.
- 만료 작업 조회에는 PENDING의 expiresAt/id, 구매 내역에는 memberId/createdAt/id, 주문항목에는 orderId, 환불 이력에는 orderId/requestedAt/id, 환불 성공 수량 집계에는 orderItemId 연결 인덱스를 검토한다. 기존 인덱스와 중복 생성하지 않는다.
- 주문당 미확정 환불 한 건 안을 채택하면 Order 잠금과 함께 활성 요청의 유일성을 DB에서도 보호한다. 현재 PROCESSING/UNKNOWN 저장 상태를 새 업무 표현으로 이행하기 전에는 두 상태 모두 활성으로 취급한다.
- 만료 작업은 작은 묶음으로 처리하고 각 주문의 상태·기한을 잠금 후 재확인한다. 중복 작업자는 같은 주문을 두 번 해제할 수 없다. SKU 실패 때문에 해당 주문의 상태만 먼저 종결하지 않는다.

## 4. 주문서 재진입과 멱등성 — 설계안

- 신규 주문서 생성에 클라이언트가 만든 생성 키를 필수로 받는다. 한 주문서 의도에 대해 응답 유실·새로고침에도 같은 키를 재사용한다. 키 길이는 현행 호환성을 고려해 최대 64자로 시작하는 안이다.
- 같은 회원+키+같은 내용이면 기존 주문과 저장한 스냅샷/만료 시각을 반환한다. 키가 같고 내용이 다르면 충돌로 거절한다. 이미 만료된 주문도 재선점하지 않고 종결된 기존 주문을 반환한다.
- 주문번호를 알고 있으면 소유권 검증 후 조회한다. `GET`은 새 주문을 만들거나 재고를 선점하지 않는다. 브라우저가 키를 잃은 경우의 복원은 인증된 사용자의 활성 주문 조회로 해결하는 안이다.
- 현재 회원당 활성 구매 하나 제한은 별도 정책 변경 없이 보존하는 안이다. 다른 생성 키로 접근했다고 기존 주문을 자동 취소하거나 TTL을 늘리지 않는다.
- 생성 DB 고유 제약이 다중 인스턴스의 최종 방어선이다. 충돌한 요청의 선점은 트랜잭션 전체 롤백 후 승자 주문을 다시 조회한다. JVM 락만으로 보장하지 않는다.
- 결제/환불 키는 생성 키와 별도 의미다. 같은 키의 재시도는 동일 결과를 반환한다. 종결 실패한 다른 업무를 시도하려면 새 키를 사용한다.
- 키 수명과 주문 보존 기간은 함께 정해야 한다. 종결 주문이 남아 있는 동안 키를 조기 재사용하지 않는다. 개인정보 보존·파기 기간은 이 설계에서 새로 정하지 않는다.

## 5. 상태와 재고 전이

상태 이름은 설계안이며 기존 응답 enum을 즉시 바꾼다는 뜻은 아니다. 별도 `PAYMENT_CONFIRMING`/`UNKNOWN` 주문 상태를 두지 않고, 아직 주문 성공이 확정되지 않았다면 PENDING과 원래 기한을 유지하는 안이다.

| 현재 → 다음 | 사건·조건 | 같은 트랜잭션의 SKU 변경 |
|---|---|---|
| 없음 → PENDING | 주문서 생성 검증 성공 | 각 SKU `available -= q`, `reserved += q` |
| PENDING → PAID | 잠금 후 판정 시각이 expiresAt 미만이며, 해당 결제 요청의 금액/통화/식별자가 일치하는 확정 성공 | `reserved -= q` |
| PENDING → FAILED(EXPIRED) | 서버 판정 시각이 expiresAt 이상 | `available += q`, `reserved -= q` |
| PENDING → FAILED(PAYMENT_FAILED) | 해당 결제의 확정 실패 | `available += q`, `reserved -= q` |
| PENDING → CANCELLED | 결제 전달 요청이 아직 저장되지 않은 주문의 사용자 취소를 수락하는 안 | `available += q`, `reserved -= q` |
| PAID/PARTIALLY_REFUNDED → PARTIALLY_REFUNDED | 일부 항목/수량 환불 성공을 최초 반영 | 해당 성공 수량만 `available += q`; reserved는 변경 없음 |
| PAID/PARTIALLY_REFUNDED → REFUNDED | 전 구매 수량 환불 성공 | 마지막 성공 수량만 `available += q`; 쿠폰 복원 정책 적용 |
| FAILED/CANCELLED → 동일 상태 | 늦은 결제 성공 | 재고 변경 없음. 실패/취소 통지와 보상 처리 경로로 전달 |

불변조건:

- SKU available/reserved는 음수가 되지 않는다. 여러 항목 중 하나라도 선점할 수 없으면 주문·모든 선점을 롤백한다.
- 주문당 선점, 예약 확정, 예약 해제는 각각 유효한 상태 전이에서만 적용한다. PAID가 된 뒤 원래 만료 작업이 도착해도 해제하지 않는다.
- 결제 성공과 만료가 경합하면 동일 Order 행 잠금 아래 기한/상태를 판정한다. 잠금 대기 전에 읽은 시각을 사용하지 않는다.
- 성공 적용 판정은 Order가 잠금 후 확인한 서버 시각을 기준으로 하는 안이다. PG가 기한 전에 승인했어도 뒤늦게 도착한 성공을 되살리기 근거로 삼지 않는다. 이 경계 시각 선택은 구현 전 Payment 호출자와 확인한다.
- 10분은 업무 기한이다. 만료 작업 주기가 늦으면 실제 재고 해제 실행은 지연될 수 있다. 조회·결제 시작·결과 반영도 기한을 검사하므로 작업자 지연이 주문 생존 연장이 되지 않게 한다.
- Order 성공/실패 판정과 결제 실행의 불확실성을 분리한다. 네트워크 타임아웃 자체를 결제 실패 확정으로 해석하지 않는다.
- 사용자 취소는 결제 전달 요청 저장 전까지만 즉시 허용한다(후속 U3 사용자 확정). 결제 요청 저장 이후에는 결과 조회/원래 기한의 만료를 따르고, PAID가 되면 환불 성공으로 취소를 확정한다. Pending이라는 상태 이름만 보고 결제 진행 중 즉시 사용자 취소를 허용하지 않는다. 만료 정책과 진행 중 취소 정책은 구분해 검토한다.

## 6. 트랜잭션과 잠금

같은 CommerceCore DB에서 Order 애플리케이션 서비스가 트랜잭션을 연다. SKU의 조건부 갱신은 그 트랜잭션에 참여하고 내부에서 별도 커밋하지 않는다. Product·SKU가 다른 DB 서비스라는 가정을 추가하지 않는다.

잠금 순서 **협의안**은 현행 회원 구매 가드가 필요한 경로의 회원 행 → Order → 해당 환불/전달 기록 → Cart 출처 → 쿠폰 → Product id 오름차순 공유 잠금 → SKU id 오름차순이다. Product 담당의 “모든 Product를 먼저 확인한 뒤 모든 SKU 처리” 안과 맞춘다. 실제 Cart/Coupon/SKU 구현의 기존 순서와 비교해 하나로 확정해야 한다. 옵션 스냅샷의 일관성/제공 경로는 별도로 조정한다. 이 순서를 현재 공통 합의로 선언하지 않는다.

### 생성 트랜잭션

1. 인증 사용자와 요청을 검증한다. 동일 생성 키가 있으면 요청 비교 후 기존 결과로 끝낸다.
2. Cart 경로라면 해당 회원의 선택 항목/버전을 확인한다. Product 미삭제·전체 판매허용과 SKU 개별 판매 가능성을 함께 검증한다. 기존 주문의 성공 확정·해제·환불 복구에는 신규 판매 허용을 다시 요구하지 않는 안이다.
3. SKU들을 안정된 순서로 잠그거나 동등한 조건부 갱신 절차를 사용해 **가격을 읽은 상태와 선점 상태의 일관성**을 확보한다. SQL·행 잠금 구현은 SKU 담당이 소유한다.
4. 서버 기준 시각을 한 번 정하고 가격/표시 스냅샷과 주문을 저장한다. 각 SKU의 `available >= q` 조건으로 선점한다.
5. 하나라도 실패하면 전체 롤백한다. 커밋된 주문을 응답하며 Cart를 이 시점에 삭제하지 않는 현행 동작을 유지하는 안이다.

### 결제 시작·성공·만료 트랜잭션

- 시작: Order 잠금 → 기한/소유권/기존 요청 검사 → 쿠폰 검증과 최종 금액 저장 → 영속 결제 전달 요청 저장 → 커밋 → 외부 호출. HTTP/PG 호출을 DB 잠금 안에서 기다리지 않는다.
- 성공: Order 잠금 → 실행 식별자·금액·통화 대조 → 기한과 적용 이력 검사 → PAID + SKU 예약 확정 + 쿠폰 사용 확정. Cart 삭제가 동반되면 저장한 원본 itemId/version이 같은 것만 대상으로 하는 안이며 Cart 담당과 계약을 맞춘다.
- 만료/취소/확정 실패: Order 잠금 → 아직 PENDING인지 검사 → 종결 + SKU 예약 해제 + 해당 주문의 쿠폰 예약 해제 + 필요한 영속 Payment 통지 의도 저장 → 커밋.
- 결과 적용 도중 SKU 갱신 실패/프로세스 종료가 발생하면 결과 적용 표식까지 롤백된다. 같은 결과 재처리로 회복하며 일부 수량만 커밋하지 않는다.

## 7. 쿠폰과 금액

SKU의 **기본 가격 스냅샷은 주문서 생성 때**, 쿠폰에 따른 **할인·실결제 금액은 결제 요청 전** 고정한다. 따라서 “주문 생성 시 쿠폰 데이터 null”과 “이후 상품 가격 변경에도 주문 가격 유지”를 함께 만족시킬 수 있다.

### 요청 수를 줄이는 주문서 설계안

1. 주문서 응답과 쿠폰 후보 조회로 계산에 필요한 데이터를 제공한다. 쿠폰 선택 클릭마다 주문 변경 요청을 강제하지 않는다.
2. 화면은 스냅샷 가격을 바탕으로 예상 금액을 보여 준다. 서버가 승인한 최종 금액이라고 표시하지 않는다.
3. 결제 클릭 시 선택 쿠폰/적용 항목, 주문서 버전, 사용자가 확인한 결제 금액을 한 요청에 보낸다.
4. 서버가 쿠폰 소유·기간·중복 사용·대상/최소 금액을 검사한다. 최종 금액이 확인 금액과 다르면 Payment에 보내지 않고 수정된 주문서를 확인하게 한다. 현재 SKU 가격으로 다시 계산하지 않는다.
5. 결제 전달 요청이 저장되면 쿠폰/금액을 고정한다. 요청 재시도는 기존 요청을 재사용하며 다른 금액으로 덮어쓰지 않는다.

현행 주문당 쿠폰 한 장 제한을 유지하고 대상 OrderItem 하나에 적용하는 안을 우선 제시한다. Product 쿠폰의 **적용 가능 대상**과 실제 할인받는 **구매 항목**은 구분한다. Product 아래 여러 SKU를 함께 할인할지·쿠폰 중복 적용을 허용할지는 아직 미결정이며 자동 확대하지 않는다.

금액은 KRW 1원 정수로 저장하고 곱셈/합산의 오버플로를 검사한다. SKU 판매가는 양수이고 할인 후 금액은 0 이상이다. 음수 금액이나 할인액이 항목 원가를 넘는 결과는 거절한다. 현행 PaymentCommand/RefundCommand와 Payment API는 amount=0을 허용하므로 전액 할인에 별도 결제 우회 흐름을 새로 만들지 않는 안이다. 0원도 수량/상태/쿠폰 검증에서 제외하지 않으며 실제 외부 PG의 수용 여부는 별도 연동 검증 대상이다.

## 8. 부분 환불과 쿠폰 복원

### 접수·중복 처리 설계안

- 요청 대상은 `orderItemId + quantity`다. Product ID나 현재 Cart ID만으로 환불 대상을 정하지 않는다. 구매자 소유권과 해당 주문의 항목인지 검증한다.
- Order 행을 잠근 뒤 성공한 환불 수량과 진행 중 요청을 검사한다. `이번 수량 <= 구매 수량 - 성공 환불 수량`이어야 한다.
- 처음에는 **주문당 미확정 환불 한 건**으로 직렬화하는 안을 권장한다. 서로 다른 SKU의 동시 환불도 앞선 건이 확정될 때까지 거절하고 기존 건 조회를 안내한다. 부분 환불의 배분/결과 순서가 단순해지는 대신 병렬 접수는 제한된다.
- RefundRequest/RefundItem과 영속 Payment 환불 전달 요청을 함께 저장한다. 결제 완료 주문은 환불 접수만으로 취소 확정·재고 복구·쿠폰 복원을 하지 않는다.
- 성공 결과 최초 적용 시 RefundRequest 상태, 항목별 성공 수량/금액, Order의 환불 범위, SKU 복구, 필요한 쿠폰 복원을 한 트랜잭션으로 반영한다. 동일 결과 재전달은 저장된 식별자/금액과 대조 후 무변경 반환한다.
- 환불 결과가 미확정이면 진행 중 수량을 다시 환불할 수 있게 풀지 않는다. 확정 실패 시 재고와 성공 수량은 바꾸지 않는다. 실패 이후 재접수는 새 키로 하며, 상충하는 성공/실패 결과는 자동 재적용하지 않고 재조사 대상으로 남긴다.

### 환불액 계산 — U1 사용자 확정

할인 전 주문 스냅샷 단가 × 이번 수량을 우선 환불하되, **그 구매 항목의 남은 환불 가능 실결제액**을 넘지 않는다. 이전 수량 비례배분 제안은 폐기됐다.

`이번 환불액 = min(주문 스냅샷 단가 × 이번 수량, 항목 실결제액 - 이전 성공 환불액)`

- 4,000원 × 3개, 쿠폰 2,000원, 실결제 10,000원: 한 개씩 4,000 → 4,000 → 2,000원이다. 두 개 먼저 환불하면 8,000원, 마지막 2,000원이다.
- 성공한 수량/금액만 누적한다. 실패 뒤 새 키로 재접수하면 미사용 수량/금액으로 다시 계산한다. 같은 키의 동일 요청은 기존 건을 반환한다.
- Order 잠금 아래 주문당 미확정 환불 한 건을 접수한다. PROCESSING/UNKNOWN 동안 다른 건을 거절해 수량/금액을 중복 예약하지 않는다. 확정 실패 이후 새 요청은 가능하다.
- 큰 할인으로 실결제액을 먼저 전부 환불한 뒤 수량이 남을 수 있다. 나머지 수량은 0원 성공 처리하며 실제 PG 환불 호출을 만들지 않는다. 성공한 수량의 재고와 전량 판정은 금액과 별도로 반영한다.
- 주문 전체 구매 수량이 성공 환불됐을 때만 쿠폰을 한 번 복원한다. 여러 항목 중 쿠폰 항목만 전량 환불한 경우에는 복원하지 않는다. 원래 유효기간을 유지하며 최소 구매 금액 재심사를 새로 추가하지 않는다.

[공식 정책 조사 기록](../../../exec-plans/active/331-order-module/refund-policy-research.md)은 사용자 결정과 외부 관행을 구분한다. 세 서비스가 같은 순차 알고리즘을 사용한다는 근거는 확인되지 않았으며 이 조사로 사용자 정책을 바꾸지 않는다.

| 일부 환불 성공 | 쿠폰 사용 완료 유지 — 사용자 확정 |
| 주문 전체 환불 성공 | 사용 쿠폰 복원 — 사용자 확정 |
| 여러 부분 환불의 누적이 전 구매 수량에 도달 | 마지막 성공 때 전체 환불로 보고 해당 주문의 쿠폰 복원 — U2 사용자 확정. 단가 우선/실결제액 상한의 U1 적용 |
| 복원하려는 쿠폰의 유효기간 경과 | 원래 기간 유지, 연장/재발급 없음 — U2 사용자 확정. 복원돼도 기간이 지났으면 사용할 수 없음 |
| 중복 전체 환불 성공 | 동일 주문 사용 건에 대한 복원 1회. 이후 다른 주문에서 사용한 쿠폰을 과거 결과로 다시 풀지 않음 |
| 만료 주문의 늦은 결제 보상 환불 | 주문 실패를 유지하며 재고 재복구 없음. 이미 해제된 쿠폰 예약도 새 사용 건을 건드리지 않음 |

전량 판정은 금액만이 아니라 모든 항목의 성공 환불 수량을 기준으로 하는 안이다. 0원 항목도 전량 여부에서 빠뜨리지 않는다. 기존 환불 가능 기간 정책은 별도 요청 없이 바꾸지 않는다.

## 9. 실패 통지와 복구

만료로 Order가 종결된 사실과 Payment에 전달할 의도를 한 커밋에 남긴다. 인메모리 이벤트나 커밋 후 HTTP 한 번만으로 끝내면 서버 종료 시 통지가 유실되므로 재시도 가능한 영속 전달이 필요하다.

현행 `payment_delivery_request`와 `event_outbox`가 있으므로 기존 전달·작업자 기반을 우선 검토한다. 현재 delivery의 kind는 PAYMENT/REFUND뿐이다. 이 설계만으로 새로운 종료 통지 종류가 이미 지원된다고 가정하지 않는다. 별도 범용 Outbox 프레임워크 구축을 추가하지 않는다.

Order의 만료 실패를 Payment 실행 실패로 복사하지 않는다. 만료 후 실제 결제 성공이 확인되면 결제 실행 기록에는 성공 사실을 보존하고, Order는 실패를 유지하며 그 결제에 대한 보상 의도를 영속화한다. 만료됐다는 이유만으로 성공 결과를 중복 결과로 버리면 금전 복구가 누락된다. 이 경로에서는 정상 주문 성공의 재고 확정·쿠폰 사용·Cart 삭제를 적용하지 않는다. 보상 요청은 동일 payment/request 식별자를 기준으로 중복 생성·전달을 차단하는 안이다.

| 실패 상황 | 복구 방향 |
|---|---|
| 주문 생성 커밋 후 응답 유실 | 같은 생성 키로 저장된 주문 반환. 재선점 없음 |
| 결제 전달 전에 프로세스 종료 | 커밋된 동일 전달 요청을 작업자가 재시도. 주문이 만료됐다면 실행/중단 경합을 Payment와 조정 |
| Payment가 응답하지 않음 | 실행은 미확정으로 추적. Order 기한은 유지하고 만료 시 종결·해제 |
| 성공과 만료 동시 처리 | Order 잠금 아래 기한을 검사. 만료가 적용된 뒤 성공은 보상 경로로 보내며 PAID 전이 없음 |
| 만료 작업 지연 | 기한 기반 조회/명령 검증으로 뒤늦은 주문 성공 방지. 작업자가 기한 지난 PENDING을 재처리 |
| 만료 알림이 결제 생성보다 먼저 도착 | Payment 측에 주문 종료 사실을 유지하거나 동일 요청의 후속 성공을 다시 보상하는 계약 필요. 이 순서 역전 처리를 구현 선행 조건으로 둠 |
| Payment 통지 실패 | 동일 종료 원인/주문/요청 식별자로 재시도. 재시도 자체는 재고를 다시 변경하지 않음 |
| 보상 환불 실패/미확정 | Order FAILED/CANCELLED 유지, 금전 복구 작업만 재시도·조회. 재고를 다시 선점하거나 복구하지 않음 |
| 환불 적용 도중 DB 오류 | 환불 적용 표식·SKU 복구·쿠폰 복원 전체 롤백. 같은 결과 재처리 |

Payment 측의 종료 통지 수신·늦은 성공 보상·미확정 조회 계약은 아직 미합의다. 특히 현행 사용자 환불 API는 PAID 주문만 허용하므로 만료 주문 보상을 그대로 통과시킬 수 없다. 사용자 환불과 실패 주문의 보상 처리를 구분해야 한다.

## 10. 모듈 협력과 API 영향 — 계약 초안

아래는 필요한 의미를 설명하는 명령 목록이다. 실제 공개 URL·DTO·이벤트명·버전은 호출자/공유 YAML 책임을 맞춘 뒤 확정한다. **기존 계약 파일은 변경하지 않는다.**

| 명령/조회 | 필요한 입력과 동작 |
|---|---|
| 주문서 생성 | 인증 회원, 생성 키, SKU/수량 목록, 구매자 정보, 선택적 Cart 출처/버전. 현재 서버 상품/가격으로 생성 |
| 주문 조회/활성 주문 조회 | 주문번호·인증 회원. 저장 스냅샷·상태·expiresAt·결제 시작 여부 반환. 상태 조회로 생성하지 않음 |
| 결제 시작 | 주문번호, 결제 키, 확인한 revision/금액, 선택 쿠폰/적용 항목. 재검증 후 금액/실행 요청을 고정 |
| 결제 전 취소 | 주문번호·인증 회원. 중복 취소는 이미 종결된 결과 반환. 이미 결제 성공한 주문은 환불 경로 안내 |
| 환불 접수/조회 | 주문번호, 환불 키, orderItemId/quantity 목록. 소유권·남은 수량·금액 검증 |
| 결제·환불 결과 반영 | 외부 요청/결제 식별자, 주문 참조, 금액·통화, 확정 결과와 결과 식별자. 연계 계층에서 신뢰 가능한 결과로 정규화 |
| SKU 협력 | 스냅샷에 필요한 현재 SKU 데이터 조회, reserve/confirm/release/restock. 같은 DB 트랜잭션 참여·조건부 수량 갱신·가격 일관성 보장 필요 |

인증된 회원의 주문만 조회/취소/환불할 수 있어야 한다. SKU ID나 환불 항목 ID가 존재한다는 이유만으로 허용하지 않는다. 결과 수신은 사용자 임의 요청으로 성공 처리할 수 없게 기존 서비스 인증/소비자 경계를 유지한다.

현재 API는 productId 및 payment-group 중심이고 환불 대상도 Cart ID 중심이다. 새 SKU/OrderItem 의미로 바꾸면 외부 계약 변경이다. 기존 API에 필드 이름만 바꿔 끼우지 않고, 호출자 이행 기간의 어댑터 유지 또는 버전 경로 도입을 비교한다. API YAML, 실제 컨트롤러/DTO, 인증, 소비자와 이벤트 원본을 같은 구현 단위로 맞춰야 한다.

## 11. 이행과 공유 파일 책임

현재 `orders`는 Sales 한 건을 가리키는 항목이고 `payment_group`이 묶음이다. `refund_target_order`와 `payment_delivery_request`에도 기존 FK/ID 의미가 있다. 새 Order/OrderItem을 설계했다고 기존 ID를 서로 대입하면 안 된다.

구현 순서 제안:

1. Product/Cart 항목/SKU 식별자는 BIGINT/Long, Sales ID를 기본 SKU ID에 보존하는 우선안을 적용한다. 옵션 공급·판매 가능 원자 검증·매핑 예외와 삭제 정책, 금액/수량 형식과 같은 DB 트랜잭션 참여는 추가로 맞춘다. 신규 Product false/SKU READY를 기존 행에 일괄 적용하지 않는다.
2. 네 담당자가 공유 API/이벤트 변경 경로와 마이그레이션 번호·적용 순서를 배정한다. Order는 공유 주문 서비스 변경 조정 창구이고 SKU 엔티티/DDL을 중복 작성하지 않는다.
3. 기존 PaymentGroup→Order, 기존 Order→OrderItem의 명시적 매핑을 설계하고 기존 주문번호·가격·할인·결제/환불 참조를 보존한다. 이미 구매한 항목의 가격을 현재 SKU 가격으로 다시 채우지 않는다.
4. 기존 판매 하나에 SKU 여러 개가 생기는 경우 과거 옵션을 복원할 근거가 없으면 임의 선택하지 않는다. 기본/레거시 SKU와 원본 ID 보존 정책을 Product/SKU와 정한다.
5. 활성 주문은 금액·재고·외부 Payment 참조가 걸려 있으므로 즉시 일괄 변환하지 않는 안을 우선 검토한다. 짧은 이행 기간의 기존 흐름 유지 또는 신규 생성 일시 제한 후 종결 대기를 선택해야 한다. 어느 방식을 사용할지는 미결정이다.
6. 기존 참조가 필요한 동안 호환 어댑터/매핑을 유지하고, 과거 주문·진행 중 결제·환불·재처리 표본으로 검증한다. 읽기/쓰기 주체가 전환되기 전에 Sales/PaymentGroup/기존 FK를 제거하지 않는다.

Order 조정 대상: `OrderCreationService`, `OrderPaymentOutcomeService`, `PaymentGroupLifecycleService`, `PaymentGroupCheckoutService`. Cart 전용 파일과 SKU/Product 모델은 각 담당자의 작업을 보존한다. 현재 위치가 order 패키지라는 사실만으로 Cart/결제 전달의 모든 책임을 Order로 가져오지 않는다.

코디네이터는 Core RefundIntake/Query/Outcome 조정도 Order에 배정했다. Cart 저장·CRUD·선택 잠금·조건부 성공 정리 포트는 Cart 담당이며 #340 보류 중 현행 Cart ID/version·환불 참조를 임의 제거하지 않는다. SKU는 sales-info 이벤트와 다중 SKU Catalog 판매 사본의 최소 호환, Product는 제어/삭제 이벤트와 Catalog Product 사본의 해당 변경을 맡는다. 대표가/최저가/합산재고나 외부 단일값 응답 정책은 이 배정에서 도출하지 않는다.

## 12. 선택 이유와 대안

| 선택/제안 | 이유 | 대안과 비용 |
|---|---|---|
| Order 1:N OrderItem | 주문번호·결제 묶음·환불 대상을 분리해 이해하기 쉬움 | 기존 항목별 Order+PaymentGroup 유지 시 이행 비용은 작지만 사용자가 정한 주문번호 의미와 계속 어긋남 |
| 스냅샷 | 당시 구매 내용이 상품 변경/삭제 후에도 보존됨 | 상품 버전 참조는 버전 이력 기능과 주문 조회를 결합 |
| 주문서 생성 때 선점 | 사용자 확정 흐름, 화면에서 확인한 재고/가격을 일정 시간 확보 | 결제 클릭 때 선점하면 홀딩은 짧지만 사용자가 정한 생성 시점과 다름 |
| 예약 테이블 없음 + 같은 DB 트랜잭션 | 사용자 확정, Order 항목/상태가 예약 수량과 해제 권한의 근거 | 별도 예약 저장소는 이번 요구에 중복 원본과 정리 작업을 늘림 |
| 환불 건별 적용 기록 | 주문 전체 상태가 유지되는 부분 환불도 중복 없이 처리 | 주문 상태만 비교하면 서로 다른 환불과 중복 결과를 구분할 수 없음 |
| 주문당 미확정 환불 한 건 | 수량 한도·원 단위 잔액·실패 후 재시도가 단순 | 여러 환불 동시 접수는 병렬성은 높지만 수량/금액 배분과 실패 회수가 복잡 |
| 기존 영속 전달 활용 | 통지 유실을 막되 기존 재처리 기반을 활용 | HTTP 단발 호출은 커밋 뒤 종료에 취약, 새로운 범용 전달 체계는 범위 확대 |

## 13. 구현 수용 기준과 검증 계획

아래는 **실행하지 않은 검증 계획**이다. 업무 단위 테스트와 실제 PostgreSQL 트랜잭션/행 잠금 검증, HTTP/Kafka 계약·실제 전달 검증을 구분한다.

| 시나리오 | 기대 결과 | 필요한 검증 |
|---|---|---|
| 두 SKU 중 하나 재고 부족 | 주문·다른 SKU 선점도 전부 롤백 | PostgreSQL 통합 |
| 동일 생성 키 다중 인스턴스 경합/응답 유실 | 주문 하나·선점 한 번·동일 스냅샷 | PostgreSQL 동시성 |
| 생성 후 SKU 가격/상품명/옵션 변경 | 기존 주문의 저장 정보와 결제 원가 유지 | 업무 테스트 + 통합 |
| 재진입·조회·쿠폰 선택 변경 | 중복 선점/TTL 연장 없음 | 업무/API 테스트 |
| 결제 성공과 정확한 만료 경계 경합 | PAID+예약 확정 또는 실패+예약 해제 중 한 결과만 | 주입 시계 경계 + PostgreSQL 경합 |
| 만료 후 지연 성공/보상 환불 중복 | 주문 실패 유지·통지 재시도·재고 재복구 없음 | 업무 테스트 + 연계 전달 |
| 여러 SKU 잠금 순서 경합 | 음수/부분 커밋 없음, 일관된 재시도 | PostgreSQL 동시성 |
| 환불 응답/이벤트 중복 및 적용 중 종료 | 한 번만 수량/금액/재고/쿠폰 반영 | PostgreSQL 통합 + 실제 전달 |
| 같은 SKU 일부 수량을 여러 번 환불 | 구매 수량·실지불액 초과 없음, 최종 잔액 일치 | 정책 확정 후 경계/성질 테스트 |
| 전체 환불 뒤 쿠폰 재사용 후 옛 성공 재전달 | 새 주문의 쿠폰 사용 상태를 변경하지 않음 | 통합 |
| 장바구니 편집/삭제/재등록 후 결제 성공 | 원본 버전과 다른 항목 보존 | Cart 공동 검증 |
| 과거 주문/진행 중 결제·환불 이행 | 번호·금액·참조·재처리 의미 보존 | 격리 PostgreSQL migration 테스트 |
| 다른 회원의 주문/항목 접근 | 조회·결제·취소·환불 모두 거절 | 인증/권한 API 테스트 |

테스트는 한국어 DisplayName과 실제 실행 경로를 지정한다. Mock/H2 통과를 PostgreSQL/Kafka/PG 검증으로 보고하지 않는다. 구현 후 `scripts/check.sh --base origin/dev --dry-run`으로 영향 검사를 선택하며, API 변경에는 계약 구조 검사와 의미 대조가 필요하다. 명령·환경·실행 결과는 실행 계획과 워크로그에서 관리한다.

## 14. 상세설계 검토 후 남길 결정

상세설계 자체는 위 구조로 검토할 수 있다. 업무 정책 U1/U2/U3는 모두 확정됐으며 아래 목록은 구현/연계 검증 상태로 관리한다.

| 항목 | 권장안 또는 필요한 확인 |
|---|---|
| 부분 환불 금액 | U1 확정: 단가×이번 수량과 남은 항목 실결제액 중 작은 값. 4,000/4,000/2,000 및 8,000/2,000, 0원 잔여 수량 회귀 검증 |
| 누적 전량·만료 쿠폰 | U2 확정: 누적 전량 마지막 성공 시 복원, 원래 기간 유지. 구현/회귀 검증은 진행 중 |
| 쿠폰 적용 범위 | U2 확정: 주문당 한 장·선택한 OrderItem 하나에 적용. Product의 여러 SKU로 나누지 않음 |
| 재진입·미확정 환불 제한 | §4의 동일 주문 복원/키/TTL, 결제 요청 이후 즉시 취소 제한은 U3 확정이며, §8의 미확정 환불 한 건은 기술 검토안 |
| 실패 주문 보상 | Payment 종료 통지, 순서 역전, 미확정 조회와 늦은 성공 보상 계약 확인. 현행 사용자 환불 API만으로 대체 불가 |
| Product/SKU/Cart·이행 | 옵션 JSON 스냅샷 공급, 판매 가능 조건의 원자 검증/잠금 순서, Cart 출처/환불 호환, Sales 매핑 예외, 활성 주문 전환, DDL 번호·적용 순서 확정. BIGINT/Long 식별자·신규 판매 준비·공유 API 최종 편집자 배정은 후속 인계로 정해졌으며 재질문하지 않음 |

## 15. 근거와 산출물 상태
