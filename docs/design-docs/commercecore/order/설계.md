# Order 상세설계

구현 기준: Core V104·Payment V4와 Order #331 통합 브랜치. **코드 작성·부분 검증 완료, 전체 통합 회귀 진행 중**이다. 논리 설계 완료와 전체 구현 검증 완료를 구분한다.

## 1. 사용자 확정

한 주문번호는 여러 SKU 구매 항목을 가진다. Product는 상품 표현·전체 판매허용, SKU는 현재 가격·available/reserved·개별 판매 의도를 소유한다. Order는 SKU 수량·가격·상품명·판매자·대표 이미지 및 Cart 출처를 주문서 생성 시 저장한다. 이후 SKU 변경으로 재가격 산정하지 않는다.

주문서 서버 생성 요청이 Pending 생성·선점 시점이다. 신규 주문은 최초 생성부터 10분이며 결제 진행/UNKNOWN도 연장 사유가 아니다. 기한이 지나면 실패·예약 해제하고 Payment에 종료를 통지한다. 늦은 성공은 주문을 부활시키지 않고 금전 보상한다. 별도 예약 테이블 없이 주문 상태와 SKU 변경을 같은 Core DB 트랜잭션으로 적용한다.

결제 결과 대기 중 즉시 취소는 제한한다. 결제 후에는 환불 성공 확인 때만 취소 범위가 확정되고 해당 성공 수량의 재고를 복구한다. 주문당 쿠폰 한 장을 선택 항목 하나에 적용하며 누적 주문 전체 수량의 환불이 성공할 때 한 번 복원한다. 원래 유효기간을 유지하고 연장·재발급하지 않는다.

## 2. 데이터와 물리 이행

논리 Order는 기존 `payment_group`, OrderItem은 기존 `orders`다. BIGINT PK·물리명·기존 외부 번호를 교환하지 않는다. 새 주문번호만 UUID 문자열이다. 내부 항목번호와 PK는 주문번호와 별개다.

`payment_group.policy_version=1`이 새 주문서 경로다. 버전0은 기존 API·활성 구매의 원래 금액·15분 기한·PAYMENT_CONFIRMING 호환을 유지한다. 이는 공통 구현 착수 인계의 기존 활성 주문 TTL 보존과 신규 주문에만 새 정책 적용 지시를 따른 병행 이행이며, 신규 `/v1/order-sheets`의 10분 확정 정책을 15분으로 바꾼 것이 아니다. 버전1은 물리 PENDING_PAYMENT를 API의 PENDING으로 표현하며 결제 요청 후에도 원래 기한 판정을 유지한다.

Core V104는 다음을 확장한다.

- payment_group: policy_version, failure_reason, coupon_order_item_id.
- orders: sku_id, product_id_snapshot, seller_id_snapshot, main_image_snapshot, selected_options_snapshot. 신규 SKU 항목은 기존 Sales가 없어도 저장할 수 있도록 sales_info_id를 nullable로 하고 둘 중 거래 출처 하나를 요구한다.
- refund_target_order: quantity. 기존 환불은 원래 전체 항목 수량을 보존하고 새 요청은 명시 수량을 저장한다.
- refund_request: USER/COMPENSATION 구분과 종료 요청 참조. 내부 보상은 사용자 환불 조회에서 제외한다.
- order_payment_closure: 원 paymentId/paymentRequestId별 종료 의도와 전달 재시도 상태.
- member_coupon: used_payment_group_id. 과거 환불이 재사용된 쿠폰을 해제하지 않도록 사용 출처를 조건부 대조한다.

V102에서 기존 Sales ID=기본 SKU ID와 available/reserved를 그대로 옮긴다. V104는 검증된 같은 ID 매핑만 사용하고 현재 SKU 가격으로 과거 주문을 채우지 않는다. 옵션 JSON 공급 계약은 보류라 null로 유지한다. 기존 FK는 적용 SQL을 수정해 지우지 않으며 새 모듈 간 FK는 추가하지 않는다.

## 3. 생성·재진입

`POST /v1/order-sheets`는 직접 items(skuId,quantity) 또는 cartItems(itemId,version) 중 하나를 받는다. null 원소·중복 SKU·비양수 수량·합산/곱셈 초과를 400으로 거절한다. 클라이언트 화면 가격을 신뢰하지 않는다.

생성 키와 정규화 입력의 해시를 회원과 함께 저장한다. 회원 구매 가드로 기존 API까지 활성 구매 하나를 직렬화한다. 같은 생성 키는 Cart를 다시 읽기 전에 원래 주문을 찾으므로 Cart가 편집·삭제돼도 최초 결과를 재사용한다. 다른 원문은409다. 만료 재전송은 FAILED/EXPIRED를 반환하며 TTL과 선점을 새로 만들지 않는다.

생성 잠금 순서는 회원 가드 → 선택 Cart → 모든 Product ID순 공유 잠금 → 모든 SKU ID순 쓰기 잠금이다. Product 미삭제·전체 허용과 SKU 판매가능/재고를 검증한 뒤, 한 트랜잭션에서 root/items 저장·전체 선점을 처리한다. 하나가 실패하면 모두 롤백한다.

시각은 PostgreSQL `clock_timestamp()`를 잠금 후 조회하고 생성 기준과 기한을 같은 값으로 저장한다. H2 대체만 CURRENT_TIMESTAMP다. 여러 JVM의 시계로 10분 경계를 달리 판정하지 않는다.

## 4. 쿠폰과 결제

쿠폰 선택 클릭마다 서버 변경 요청을 강제하지 않는다. 주문서 스냅샷과 기존 쿠폰 후보로 화면이 예상 금액을 계산하고, 결제 요청에 couponId/couponOrderItemId/expectedPayableAmount를 보낸다. 쿠폰과 대상은 함께 선택하거나 함께 null이다.

서버는 저장된 해당 항목 원가로 소유·유효기간·대상·사용 가능 여부를 검증한다. SKU 현재 가격은 다시 읽지 않는다. 서버 금액과 사용자가 확인한 금액이 다르면409로 거절하고 요청 전체를 롤백한다. 결제 전달 원문 저장 시 쿠폰·항목 할인·실결제액을 고정한다. 같은 키는 원 결제를 재사용하고 원문 변경은 거절한다.

외부 HTTP는 트랜잭션 커밋 뒤 호출한다. 기한 안 SUCCESS 최초 적용은 주문/항목 PAID, SKU reserved 소진, 쿠폰 USED+사용 주문 출처, Cart ID/member/version 조건부 삭제를 함께 처리한다. 수정·삭제 후 재등록한 Cart 항목은 보존한다. 직접 구매에는 빈 Cart 포트를 호출하지 않는다.

0원 결제도 독립 Payment의 원장·결과·멱등성 경로를 사용하며 실제 PG 승인은 만들지 않는다. 시간 초과/UNKNOWN을 결제 실패로 단정하지 않는다.

## 5. 만료와 늦은 성공

버전1의 기한이 지나면 PENDING_PAYMENT → FAILED/failureReason=EXPIRED, 각 SKU available+q/reserved−q, 쿠폰 예약 해제, 필요한 종료 의도 저장을 같은 Core 트랜잭션으로 처리한다. 단순 결제 확정 실패는 failureReason=PAYMENT_FAILED다. 취소는 결제 요청 저장 전만 가능하고 CANCELLED로 한 번 해제한다.

[Payment 종료/보상 계약](../../../exec-plans/active/331-order-module/payment-closure-contract.md)은 PUT /v1/internal/payments/{paymentId}/order-closure다. Core는 종료 의도를 재전송하고 receipt를 저장한다. Payment는 생성·종료·호출 시작이 같은 영속 실행 제어키를 잠근다. 아직 호출하지 않았다면 승인을 차단하고 이미 호출 중/UNKNOWN이면 결과 조회로 수렴한다.

종료 HTTP보다 보상 환불 접수가 먼저 오면503 재시도이며 원문 충돌409와 구분한다. 늦은 성공의 원 결제 전액 보상은 같은 paymentId+원 paymentRequestId로 유일하다. 다른 환불/종료 키로 중복 우회할 수 없다. 보상 결과는 원 주문 실패를 유지하며 SKU·Cart·쿠폰을 다시 변경하지 않는다. 0원 늦은 성공은 환불 요청 자체를 만들지 않는다.

일반 환불 flag off에서도 저장된 종료와 대조된 COMPENSATION만 전달·실행·재시작 복구한다. 일반 사용자 환불은 계속 off다. 확정 보상 FAILED의 운영 재처리는 별도 원장 확인이 필요하며 새 키로 같은 보상을 무단 복제하지 않는다.


### 종료 뒤 성공 결과의 도달 조건

보드 초안의 `FAILED/CANCELLED → 늦은 성공 보상`을 모든 종료 원인에 적용하지 않는다. 현재 사용자 확정인 U3에 따라 취소는 `paymentId IS NULL`일 때만 가능하다. 취소와 결제 시작은 같은 회원/주문 잠금으로 직렬화하므로 CANCELLED 주문에는 전달 원문·Payment 실행이 없으며 취소 뒤 결제 시작도 거절한다.

`FAILED/PAYMENT_FAILED`는 Payment의 확정 FAILED를 반영한 상태다. 독립 Payment의 `PaymentRecoveryStore.complete`는 미확정 상태와 유효 lease·resolved_at null을 조건으로 한 번만 확정하며 UNKNOWN을 FAILED로 강제하지 않는다. Core도 저장된 requestId·금액·대상·시각과 확정 결과를 대조한다. 동일 확정 결과는 무변경, FAILED 뒤 상충 SUCCESS는 계약 위반409다. 실제 PG에서 확정 실패를 나중에 성공으로 정정하는 새 계약은 이번 Mock 실행 계약에 없고 지원 완료로 주장하지 않는다.

반면 `FAILED/EXPIRED`는 Core의 기한 종료이며 Payment 결과 확정과 독립이다. 만료 당시 PROCESSING/UNKNOWN 또는 승인 성공 미반영이 도달 가능하므로 종료 의도를 영속화하고 뒤늦은 SUCCESS를 전액 보상한다. 이미 해제한 재고·Cart·쿠폰에는 보상 부수 효과를 다시 적용하지 않는다.

## 6. 수량 환불과 쿠폰 복원

사용자 확정 계산은 항목별 `min(스냅샷 단가×이번 수량, 항목 실결제액−이전 성공 환불액)`이다. 비례배분·반올림 제안은 폐기했다.

| 4,000원×3개, 쿠폰2,000원 | 이번 환불 | 누적 환불 |
|---|---:|---:|
| 첫1개 | 4,000 | 4,000 |
| 둘째1개 | 4,000 | 8,000 |
| 셋째1개 | 2,000 | 10,000 |
| 처음2개 일괄 | 8,000 | 8,000 |

환불 원결제 성공 후 기존168시간 접수 기한을 유지한다. 주문 잠금 아래 미확정 사용자 환불 한 건으로 직렬화하고 대상 수량/금액과 전달 원문을 저장한다. 다른 동시 요청은409다. 같은 키는 최초 요청을 반환하고 다른 원문은409다. 실패 건의 수량/금액은 성공 합계에 넣지 않아 새 키 재시도가 가능하다.

성공 결과 최초 적용 시 환불 기록·항목 PARTIALLY_REFUNDED/REFUNDED·root 부분/전체 상태·이번 성공 수량만 SKU 복구·필요한 쿠폰 복원을 같은 트랜잭션으로 처리한다. 반영 중 오류는 전부 롤백하고 같은 Payment 결과로 재시도한다. 접수/UNKNOWN/실패에는 재고를 복구하지 않는다.

큰 할인으로 남은 환불액이0이 되더라도 남은 구매 수량은 환불할 수 있다. Payment 원장에0원 성공을 기록하고 실제 PG 환불을 호출하지 않는다. 쿠폰 항목만 모두 환불하고 다른 항목이 남은 경우는 전체 주문 환불이 아니다. 모든 항목의 전체 수량이 누적으로 성공했을 때만 기존 유효기간 그대로 쿠폰을 한 번 복원한다.

외부 관행은 [공식 정책 조사](../../../exec-plans/active/331-order-module/refund-policy-research.md)에 별도 보존한다. 외부 업체가 같은4천/4천/2천 방식을 쓴다고 주장하지 않는다.

## 7. 구 API 호환과 모듈 경계

구 productId API는 `SkuService.findByProductId`로 SKU가 하나인 상품만 지원한다. SKU가 없으면404, 여러 개면409와 새 주문서 경로를 안내한다. Sales 이력이 없는 신규 SKU도 지원하며 새 구 API 주문은 `sku_id`/`product_id_snapshot`을 저장하고 `sales_info_id`는 null로 둔다. 과거 주문의 Sales 참조와 FK는 보존하고 완료·해제·환불은 `sku_id` 우선, 없으면 보존된 `sales_info_id`를 사용한다. 가격·재고는 SKU 원본이다. 옵션 SKU Cart를 임의 기본 SKU로 바꾸지 않는다. 기존 단일 SKU 호출의 번호·금액·멱등키·기한은 유지한다. 이미 생성된 기존 구매의 완료/해제/환불에는 현재 상품·SKU 판매 상태를 다시 요구하지 않는다.

ProductTradingService, SkuService, CartSelectionPort의 실제 소유 DTO/포트를 연결한다. SKU 수량은 호출자 트랜잭션 MANDATORY다. Product/SKU/Cart 코드나 공통 FigJam을 Order가 대신 소유하지 않는다. 코드 의존은 Product→SKU→Cart→Order 네 PR로 통합한다.

## 8. 검증 상태

현재 실행 건수·실패 이력·재현 명령은 [실행 계획](../../../exec-plans/active/331-order-module/README.md)과 [워크로그](../../../worklog/2026-11-13.md)가 원본이다. PostgreSQL/Mock gateway, H2, 정적 계약/문서, 브라우저, 외부 Kafka/PG/AWS/CI 증거를 섞지 않는다. HTML의 논리 관계는 물리 확장과 대응하지만 전체 회귀 통과·배포 완료를 뜻하지 않는다.

## 8. 직접 합의와 구분하는 구현 선택

다음 세 항목은 사용자 직접 선택으로 확인한 근거가 없다. 기존 구현 인계·코디네이터의 기술 선택을 이어받아 검증하는 현재 동작이며, 사용자 영향의 확인 전 전체 정책 확정으로 표시하지 않는다.

| 항목 | 현재 동작·사용자 영향 | 대안 |
|---|---|---|
| 구 API 신규 주문 15분 | 기존 활성 행의 TTL뿐 아니라 구 API로 새로 생성한 policy_version=0도15분이다. 신규 주문의 endpoint에 따라10/15분이 갈린다. 사용자 직접 확정은 신규 주문서10분이며 구 API 예외 자체를 직접 선택한 근거는 없다. | 과거 행의 TTL만 보존하고 모든 신규 생성 경로를10분으로 통일 |
