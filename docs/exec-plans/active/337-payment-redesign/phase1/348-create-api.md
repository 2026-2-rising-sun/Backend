# #348 결제 생성·결제창·조회 내부 API

상태: 설계 확정(2026-11-15)
이슈: [#348](https://github.com/2026-2-rising-sun/Backend/issues/348) · Phase 문서: [Phase 1 결제 1차](../phase1-payment.md)

## 개요

끝나면 Commerce가 내부 API로 **결제를 만들고, 결제창을 다시 열고, 상태를 조회**할 수 있다. 같은 요청을 다시 보내도 결제는 1건이다. 이 이슈가 만드는 V4 스키마와 결제 키 규칙을 #338·#349가 그대로 쓴다. **스키마의 원본은 이 문서다.** 컬럼을 바꿀 일이 생기면 이 문서를 먼저 고친다.

### 2) 새 테이블

```sql
-- 결제 1건. 주문(Commerce)과는 order_ref 값으로만 연결한다.
CREATE TABLE payment (
    id                 BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_ref          VARCHAR(64)  NOT NULL UNIQUE
                       CHECK (char_length(order_ref) BETWEEN 6 AND 50),
    buyer_id           VARCHAR(36)  NOT NULL,
    amount             BIGINT       NOT NULL CHECK (amount > 0),
    refunded_amount    BIGINT       NOT NULL DEFAULT 0,
    status             VARCHAR(32)  NOT NULL,
    expires_at         TIMESTAMP WITH TIME ZONE NOT NULL,
    pg_provider        VARCHAR(32)  NOT NULL,
    pg_order_id        VARCHAR(64)  UNIQUE,
    checkout_seq       INTEGER      NOT NULL DEFAULT 0,
    pg_payment_key     VARCHAR(200) UNIQUE,
    pg_status          VARCHAR(32),
    partial_cancelable BOOLEAN,
    approved_at        TIMESTAMP WITH TIME ZONE,
    approving_at       TIMESTAMP WITH TIME ZONE,
    next_check_at      TIMESTAMP WITH TIME ZONE,
    check_deadline_at  TIMESTAMP WITH TIME ZONE,
    created_at         TIMESTAMP WITH TIME ZONE NOT NULL,
    updated_at         TIMESTAMP WITH TIME ZONE NOT NULL,
    CONSTRAINT ck_payment_status CHECK (status IN
        ('CREATED','APPROVING','APPROVED','UNKNOWN','CANCELED','PARTIALLY_REFUNDED','REFUNDED')),
    CONSTRAINT ck_payment_refunded CHECK (refunded_amount BETWEEN 0 AND amount)
);
CREATE INDEX ix_payment_check     ON payment(next_check_at) WHERE status = 'UNKNOWN';
CREATE INDEX ix_payment_approving ON payment(approving_at)  WHERE status = 'APPROVING';
CREATE INDEX ix_payment_expiry    ON payment(expires_at)    WHERE status = 'CREATED';

CREATE TABLE payment_seller_amount (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    payment_id          BIGINT       NOT NULL REFERENCES payment(id),
    seller_order_number VARCHAR(64)  NOT NULL UNIQUE,
    seller_id           VARCHAR(36)  NOT NULL,
    amount              BIGINT       NOT NULL CHECK (amount > 0),
    commission_rate     NUMERIC(5,4) NOT NULL CHECK (commission_rate BETWEEN 0 AND 1)
);
CREATE INDEX ix_psa_payment ON payment_seller_amount(payment_id);

-- PG 호출 기록. 호출 전에 outcome='UNKNOWN'으로 넣고, 응답을 받으면 그 행의 결과만 채운다(#338).
CREATE TABLE pg_call (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    payment_id      BIGINT      NOT NULL REFERENCES payment(id),
    kind            VARCHAR(16) NOT NULL CHECK (kind IN ('CONFIRM','QUERY','CANCEL')),
    pg_order_id     VARCHAR(64),
    idempotency_key VARCHAR(300),
    outcome         VARCHAR(16) NOT NULL CHECK (outcome IN ('SUCCESS','DECLINED','NOT_SENT','UNKNOWN')),
    http_status     INTEGER,
    result_code     VARCHAR(64),
    requested_at    TIMESTAMP WITH TIME ZONE NOT NULL,
    responded_at    TIMESTAMP WITH TIME ZONE
);
CREATE INDEX ix_pg_call_payment ON pg_call(payment_id, id);

-- 원장. 분개는 고치거나 지우지 않는다. 정정은 반대 분개로 한다.
CREATE TABLE ledger_journal (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ref_type   VARCHAR(32) NOT NULL CHECK (ref_type IN
        ('PAYMENT_APPROVED','REFUND_SUCCEEDED','PURCHASE_CONFIRMED','SETTLEMENT_REVERSED','PAYOUT_COMPLETED')),
    ref_id     VARCHAR(64) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    CONSTRAINT uq_ledger_journal_ref UNIQUE (ref_type, ref_id)
);
CREATE TABLE ledger_entry (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    journal_id BIGINT      NOT NULL REFERENCES ledger_journal(id),
    account    VARCHAR(32) NOT NULL CHECK (account IN
        ('PG_CUSTODY','BUYER_DEPOSIT','SELLER_PAYABLE','COMMISSION_REVENUE')),
    debit      BIGINT      NOT NULL DEFAULT 0,
    credit     BIGINT      NOT NULL DEFAULT 0,
    seller_id  VARCHAR(36),
    CONSTRAINT ck_ledger_side   CHECK ((debit > 0 AND credit = 0) OR (credit > 0 AND debit = 0)),
    CONSTRAINT ck_ledger_seller CHECK (account <> 'SELLER_PAYABLE' OR seller_id IS NOT NULL)
);
CREATE INDEX ix_ledger_entry_journal ON ledger_entry(journal_id);
CREATE INDEX ix_ledger_entry_account ON ledger_entry(account, seller_id);
```

설계 HTML `#ddl`의 V4와 같다. `pg_call`은 호출 전에 행을 먼저 커밋해야 하므로(공통 규칙 "외부 호출") 추가만 하지 않고 응답 뒤 그 행의 결과만 채운다(#348 스키마 PR에서 HTML 주석도 맞춤).

### 시각 규칙

- 엔티티는 common-module `AuditedEntity`를 상속하고, 애플리케이션이 `@Import(JpaAuditingConfig.class)`로 auditing을 켠다. INSERT의 `created_at`·`updated_at`은 auditing이 채운다. 네이티브 INSERT(`ON CONFLICT`)는 auditing을 거치지 않으므로 SQL에서 `now()`를 넣는다.
- 상태를 바꾸는 UPDATE는 SQL에서 `updated_at = now()`로 쓴다. 만료·정체 같은 시간 판단은 모두 DB `now()`로 한다(공통 규칙 "시간").
- JPA는 `ddl-auto: validate`다. 엔티티 매핑이 위 DDL과 다르면 기동이 실패한다.

## API

공통: 경로 접두 `/v1/internal`, 헤더 `X-Service-Token`(없거나 다르면 **401**, PAY-AUTH-01), 응답 `ApiResponse {success, data, error{code, message, requestId}}`. 계약 원본은 이 PR에서 `contracts/api/payment-service.yaml`을 다시 쓴 것이 된다.

### 오류 응답 만들기

공통 `ErrorCode`에는 업무 코드가 없다. Payment는 `PaymentError` enum(`code`, `httpStatus`)과 `PaymentException`을 두고, `PaymentExceptionHandler`가 `new ApiResponse.ApiError(code, message, CorrelationId.current())`로 응답한다. Catalog `RequestErrorExceptionHandler`와 같은 방식이다. Bean Validation 실패는 400 `INVALID_REQUEST`다.

### 1. 결제 생성 `POST /v1/internal/payments`

요청:

| 필드 | 의미 | 형식·제약 | 예시 |
|---|---|---|---|
| `orderRef` | 주문 참조 | 필수(`@NotBlank`만). 형식 `^[A-Za-z0-9_-]{6,50}$`은 **Bean Validation 밖**에서 검사해 400 `INVALID_ORDER_REF`를 낸다. 문자 제한은 토스 orderId 규칙(영문·숫자·`-`·`_`, 6–64자)에서 왔고, 50자는 `-{시도 번호}`가 64자 안에 들어가게 한 값이다 | `OD-20261110-K7Q2M9XA` |
| `buyerId` | 구매자 | 필수, UUID | |
| `amount` | 결제 금액 | 필수, ≥ 1 | `30000` |
| `expiresAt` | 결제 만료 시각 | 필수, ISO-8601 오프셋 포함. **새 결제를 만들 때만** DB `now()` 이하면 400 `INVALID_EXPIRES_AT`(같은 orderRef가 있으면 검사하지 않는다) | `2026-11-10T14:10:00+09:00` |
| `sellerAmounts[]` | 판매자별 금액 | 필수, 1개 이상 | |
| `sellerAmounts[].sellerOrderNumber` | | 필수, ≤ 64자, 요청 안에서 중복 없음 | `…-S1` |
| `sellerAmounts[].sellerId` | | 필수, UUID | |
| `sellerAmounts[].amount` | | 필수, ≥ 1. 합 ≠ `amount`면 400 `SUM_MISMATCH` | `20000` |
| `sellerAmounts[].commissionRate` | | 필수, 0–1, 소수 4자리 이하 | `0.1000` |

응답 `data`: `{paymentId, status, pgOrderId, amount, expiresAt}`

```json
// 201 (새 결제)
{ "paymentId": 1001, "status": "CREATED", "pgOrderId": "OD-20261110-K7Q2M9XA-1",
  "amount": 30000, "expiresAt": "2026-11-10T14:10:00+09:00" }
```

**같은 orderRef가 이미 있을 때** (PAY-CREATE-02·03·06). 위에서부터 처음 맞는 줄:

| 기존 결제 | 요청과 비교 | 응답 |
|---|---|---|
| 없음 | — | 201 새 결제. `checkout_seq = 1`, `pg_order_id = {orderRef}-1` |
| 있음 | `amount` 또는 `buyerId`가 다름 | 409 `AMOUNT_CONFLICT` |
| CREATED, 만료 전 | 같음 | 200 현재 값(현재 `pgOrderId`) |
| APPROVING · UNKNOWN · APPROVED | 같음 | 200 현재 값(`status` 그대로) |
| CREATED 만료 · CANCELED · PARTIALLY_REFUNDED · REFUNDED | 같음 | 409 `PAYMENT_CLOSED` |

- 비교는 `amount`·`buyerId`만 한다. `expiresAt`·`sellerAmounts`가 달라도 저장된 값을 유지하고 비교하지 않는다(미결정 1). 재시도 본문의 `expiresAt`이 이미 지났어도 기존 결제가 있으면 `INVALID_EXPIRES_AT`이 아니라 위 표로 응답한다(2026-11-16 결정, PAY-CREATE-02).
- **동시 생성**(PAY-CREATE-02): `INSERT … ON CONFLICT DO NOTHING`(충돌 대상 생략. H2 PostgreSQL 모드에서 확인된 형태)의 영향 행 수로 판단한다. 0행이면 같은 트랜잭션에서 기존 행을 읽어 위 표로 응답한다. 예외를 잡는 방식은 쓰지 않는다(PostgreSQL은 UNIQUE 위반 시 트랜잭션 전체가 중단된다). `payment_seller_amount`는 INSERT가 1행일 때만 같은 트랜잭션에서 넣는다.
- `sellerOrderNumber`가 다른 결제에 이미 있으면 UNIQUE 위반이다. 정상 Commerce라면 생기지 않는다. 400 `INVALID_REQUEST`로 응답하고 WARN 로그를 남긴다.

### 2. 결제창 다시 열기 `POST /v1/internal/payments/{orderRef}/checkouts`

요청 본문 없음. 응답 201 `data`: `{pgOrderId, amount, expiresAt}`

```sql
UPDATE payment
   SET checkout_seq = checkout_seq + 1,
       pg_order_id  = order_ref || '-' || (checkout_seq + 1),
       updated_at   = now()
 WHERE order_ref = :orderRef AND status = 'CREATED' AND expires_at > now();
-- 1행: 같은 트랜잭션에서 다시 읽어 응답 (H2가 RETURNING을 지원하지 않으므로 다시 읽는다)
-- 0행: 결제 없음 → 404 NOT_READY, 있음 → 409 PAYMENT_CLOSED
```

- 호출할 때마다 새 결제창이 생긴다(멱등 아님. 그래서 201). 이전 pgOrderId로 온 승인은 #338에서 409 `STALE_CHECKOUT`이 된다.
- `NOT_READY`는 "Commerce의 결제 생성 요청이 아직 도착하지 않음"이다(결제 생성 재시도 중).
- APPROVING·UNKNOWN 중에 부르면 요구사항대로 409 `PAYMENT_CLOSED`지만, `message`는 "결제를 처리하고 있습니다"로 구분한다(닫힌 결제와 다르다는 것을 Commerce 로그에서 알 수 있게).
- 승인이 거절되거나 조회에서 ABORTED가 나오면 #338·#349가 `pg_order_id`를 NULL로 비운다. 그 뒤의 결제 생성 재요청(200)은 `pgOrderId: null`을 돌려주고, Commerce는 이 API로 새 결제창을 연다.

### 3. 조회 `GET /v1/internal/payments/{orderRef}`

응답 200 `data`: `{paymentId, status, amount, refundedAmount, pgOrderId, approvedAt}`. 없으면 404 `PAYMENT_NOT_FOUND`(제안). `approvedAt`은 승인 전 `null`.

### 오류 코드 (이 이슈)

| HTTP | code | 언제 |
|---|---|---|
| 400 | `INVALID_REQUEST` | Bean Validation 실패, 판매자 주문 번호 중복 |
| 400 | `INVALID_ORDER_REF` | orderRef 형식 |
| 400 | `INVALID_EXPIRES_AT` | 만료 시각이 현재 이하 |
| 400 | `SUM_MISMATCH` | 판매자별 금액 합 ≠ amount |
| 401 | `UNAUTHORIZED` | 서비스 토큰 없음·다름(공통 필터) |
| 404 | `NOT_READY` | 결제창: 결제 없음 |
| 404 | `PAYMENT_NOT_FOUND`(제안) | 조회: 결제 없음 |
| 409 | `AMOUNT_CONFLICT` | 같은 orderRef에 금액·구매자 다름 |
| 409 | `PAYMENT_CLOSED` | 닫힌 결제에 생성·결제창 |
