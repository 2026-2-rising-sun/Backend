## 목표와 범위

AI 에이전트가 요청 범위를 지키고 팀의 공통 기준으로 조사·변경·검증·기록하도록 기존 하네스를 재구성한다. 다음 사람이 작업의 목적과 결정 이유, 실제 실행 결과를 찾아 이어받을 수 있게 한다.

- 루트 `harness/`의 문서·검사기를 `docs/`와 `scripts/`로 이관하고 진입점과 실행 경로를 연결한다.
- 참고 이미지처럼 `docs/` 바로 아래에 명세·요구사항·ADR·설계·실행 계획·워크로그를 둔다.
- 복잡한 작업은 `exec-plans/active/<이슈번호>-<주제>/README.md`에서 계획·상태·관련 자료를 연결한다. 필요한 판단·조사 자료를 같은 폴더에 추가한다.
- MD는 AI 에이전트가 참조하기 쉬우면서 사람도 읽을 수 있는 원본으로, HTML은 사람이 구조·흐름·차이를 이해하는 시각 자료로 관리한다.
- 6개 서비스의 모듈별 API 명세·DB ERD·실제 상태 전이를 MD·HTML로 문서화한다. API 명세의 원본은 기존 OpenAPI YAML이며 HTML은 이를 표시하는 파생 자료다.
- 공통 모듈은 공통 처리와 Outbox를 설명하고, 여러 서비스가 협력하는 흐름은 상위 설계 문서로 연결한다.
- 기존 코드·테스트·Git 협업·API/이벤트 계약 기준과 검증기의 실패·스킵·0건·미실행·검사 중 변경 구분을 보존한다.

서비스 업무 동작과 API·이벤트 계약은 이번 개편의 변경 대상이 아니다. 가드·편집 후 훅·MCP 설정은 실제 사용 목적과 연결 경로가 정해질 때 별도로 구현한다. 커밋·푸시·PR·병합·배포는 사용자가 허용한 범위에서 수행한다.

### 4. 모듈별 문서의 원본과 생성·갱신 방식을 정한다

- [x] [모듈별 문서 범위](tables.md)에 따라 각 서비스의 계약, 마이그레이션, 엔티티, 상태 변경 코드와 관련 테스트를 조사한다.
- [x] 모듈 문서의 공통 구성을 `README.md`, `api.html`, `erd.md`, `erd.html`, `states/<주제>.md`와 같은 이름의 HTML로 정한다.
- [x] API HTML은 서비스 YAML과 공통 참조를 입력으로 생성한다. OpenAPI 렌더러·버전을 정하고 `scripts/render-api-docs.sh`에서 생성과 최신성 확인 방법을 제공한다. 명세를 MD에 다시 복사하지 않는다.
- [x] 생성한 API HTML은 Git에 추적하고 저장소의 로컬 자산으로 열람할 수 있게 한다. 문서를 열 때 별도 API 서버 실행이나 YAML 네트워크 요청을 요구하지 않도록 한다.
- [x] ERD는 Flyway 마이그레이션을 적용 순서대로 종합하고 엔티티 매핑과 대조한다. 물리 FK, 논리 참조, 서비스 간 식별자 참조를 구분한다.
- [x] 상태도는 상태값뿐 아니라 변경 서비스·이벤트·선행 조건·허용 전이·실패·중복 처리와 테스트를 확인한 뒤 작성한다. enum이나 주석만으로 전이를 추정하지 않는다.
- [x] 각 문서에 원본 경로·확인 기준 커밋과 작업 트리 변경 여부·검증 범위·미확인 사항을 남긴다. 독립 API·DB·상태 전이가 없는 항목은 모듈 안내에 적용되지 않는 이유를 적는다.

완료 기준: 모든 모듈에서 같은 방식으로 문서를 작성·열람·갱신할 수 있고, 계약·구현 원본과 문서의 관계가 분명하다. 실제 DB나 HTTP 동작을 실행하지 않았다면 코드·계약을 기준으로 작성한 자료임을 구분한다.

- [x] 파일 이름이나 링크 존재만으로 실제 검증 완료를 판단하지 않는다. 결과의 적절성과 의미는 문맥 검토로 확인한다.
- [x] 존재하는 기록과 참조의 구조를 검사한다. 중요한 결정의 발생 여부나 모든 작업의 ADR·계획 작성을 경로만으로 판정하지 않는다.
- [x] 생성된 API HTML이 원본 YAML·공통 참조와 일치하는지 확인하는 절차를 연결한다. ERD·상태도는 MD와 시각 자료의 노드·관계·전이 조건을 대조한다.
- [x] 동적 API 화면의 내부 이동과 정적 문서 앵커의 검사 범위를 구분해 안내한다. 실제 화면에서 지원하는 경로도 확인한다.

완료 기준: 유효한 문서는 통과하고 누락된 링크·잘못된 상태·완료 근거 부재는 관련 회귀 검사에서 탐지된다. 문서·시각 자료 작업도 실제 근거로 완료 상태를 표현할 수 있다.

### 8. 검사 실행 경로와 CI 선택을 완성한다

- [x] `check.sh`, `check-docs.sh`의 실행 권한·Python 선택·전달 인자·종료 코드를 확인한다.
- [x] 로컬 실행기와 CI가 같은 문서 검사 구현을 호출하도록 연결한다.
- [x] API 계약·공통 참조·렌더러 변경 시 HTML 생성 결과의 최신성 검사도 선택한다. 스키마·상태 코드 변경은 관련 문서 갱신 여부를 작업 절차와 리뷰에서 확인한다.
- [x] 도구·워크플로 변경은 해당 회귀 검사, 일반 MD·HTML 변경은 문서 검사로 선택되는지 확인한다.
- [x] `.gitignore`에서 문서 추적 패턴과 주석만 변경한 경우를 좁게 구분할 수 있는지 검증한다. 그 외 변경의 기존 전체 검사 선택은 유지한다.
- [x] 실행 리소스·공통 모듈·API·이벤트 계약 변경을 문서 변경으로 잘못 분류하지 않는지 확인한다.
- [x] 기존 검증기의 실패·스킵·0건·미실행·검사 중 diff 변경 처리와 결과 경로 호환성을 보존한다.

완료 기준: 검사 선택 이유를 설명할 수 있고 문서 추적 규칙 변경이 불필요하게 전체 Java·외부 검사를 선택하는 문제를 근거와 테스트로 해결한다.

### 9. 실제 사용 흐름으로 검증하고 작업을 정리한다

- [x] 아래 검증을 최종 diff에 맞춰 실행하고 결과·환경·미실행 사항을 워크로그에 기록한다.
- [x] 작은 수정, 여러 단계의 작업, 공통 설계 결정의 세 사례로 지침의 읽기 경로와 기록 작성 조건을 대조한다.
- [x] 문서 작성 → 로컬 검사 → 결과 기록 → 계획 완료 이동의 링크 연결을 확인한다.
- [x] 6개 서비스 문서 범위표를 대조하고, API 생성 결과·ERD·상태도·서비스 간 흐름이 근거와 연결되는지 확인한다.
- [x] 실제 확인한 수용 기준만 완료로 표시하고 남은 문서·도구 확장은 기술부채나 후속 이슈로 연결한다.
- [x] 최종 구조와 MD·HTML을 갱신하고 허용된 전달 범위에 맞춰 결과를 보고한다.

완료 기준: 저장소 안에서 작업 맥락을 이어갈 수 있고 실제 검증 근거가 연결된다. 문서·로컬 검사 통과를 원격 CI나 팀원별 에이전트 동작 확인으로 확대하지 않는다.

## 실행한 검증과 재현 방법

`scripts/check.sh --base origin/dev`에서 문서·API HTML·설계 HTML·분류기·하네스·워크플로 검사 6종이 모두 통과했고 검사 중 diff 변경은 없었다. 분류기 44개와 하네스 46개 테스트가 포함됐다. 아래는 개별 검사와 실행기의 재현 명령이다.

```bash
# 문서 검사기·실행기와 변경 선택기의 회귀 검사
.venv-api/bin/python -m unittest discover -s scripts -p 'test_*.py'
.venv-api/bin/python -m unittest discover -s .github/scripts/ci -p 'test_*.py'

# 문서·쉘·CI 정의 검사
.venv-api/bin/python scripts/check_docs.py
bash -n scripts/check.sh scripts/check-docs.sh scripts/render-api-docs.sh
scripts/render-api-docs.sh --check
.venv-api/bin/python scripts/render_design_docs.py --check
actionlint .github/workflows/ci.yml

# 최신 기준 ref를 확인한 뒤 최종 변경의 선택과 실행 결과 검토
.venv-api/bin/python scripts/verify.py --base origin/dev --dry-run
.venv-api/bin/python scripts/verify.py --base origin/dev
git diff --check
```

검증 환경은 [도구 안내](../../../guides/tooling.md), 결과 해석은 [테스트 기준](../../../guides/tests.md)을 따른다. 쉘 진입점 직접 실행과 생성 최신성 회귀 검사를 확인했다. HTML의 실제 확인 방법·결과와 미실행 범위는 워크로그를 참조한다.

API 문서는 `.venv-api/bin/python .github/scripts/api/check_structure.py`에서 6개 서비스의 경로·메서드 매핑 119개가 통과했으며, 계약 YAML과 생성 내용도 대조했다. 실제 응답·인증 동작을 검증한 것으로 확대하지 않는다. ERD·상태도는 소유 서비스, 마이그레이션·엔티티, 상태 변경 로직과 테스트의 근거를 대조한다. 불일치나 확인하지 않은 실행 경로는 문서에 남긴다.

원격 CI는 허용된 저장소 전달 이후 확인한다. 실제 PostgreSQL·Kafka·외부 서비스 검증은 해당 환경과 변경 영향이 있을 때 수행하며 실행하지 않은 환경을 성공으로 기록하지 않는다.
