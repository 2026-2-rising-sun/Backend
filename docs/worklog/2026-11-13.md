## #330 하네스 변경 계획

관련 작업: [실행 계획](../exec-plans/completed/330-document-harness/README.md) · [판단 기준](../exec-plans/completed/330-document-harness/decision.md) · [현황 조사](../exec-plans/completed/330-document-harness/research.md)

상태: 계획 수립 · 하네스 구현 미완료

### 작업과 판단

- 하네스를 AI 에이전트의 행동 기준과 실행 절차로 정의하고, 필요한 프로젝트 지식과 실제 작업 기록을 연결하는 방향을 정리했다.
- 참고 이미지의 문서 종류별 배치를 유지하면서 복잡한 작업은 실행 계획 아래 작업 폴더로 묶는 계획을 작성했다.
- MD는 에이전트가 참조하면서 사람도 읽을 수 있는 원본, HTML은 사람이 이해할 시각 자료로 관리한다.
- 공통 ADR·날짜별 워크로그의 원본을 유지하고 작업별 판단·조사 문서에서는 링크한다. 모든 작업에 ADR·실행 계획을 새로 요구하지 않는다.
- 기존 이관을 유지하면서 진입점 복구, 기록 절차, 공유 문서와 예시, 문서 검사, CI 연결, 최종 검증의 순서를 정리했다.

### 실행한 진단

- 브랜치 `refactor/#330-document-harness`와 기존 미커밋 변경을 확인했다. 로컬 HEAD·`origin/dev`는 `e5a1b66bf3b06a971b1242dd02bd623e717c2902`다.
- 계획 파일 추가 전 `.venv-api/bin/python scripts/check_docs.py`를 실행했다. 문서 18개 중 `AGENTS.md`의 옛 경로 링크 19개가 오류로 보고되어 종료 코드 `1`이었다.
- 이슈 #330의 목표·완료 조건과 로컬 가이드·검사기·CI 정의를 대조했다. 문서 검사기 회귀 테스트와 하네스 구현 전체의 검증은 이번 계획 수립에서 실행하지 않았다.
- 계획 작성 후 관련 문서 7개의 로컬 링크·공백 검사는 오류 0개였다. 구조 MD·HTML의 80개 항목과 주석이 일치했다.
- 전체 문서는 22개로 늘었으며 검사 결과는 여전히 종료 코드 `1`, `AGENTS.md`의 기존 링크 오류 19개였다. 새 계획 문서의 검사 통과와 전체 하네스 상태를 구분한다.
- Orca 브라우저에서 구조도의 작업 폴더·계획 연결을 확인했다. 390px 화면에서 새 작업 폴더의 설명이 가로 넘침 없이 표시되는지 확인하고 데스크톱 화면으로 복원했다.

### 남은 작업과 범위

첫 구현 단계는 `AGENTS.md`의 끊긴 링크와 읽기 경로를 복구하는 일이다. 이후 기록 작성 조건, 요구사항의 검증 근거 표현, 검사기와 CI 선택을 순서대로 연결한다.

서비스 업무 코드와 API·이벤트 계약은 변경하지 않았다. Java 빌드·외부 DB·Kafka·원격 CI·팀원별 에이전트 동작은 미확인이다. 커밋·푸시·PR·병합·배포는 진행하지 않았다.

- 임시 계정은 실행 프로세스 환경으로만 전달하고 자격증명을 로그/저장소에 남기지 않았다. Docker가 loopback 가용 포트를 선택하게 했고 증거는 Git 제외 build/product-validation에 보존했다. 각 실행은 자기 이름/라벨의 컨테이너만 제거하고 제거 여부를 확인했다.
- 첫 실제 PostgreSQL 실행은 20건 중 19건 통과·공유 잠금 경합 1건 실패였다. 실제 SQL은 FOR SHARE였지만 테스트 pool 3개를 두 주문+제어가 사용해 pg_locks 관측 연결이 대기했다. PostgreSQL 테스트에만 관측용 연결을 포함한 pool 4를 지정하고 실제 JPA backend PID와 writer 조기 종료를 함께 확인했다. 준비 상태 확인도 임시 서버의 pg_isready 대신 대상 DB TCP SELECT 1로 보완했다.
- 보완 후 공유 잠금 경합 단독 1건, 전체 PostgreSQL 20건(Core 업무13·V101 이행1·Catalog 업무4·스키마2)이 실패/오류/스킵 0으로 통과했다. 두 공유 잠금 공존, 전체 중지/삭제의 잠금 대기와 후속 신규 거래 거절, 같은 컨텍스트의 앞선 일반 조회 최신화, 원자성·중복/역순·삭제 보존을 확인했다. 자기 컨테이너 제거도 확인했다. 이 결과는 전용 로컬 PostgreSQL이며 운영 DB/외부 Kafka 실행이 아니다.
- Order 검토 msg_3966323c163a 후 신규 Product API 3매핑과 제어 응답 필드·예시를 제한 적용했다. 빈 security 배열을 없애 루트 BearerAuth를 상속하고 SELLER 역할을 명시했다. 기존 GET/PATCH/path parameters와 다른 모듈 경로는 보존했다. Catalog reason 확장만 반영했다.
- API 구조 6개 서비스/122매핑, Product 응답 예시 10개 JSON Schema 검사가 통과했다. API HTML 6개를 재생성했으며 Live HTML도 기존 Core 외부 참조에 따라 함께 갱신됐고 Live 코드/계약 원본은 변경하지 않았다. Core API HTML에서 sale-state 검색 1/58, 펼친 요청·200 예시·BearerAuth/SELLER, 1280px/390px 가로 넘침 없음을 확인했다.
- Product는 SKU/Order를 역merge하지 않는다. 다중 SKU Product 조회 변경 조각/검증 기준은 #334에서 적용하도록 배정됐고 Product 페이지의 N+1 방지를 위해 실제 SKU productIds 일괄 조회 포트를 소유자에게 요청했다. 임의 SKU 타입/테이블 접근 포트는 만들지 않는다.
