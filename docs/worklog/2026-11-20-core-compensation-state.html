보상 실패는 완료가 아니다. 기존 terminal-intent guard를 시스템 FAILED에 한해 해제했으며 새 요청ID나 실행ID를 만들지 않는다. 동일버전 다른 원문, 실행ID 변경, 완료 뒤 더 높은 모순 결과는 계속 거절한다. 이미 검증한 낮은 FAILED/UNKNOWN 재전달은 무효과로 기억한다. 완료 시 PG 거절을 뜻하는 PaymentFailed나 가짜 알림을 합성하지 않는다.

호출 경로·원자성

PaymentRelayDispatcher의 승인 HTTP 통신 예외/의미 불명 HTTP 실패는 pending 전달 이력만 남긴다. OrderSheetLifecycleService.expire는 신규 주문서의 PAYMENT_CONFIRMING 처리 기한에서 일반 만료 대신 KafkaRefundService.compensateLocked로 진입한다. 명시적 UNKNOWN도 같은 경로로 들어간다. 구매 guard→그룹 잠금 아래 상태·항목·고정 원문·Outbox를 커밋하며 외부 HTTP 동안 DB 잠금을 유지하지 않는다. 기존 approval_send_started_at 송신 시작 fence와 영속 보상 fence를 유지한다.

OrderPaymentResultApplier.completeCompensation은 COMPENSATION_PENDING에서 CANCELLED로만 확정한다. 일반 결제 거절의 FAILED/알림과 분리한다. 보상 대기는 활성 조회와 새 구매 차단에도 포함하며 API 그룹/항목 enum에 노출한다. Frontend는 새 COMPENSATION_PENDING을 처리 중 보상 상태로 표시해야 하며 Frontend 파일은 수정하지 않았다.

V115는 변경하지 않았다. 새 V116은 CHECK·활성 회원 유일 인덱스를 확장하고, 기존 미완료 보상을 가진 진행 중 policy1 주문만 원문·ID·버전·재고 예약을 보존하여 대기로 이행한다. 이미 종료한 주문은 유지한다.

공통 토픽과 소비 검증 경계

사용자/시스템 요청은 모두 commerce.refund.requests.v1, 결과는 모두 payment.refund.results.v1이다. 두 토픽의 key는 처음부터 존재하는 orderRef(groupNumber)로 같으며 payload purpose만 신뢰하지 않고 refundRequestId로 찾은 저장 원문의 목적·대상·금액·수량·시각·ID를 대조한다. Core 생산 요청 계약의 필드 의미 변경은 없어 이번 증분에서는 보존했다. Payment 담당 결과/실행 계약은 수정하지 않았다. 테스트 결과 형태는 Core 소비자가 기대하는 fixture이며 상대 producer 구현의 증거가 아니다. 기존 legacy 호환 소비 경로는 변경하지 않았다.

RECORD ack·무한 backoff 오류 처리를 유지한다. 불일치/미등록 결과나 로컬 반영 장애는 예외로 전파하여 성공 ack하지 않고 결과 원장을 확정하지 않는다. broker 재전달·실제 offset은 이번에 실행하지 않았다.

원요청에 paymentId가 없고 결과가 새 ID만 제공하면 기존 검증된 binding이 없는 한 거절·보류한다. 현재 Payment GET 필드만으로 구매자·판매자 원문을 안전하게 확인할 수 없으므로 연결 복구 결함은 미해결이다. 새 필드를 Mock에 만들거나 이벤트 ID를 신뢰해 연결하지 않았다. 진짜 ID 없는 NO_CHARGE 완료는 계속 지원한다.

실제 검증

Java21, 기존 C 전용 PostgreSQL 127.0.0.1:25434/core_refunds_c의 매번 분리된 schema를 사용했다. DB/user를 실제 SQL로 대조하고 테스트 schema만 정리했다. 비밀번호는 프로세스 환경으로만 전달했고 문서/인계물에는 저장하지 않는다. Docker 명령·공용 컨테이너·새 스택·다른 서비스 프로세스를 사용하지 않았다.

미실행과 남은 문제

Payment 실제 실행/PG·Toss·조회 대사·결과 producer, 실제 서비스 연결, 공통 환불 Kafka 전달/offset 재전달, 외부 Kafka2검사는 미실행/스킵이며 성공으로 보고하지 않는다. missing-paymentId binding 복구, 별도 시스템 완료 알림, 타팀의 결과 생산 계약·구현은 후속이다. 기존 policy0 legacy 흐름을 새 시스템 보상 흐름으로 전면 이행하지 않는다.

시작점 전체1242파일 중 허용 밖841파일의 hash와 status를 종료 시 대조하고 Payment 경로는 baseline clean임을 확인한다. 원래 A/frozenC/중지된 binding/다른 공간 산출물은 적용하거나 수정하지 않는다. 이번 증분만 별도 patch·신규 archive·before/after hash·receipt로 전달하며 전체 작업은 미커밋 상태다.
