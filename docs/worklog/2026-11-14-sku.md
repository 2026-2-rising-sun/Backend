## 변경

0b36ba47·clean에서 시작해 Product729d2d5f를 일반 merge1b9b4d5b로 통합했다. 문서 충돌에서 양쪽 작업을 보존하고 생성 HTML을 재생성했다. 다른 워크트리·FigJam과 기존 적용 SQL은 변경하지 않았다.

SalesController 등록·가격·재고·상태·재고조회와 배치 판매조회, Product 단일 판매조회는 SKU 원본으로 전환했다. 본인·미삭제 Product 검증/잠금, 기본 등록 중복 경합, 같은 트랜잭션 SKU·Outbox, ID순 잠금·수량 조건부 UPDATE를 사용한다. Product 페이지를 먼저 계산하고 SKU 일괄조회·페이지 전 EXISTS 상태필터를 적용해 상품 건수와 offset을 유지한다. 판매자 내부 listSkus는0..N개를 반환한다.

상품 전체 중지/재개는 SKU 상태·수량을 바꾸지 않는다. 기존 완료·해제·복구는 Product 신규 거래 조건을 다시 요구하지 않는다. 외부 enum/필드는 유지하며 ON_SALE+available0만 SOLD_OUT으로 파생한다. READY 수동 복귀는 없다. 단일 응답에서 복수 SKU는 Core409/Catalog503으로 구분한다.

## 검증과 실패 처리

전용 PostgreSQL16 컨테이너에서 V102 이행3건·SKU/Product연계 및 동시선점8건·CatalogV3 이행1건을 실패/오류/스킵0으로 실행했다. 기존 ID·가격·수량·버전/시퀀스 보존, 모순상태/재고누락 거절, Outbox 실패 롤백, 상품삭제 후 기존 수량처리, 재고5의 동시10요청 선점5개를 확인했다. 자기 컨테이너만 생성/삭제하고 제거를 확인했으며 자격증명은 프로세스 환경에만 전달했다.

최초 연결검사 실패는 실제 Product/판매자 fixture 누락과 H2 enum의 파생 SOLD_OUT 표현이었다. fixture를 실제 원본에 맞추고 SKU sale_status의 JPA VARCHAR 매핑을 V102와 맞췄다. 추가 SKU연계 테스트의 테스트 보안 설정 누락, 기대 예외 타입과 Outbox 실패주입 제약의 기존 행 충돌을 수정했다. 뒤이은 전체회귀의 HTTP5건은 구 Sales fixture를 실제SKU로 전환했다. 0재고 판매시작 회귀의400/409 기대는 채택 기술안에 따라 ON_SALE 저장·SOLD_OUT 응답과 available0 보존으로 검증한다. 수량·롤백·멱등성 검사를 약화하거나 스킵하지 않았다.

문서120개 링크 오류0, 설계HTML28·API HTML6 최신성과 API6서비스122매핑·이벤트7계약22예시 정적 검사를 통과했다. 이 정적 검사는 실제 응답/브로커 전달을 대신하지 않는다. SKU ERD·상태 HTML은 기존 MD 생성기로 만들고 Orca browser1280×900/390×844에서 글·도표·필터·문서지도 링크·콘솔을 확인했다. 본문 가로넘침은 없고 좁은 도표만 내부 스크롤한다. READY 필터3/7·ERD SKU연관2/4와 복원을 확인했다. 개인 HTML 기준과 frontend-design 지침을 읽었으며 개인 설정 경로는 프로젝트에 복사하지 않았다.

최초 전체 회귀는 Core단위152·통합294(외부Kafka2스킵), Catalog단위12·통합82, 실패/오류0이었다. 이어서 저장소 전체하네스는 Gradle build자체종료0/2분10초였고 정적검사도 통과했지만 외부Kafka/Notification스킵과 외부DB미실행으로exit2/incomplete였다. 검사중diff변경은없었다. 이때event-samples는선행스킵때문에not-run이다.

후속정적대조에서SKU기본등록이캐시된Product의옛version으로배타잠금을먼저요청하는문제를새테스트로재현했다(OptimisticLockException). 일반조회뒤다른트랜잭션의전체허용변경이완료된상황이다. Product포트와같이refresh(PESSIMISTIC_WRITE)로잠금·최신화를함께수행해수정했다. 최종전용PostgreSQL은SKU업무11·V102이행3·CatalogV3이행1·Catalog사본업무9, 총24건모두실패/오류/스킵0이었다. 같은Catalog저장소테스트의H2 9건도통과했다. 새페이지/전체제어/캐시최신화·동시등록/선점·Outbox롤백을포함한다. 전용컨테이너제거를확인했다. 최종소스의전체하네스/원격CI는PR과최종인계보고에서확인한다.

## 남은 경계

공개 다중 SKU 생성/판매자 HTTP목록·고객 옵션선택·상품별 공개skus[]·대표가·새 가격정렬·Live 다중SKU는 미완/보류다. 옵션JSON 상세·별도예약테이블·가격이력을 임의 추가하지 않았다. 상품·SKU 내부1:N 저장/조회와 거래 수량기반을 전체 공개흐름 완료로 보고하지 않는다.

기존 SalesService/RegistrationService·sales_info/sales_stock은 전환 전 Order호환/이력으로 남는다. 후행 Order는 신규 주문식별·거래와 완료/해제/보상을 SKU로 연결하고 과거참조를 보존한다. Core API 원본 최종 편집자에게 [API 조각](../exec-plans/active/334-sku-module/api-changes.md)을 전달했고 Catalog 판매 설명은 SKU에서 갱신했다. V102/V3와 통합순서는 코디네이터 기술배정이다. 이 중간 브랜치만 독립 배포하지 않으며 병합/배포는 하지 않는다.


## 최종 소스 검증과 PR

소스 커밋 `1a09aacd8a4413b1ad64b1987335e67ad4dd695e`를 push한 뒤 `scripts/check.sh --base 729d2d5f`를 다시 실행했다. Gradle 전체 build는 종료0·3분3초, Core 단위152/통합295·Catalog 단위12/통합82에서 실패/오류0이었다. Core 외부 Kafka2건과 Notification 비활성3건이 스킵되어 하네스는 exit2/incomplete이며 검사 중 diff 변경은 없었다. 기본 빌드의 성공을 스킵/외부 미실행 성공으로 보고하지 않는다.

문서121개·API122매핑·API HTML6/설계 HTML28 최신성·이벤트7계약22예시는 통과했다. event-samples는 선행 스킵 때문에 자동 실행되지 않았고 선택된 전체 migration/postgres 작업은 기본 실행에서 미실행이다. 별도로 실행한 전용 PostgreSQL24건·Catalog H2 9건의 결과와 구분한다. Live/Payment 전체 외부 DB·Redis·PG/AWS·운영 환경은 이 작업에서 검증하지 않았다.
