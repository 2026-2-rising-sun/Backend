Core Outbox CDC와 Catalog 상품·SKU·60초 재고 동기화

실행일:2026-11-19~20(KST).

기준과 소유 경계

Backend 기준 3537340c4686fec3b962da8ed02d368829d639af, 작업 브랜치 catalog-cdc-sync. 시작 당시 미커밋 변경이 없었다. 승인된 A 계약 patch와 신규23파일을 해시/적용 가능성 확인 뒤 상속했다. A 원본 계약·문서는 수정하지 않았다. B는 common-module Outbox, Core Product/SKU/Sales와 Core application.yml, Catalog/API/관련 문서·테스트만 변경했다. 주문·결제 상태·환불 업무, Frontend, Infra와 다른 체크아웃은 수정하지 않았다. 커밋·푸시·PR·병합·배포는 하지 않았다.

구현 결과

  • 상품 metadataVersion(JPA version, 최초0) 전체 스냅샷은 업무 TX에서 commerce.catalog.snapshots.v1 Outbox로 즉시 기록한다. 상품명·설명·이미지·판매자·판매 제어·삭제·initialSkuCount를 포함한다. timestamp는 flush 후 DB 값으로 읽어 재적재 원문 정밀도를 맞춘다.
  • SKU 가격/판매의도는 독립 metadata_version과 영속 변경시각으로 즉시 Outbox에 저장한다. Product 참조 버전도 메타데이터 변경 때 저장해 재적재 시 바꾸지 않는다.
  • 예약·소진·해제·환불 복원·판매자 수량 수정의 공통 SQL에서 inventory_version을 증가시킨다. 호출자에게 dirty-marker API를 추가하지 않았다. 수량마다 Catalog Outbox를 쓰지 않고 기본60초 주기에 SKU별 최신 한 건을 합친다.
  • 배치는 ID순 FOR UPDATE SKIP LOCKED로 다중 인스턴스의 대상을 선점한다. 스냅샷 Outbox와 inventory_published_version 완료표시는 한 TX다. 동시 변경은 잠금 뒤 새로운 dirty revision으로 남고, Outbox 실패·중단은 롤백/재시작 재처리한다. capturedAt은 영속 inventory_changed_at을 재사용한다.
  • 초기 적재는 commercecore.catalog.backfill.enabled=true인 명시적 기동으로 Product 공유잠금→SKU ID순 잠금을 사용한다. 삭제 이력과 세 스냅샷을 같은 버전으로 재적재한다. 범위별 서비스 포트도 유지한다.
  • 공용 Outbox의 excluded-topics 기본은 빈 목록이다. Core만 Catalog 토픽을 제외하며 일반 JPA 조회와 lease/claim SQL이 모두 배제한다. 다른 서비스 기본 relay와 필요한 sales-info/주문/쿠폰/Live 알림은 유지하고 CDC 장애 fallback/행 TTL 삭제는 추가하지 않았다.
  • Catalog 공통 리스너는 봉투·source·schemaVersion·eventType·UUID·key/ID·필수 필드·타입을 확인하고 상품/SKU metadataVersion과 inventoryVersion을 독립 적용한다. 같은 revision의 원문 충돌 및 eventId 재사용을 거절한다. JSON 중복 키·후행 JSON도 허용하지 않는다.
  • Catalog의 aggregate 행 잠금과 receipt/상태/공개 사본 갱신은 같은 TX다. SKU·재고 선도착은 영속 보관하고 두 SKU 영역이 모여야 product_sales를 만든다. Product가 없으면 공개 JOIN에서 숨는다. 삭제 fence는 재시작·높은 생존 버전·재고 메시지로 부활시키지 않는다. 다중 SKU 단일값 API503 보호를 유지한다.
  • Catalog API2.1.0은 available/salesStatus를 표시 사본으로 보존하며 사본 수량만으로 PurchaseCheck를 SOLD_OUT/EXCEEDS_STOCK으로 거절하지 않는다. purchasable/orderable은 Core 확인 진입 표시이고 구매 승인이 아니다. 실제 가격·재고는 Core가 확정한다. Frontend의 현재 차단과 수용 기준은 전용 인계에 남겼다.

실행 환경과 검증

Java21, Gradle Wrapper, H2 및 EmbeddedKafka 검사와 독립 Lima PostgreSQL16 검사를 구분했다. Python 검사는 기존 API 가상환경을 읽기 전용으로 사용했다. B PostgreSQL은 127.0.0.1:25433의 전용 DB와 테스트마다 고유 schema를 사용했다. 다른 DB/볼륨/클러스터 초기화·종료나 Docker context 변경은 하지 않았다. 실제 PG 결제와 운영 환경 검증은 없다.

이6개 외부 Gradle 작업은 하네스에 --external과 연결 설정을 주지 않아 실행되지 않았다. E는 각 서비스의 독립 DB/schema를 먼저 확인하고 현재 통합 diff에서 scripts/verify.py --dry-run으로 선택을 갱신한 뒤 필요한 외부 검사를 실행해야 한다. 위 별도 B 검사로 전체 외부 선택을 통과했다고 대체하지 않는다.

스킵5건도 별도로 해소하거나 미실행으로 남겨야 한다. Core의 두 외부 Kafka 테스트는 E 전용 broker/topic/group을 준비하고 해당 환경변수를 주입해 integrationTest --tests '*SalesInfoEventKafkaTest' --tests '*CouponSyncKafkaTest' --rerun-tasks로 재실행한다. Notification 동시성3건은 독립 Notification PostgreSQL 설정으로 integrationTest --tests '*ConcurrentInsertPostgresTest' --rerun-tasks를 실행한다. 새 쿠폰 동기화 기능을 추가하라는 뜻은 아니며 기존 전송 경계 회귀다.

E의 서비스 간 게이트는 실제 앱 변경→Core DB/Outbox→연속 CDC→Kafka→Catalog 소비·조회와 사용자/시스템 환불→Payment PG 대역→Core 결과 적용, 알림/Live 보존이다. 실제 PG/운영 검증으로 확대하지 않는다. I 별도 인프라 전체 smoke의 broker 재시작/최종 확인은 I dependency 완료를 기다린다.

PostgreSQL 명령은 COMMERCECORE_TEST_POSTGRES_*, CATALOG_TEST_POSTGRES_*를 B 전용 DB로 주입한 뒤 다음 선택을 실행했다. 자격값은 기록하지 않는다.

./gradlew :services:commercecore-service:postgresTest \
  --tests '*sku.event.CatalogSnapshotPostgresTest' \
  --tests '*sku.service.SkuSalesPostgresTest' \
  :services:catalog-service:postgresTest \
  --tests '*snapshot.CatalogSnapshotPostgresTest' \
  --continue --max-workers=2 --console=plain

전체 하네스 후 추가한 것은 기존 데이터 migration 검사, Kafka 테스트의 조회 준비 확인, 미실행 외부 Kafka 회귀의 판매 알림 기대값7→5 정렬과 문서 인계다. 해당 migration1건·Kafka1건, 판매 알림 H2 회귀8건(실패/스킵0)과 문서/포맷 검사를 별도로 재실행했다. 외부 Kafka 회귀의 수정은 컴파일됐으나 환경변수 미설정 조건부 실행을 통과로 표시하지 않는다. 하네스의 전체 외부 선택이나 최종 서비스 간 CDC·환불 통합을 완료했다는 의미는 아니다.

앞선 실패와 재검증

초기 공용 설정의 다중 생성자 바인딩, H2 테스트용 SKU 열/producer 주입 누락, 새 토픽·순수 재고 Outbox 제거에 따른 기존 기대값, serializer H2 연결 수명 오류를 검사 실패로 기록하고 수정했다. 앞선 common 전체 통합 검사에는 JSON 로깅 회귀2건 실패도 있었으나 최종 전체 실행의 common60건에서 실패0을 확인했다. 이를 초기 실행부터 통과한 것으로 합산하지 않는다.

첫 PostgreSQL 실행은 Core21건 중 테스트 spy reset의 제네릭 varargs 형변환 오류6건으로 실패했다. 형변환을 명시해 재실행한 Core21/Catalog6건은 모두 통과했고, 상품 시각/삭제 재적재1건을 추가한 최종 Core22/Catalog6건도 실패·스킵0으로 통과했다. Core의 원자성·claim·경합 시나리오와 Catalog의 독립 버전·원문·선도착·삭제/동시 소비 시나리오를 실제 PostgreSQL에서 확인했다.

Desktop 전용 DB 기동 시도는 포트25432 중복/비실행 상태로 확인돼 접속·초기화·재시작하지 않았다. 조정자가 실제 health를 확인한 Lima25433을 받은 뒤에만 DB 검증을 재개했다. 앞선 환경 미실행을 DB 통과로 보고하지 않는다.

전체 이벤트 직렬화 표본 검사는 상속받은 새 환불 계약에 기존 Core 환불 표본의 purpose 등이 없어 실패한 별도 실행이 있다. 이는 C/D 적용 전 상태로 B가 수정하지 않았다. B의 실제 세 DTO 표본은 A Catalog 스키마에 별도로 검증해3건 통과했다. 통합 후 전체 환불/결제 표본 대조는 E가 수행해야 한다.
