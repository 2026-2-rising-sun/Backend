# 문제 고친 내용 위치
1 1차 승인 결과 불명 → 2차 재호출이 연결 실패면 CREATED로 되돌림. 1차가 이미 승인됐다면 재결제가 가능해진다 한 번이라도 불명을 받은 시도는 CREATED로 되돌리지 않고 UNKNOWN으로 두어 조회로 확정 338 §2 ③
2 승인 반영 UPDATE가 0행이면 그냥 끝냄. 조회기가 먼저 CREATED로 돌린 뒤 DONE이 오면 돈만 빠지고 기록이 없음 0행이면 다시 읽음. APPROVED면 끝, 그 밖이면 ERROR 로그 + 보상 취소 338 §2 ③
3 보상 취소 대상 paymentKey가 DB 값인지 응답 값인지 불명. 트랜잭션 경계 없음 취소 대상은 토스 응답의 paymentKey. pg_call 먼저 기록 → 트랜잭션 밖 호출 → CANCELED 338 §2 보상 취소

# 문제 고친 내용 위치
4 FORBIDDEN_CONSECUTIVE_REQUEST를 "보내지 않음"으로 분류. 앞선 요청이 처리 중일 수 있음 "불명"으로 옮김(요구사항 PAY-PG-02에도 추가) 338 §1 분류표
5 검증 순서가 요구사항과 다름. 처리 중 상태에 옛 결제창이 오면 202 요구사항 순서로 맞춤. STALE_CHECKOUT은 상태와 관계없이 먼저 검사 338 §2 ①
6 거절 뒤 같은 결제창으로 재승인하면 멱등 키가 재사용되어 토스가 첫 거절을 돌려줌 CREATED로 돌릴 때 pg_order_id = NULL. 다음 승인은 STALE_CHECKOUT → 새 결제창 338 §2 ③, 349 조회 결과표
7 본문이 깨진 4xx가 "거절", 200인데 DONE이 아닌 응답이 보상 취소로 감 둘 다 "불명"으로 분류해 조회로 확정 338 §1 분류표
8 ADR 0337-5 "크기를 제한한 스레드 풀"과 설계(가상 스레드, 제한 없음)가 충돌 ADR 본문에 정정 메모(벌크헤드 없음) ADR 0337-5
9 422 응답 모양이 요구사항과 다름 요구사항의 {status, code, message}를 data에 그대로 담음 338 §2 응답 예시
10 #347이 지우는 계약 테스트를 #338이 재사용한다고 씀 #338에서 PaymentApprovedContractTest를 새로 만듦 338 테스트
11 보안 테스트가 /actuator/health 200을 기대. 실제는 403 기존대로 liveness·readiness 200 347 남길 것
12 orderRef 형식을 @Pattern으로 달면 오류 코드가 충돌 형식은 Bean Validation 밖에서 검사 → INVALID_ORDER_REF 348 생성 API 입력
13 ON CONFLICT (컬럼) 형태는 H2에서 확인되지 않음 충돌 대상을 생략한 형태로 통일 348 동시 생성, 338 원장
14 서버가 토스 호출 전에 죽으면 마감까지 IN_PROGRESS로 남고 처리 방법이 없음 마감 뒤에는 사람이 확인. 로그 형식을 정함 349 마감 처리
