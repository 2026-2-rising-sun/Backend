#338 토스 결제 승인과 원장 분개

상태: 설계 확정(2026-11-15) 이슈: #338 · Phase 문서: Phase 1 결제 1차 · 스키마: #348 설계

개요

끝나면 Commerce가 중계한 승인 요청을 Payment가 검증하고, 토스 승인을 한 번만 호출하고, 결과를 상태·원장·이벤트에 한 트랜잭션으로 남긴다. 토스 응답이 8초 안에 없으면 202를 먼저 돌려주고 처리는 계속한다. 결과를 모르면 UNKNOWN으로 두고 #349가 확정한다. 이 이슈의 "승인 반영" 함수(applyDone)를 #349가 그대로 쓴다.

원장 서비스 LED-01–05, LED-APPROVE-01(분개 내용은 승인 처리 PR에서 호출·검증)
토스 클라이언트 PAY-PG-01–04
승인 처리(서비스) PAY-CONFIRM-01–10, 12, PAY-EVENT-01–02

하지 않는 것: 결과 불명 조회·정체 스위퍼·만료(#349), 환불(Phase 3), 웹훅, 동시 호출 수 제한.

1. 토스 클라이언트 (client.toss)

설정 (제안 이름)

키 환경 변수 기본값 의미
payment.toss.base-url PAYMENT_TOSS_BASE_URL https://api.tosspayments.com
payment.toss.secret-key PAYMENT_TOSS_SECRET_KEY 빈 값 테스트 키 test_sk_…. 로그·예외 메시지에 남기지 않는다. 비어 있으면 기동하고 WARN 로그 한 줄을 남긴 뒤, 모든 호출을 보내지 않고 NotSent로 돌려준다(2026-11-15 사용자 결정)
payment.toss.connect-timeout — 3s PAY-PG-01
payment.toss.read-timeout — 60s PAY-PG-04. 헤더와 본문을 합친 응답 대기다. JDK 요청 타임아웃은 헤더까지만 막으므로 호출 전체에 connect-timeout + read-timeout 데드라인을 두고, 넘으면 Unknown이다

HTTP 클라이언트는 Spring RestClient(+ JDK HttpClient 요청 팩토리)로 만든다. 공통 ServiceRestClientFactory는 내부 서비스용이라 쓰지 않는다. Boot가 주입하는 RestClient.Builder도 쓰지 않는다. 공통 커스터마이저가 내부 요청 ID(X-Request-Id) 같은 헤더를 붙이기 때문이다. 외부 PG에는 토스 헤더만 보낸다.

결과 분류 TossResult

Success(payment) · Declined(code, message) · NotSent(reason) · Unknown(reason) 네 가지다. 위에서부터 처음 맞는 줄로 고른다.

상황 결과 근거
시크릿 키 미설정(호출하지 않음) NotSent PAY-PG-01
연결 타임아웃, 연결 거부(요청을 보내기 전 예외) NotSent PAY-PG-01
읽기 타임아웃, 응답 중 끊김, HTTP 5xx, 분류하지 못한 예외 Unknown PAY-PG-03. 애매하면 불명
HTTP 401 (UNAUTHORIZED_KEY), HTTP 429 NotSent 우리 키 문제, 호출 제한. 상태 코드만 본다(본문 code 불필요)
HTTP 4xx인데 본문에서 code를 읽지 못함 Unknown 무엇이 거절됐는지 모른다
HTTP 400 INVALID_API_KEY, HTTP 403 + code ∈ {INCORRECT_BASIC_AUTH_FORMAT, API_KEY_ACCESS_DENIED} NotSent 우리 키·설정 문제
HTTP 400 + code ∈ {ALREADY_PROCESSED_PAYMENT, ALREADY_PROCESSING_REQUEST}, HTTP 403 FORBIDDEN_CONSECUTIVE_REQUEST, HTTP 409 IDEMPOTENT_REQUEST_PROCESSING Unknown PAY-PG-02. 앞선 요청이 처리 중일 수 있다. 409는 같은 멱등 키 요청이 처리 중이다(토스 멱등 키)
그 밖의 HTTP 4xx (카드 거절 403 REJECT_CARD_COMPANY 등 포함) Declined(code, message) PAY-PG-02
HTTP 200, 본문 status가 호출별 기대 상태 Success(payment) 값 검증은 ③에서
HTTP 200, 본문 파싱 실패 또는 status가 기대 상태가 아님(IN_PROGRESS 등) Unknown 조회로 확정한다. 보상 취소로 보내지 않는다
그 밖의 HTTP 상태(1xx·3xx·200이 아닌 2xx) Unknown 분류하지 못한 응답

200의 기대 상태는 호출마다 다르다. confirm은 DONE, cancel은 CANCELED(전액 취소)다. getPayment는 본문만 읽히면 어떤 status든 Success로 돌려주고 판단은 호출자(#349의 PAY-RECOVER-02–03)가 한다. 4xx·5xx·예외 줄은 세 호출에 같게 적용한다.

요구사항 수정: 기존 PAY-PG-01은 "401·403·429는 보내지 않음"이었다. 토스 승인 API는 카드 거절 대부분(REJECT_CARD_PAYMENT, REJECT_CARD_COMPANY, FDS_ERROR 등)을 403으로 준다(토스 오류 코드, 2026-11-15 확인). 그대로 두면 카드 거절이 "결제사 연결 불가"로 보인다. 403은 위 2개 코드만 "보내지 않음"으로 보도록 요구사항 문장을 이 PR에서 함께 고친다. 돈 쪽 결과는 같다(둘 다 CREATED로 돌아간다). 바뀌는 것은 응답 코드(503 → 422)뿐이다.

2. 승인 처리

입력

POST /v1/internal/payments/{orderRef}/approval

필드 의미 형식·제약 예시
경로 orderRef 결제 찾기 키 #348 형식 OD-20261110-K7Q2M9XA
buyerId Commerce가 로그인 토큰에서 꺼낸 구매자 필수, UUID
paymentKey 브라우저가 받은 토스 paymentKey 필수, ≤ 200자 tgen_…
pgOrderId 브라우저가 받은 토스 orderId 필수, ≤ 64자 OD-20261110-K7Q2M9XA-1
amount 브라우저가 받은 금액 필수, ≥ 1 30000

순서와 트랜잭션

① 트랜잭션 A (검증 + 시작)        ② 트랜잭션 밖 (가상 스레드)        ③ 트랜잭션 C (반영)
   검증 → CREATED→APPROVING          토스 confirm (같은 키로 1번 더)      결과별 반영 + pg_call 결과
   pg_call(CONFIRM, UNKNOWN) INSERT  재호출이면 그 전에 pg_call 1행 INSERT  (+ 분개 + outbox)
   커밋                                                                 커밋
요청 스레드: ②③을 가상 스레드에 맡기고 최대 8초 기다린다. 끝나면 결과 응답, 아니면 202.

① 검증 (요구사항 순서. 처음 걸린 하나만 응답)

# 검사 실패 응답 토스 호출
1 orderRef로 결제 찾기 404 PAYMENT_NOT_FOUND 안 함
2 pgOrderId의 마지막 - 앞부분 = orderRef 400 ORDER_ID_MISMATCH 안 함
3 buyerId = buyer_id 403 BUYER_MISMATCH + WARN 보안 로그 안 함
4 amount = amount 400 AMOUNT_MISMATCH + WARN 보안 로그 안 함
5 pgOrderId ≠ 현재 pg_order_id(현재 값이 NULL이어도) 409 STALE_CHECKOUT (PAY-CONFIRM-02) 안 함
6 상태: APPROVED → 200(같은 응답 반복), APPROVING·UNKNOWN → 202, CANCELED·PARTIALLY_REFUNDED·REFUNDED → 409 PAYMENT_CLOSED 안 함
7 CREATED인데 expires_at ≤ now() 409 PAYMENT_CLOSED (PAY-CONFIRM-03) 안 함

요구사항 순서(01 → 02 → 03)를 따른다. 다만 만료 검사(7)는 CREATED에만 한다. 이미 승인된 결제는 만료 시각이 지나도 새로고침에 200을 줘야 하기 때문이다(PAY-CONFIRM-05).

검사를 통과하면 조건부 UPDATE로 시작한다. 동시 요청은 여기서 한 건만 1행이 된다(PAY-CONFIRM-05).

UPDATE payment
   SET status = 'APPROVING', approving_at = now(), pg_payment_key = :paymentKey, updated_at = now()
 WHERE id = :id AND status = 'CREATED' AND pg_order_id = :pgOrderId
   AND amount = :amount AND buyer_id = :buyerId AND expires_at > now();
-- 0행: 다시 읽어 표 5–7로 응답(경합에서 진 요청)
-- 1행: 같은 트랜잭션에서 pg_call(kind=CONFIRM, outcome=UNKNOWN, idempotency_key=confirm-{pg_order_id}, requested_at=now()) INSERT

pg_payment_key UNIQUE 위반(다른 결제가 이미 쓴 paymentKey)은 정상이라면 생기지 않는다. 400 INVALID_REQUEST + WARN 보안 로그로 거절한다.

② 토스 호출 — 트랜잭션 밖. confirm이 Unknown이면 같은 키로 1번 더 부른다(PAY-CONFIRM-10). 두 번째 호출도 pg_call 1행을 남긴다(① 이후 ③ 전에 별도 짧은 트랜잭션으로 INSERT).

한 번이라도 Unknown을 받은 시도는 CREATED로 되돌리지 않는다. 첫 요청이 토스에 닿았을 수 있기 때문이다. 두 번째 결과가 Success면 그대로 반영하고, Declined·NotSent·Unknown이면 모두 아래 표의 Unknown 줄로 처리해 조회로 확정한다. 아래 표의 Declined·NotSent 줄은 첫 호출의 결과일 때만 쓴다.

③ 반영 (PaymentOutcomeService, 결과마다 한 트랜잭션)

결과 상태 변경(조건부 UPDATE) 함께 쓰는 것 승인 API 응답
Success + 응답 검증 통과 APPROVED, approved_at, pg_status, partial_cancelable · WHERE id AND status IN ('APPROVING','UNKNOWN') 분개(아래), outbox PaymentApproved, pg_call SUCCESS 200 {paymentId, status: APPROVED}
Success + 응답 검증 실패 아래 "보상 취소" pg_call SUCCESS + CANCEL 행, ERROR 로그 409 PAYMENT_CLOSED
Declined(첫 호출) CREATED, approving_at = NULL, pg_order_id = NULL · WHERE id AND status = 'APPROVING' pg_call DECLINED + result_code 422 DECLINED
NotSent(첫 호출) 같은 변경 pg_call NOT_SENT 503 PG_UNAVAILABLE
Unknown, 또는 재호출 뒤 Success가 아닌 모든 결과 UNKNOWN, next_check_at = now() + 10s, check_deadline_at = now() + 30m · WHERE status = 'APPROVING' pg_call UNKNOWN 유지 202 {paymentId, status: PENDING}
  • 응답 검증(PAY-CONFIRM-06): status = DONE, orderId = pg_order_id, totalAmount = amount, paymentKey = 보낸 값. 하나라도 다르면 실패다.
  • CREATED로 되돌릴 때 pg_order_id를 NULL로 비운다. 같은 pgOrderId로 다시 승인하면 멱등 키 confirm-{pg_order_id}가 재사용되어 토스가 첫 거절 응답을 돌려줄 수 있다. 비워 두면 그 요청은 409 STALE_CHECKOUT이 되고, Commerce는 POST …/checkouts로 새 결제창을 연다(PAY-CONFIRM-08 "새 결제창으로 다시 승인").
  • applyDone의 조건부 UPDATE가 0행이면 다시 읽는다. APPROVED면 이미 반영된 것이므로 끝낸다(분개·outbox 없음, 중복 없음). 그 밖의 상태(CREATED·CANCELED 등)면 토스에서는 승인됐는데 우리는 다른 상태라는 뜻이다. ERROR 로그를 남기고 아래 보상 취소로 보낸다. 돈만 빠진 채 끝나는 경로를 남기지 않는다.
  • applyDone(paymentId, tossPayment)는 #349의 조회 DONE도 같은 함수로 처리한다. 승인 반영 코드는 한 곳에만 있다.

보상 취소(PAY-CONFIRM-07): 취소 대상은 토스 응답의 paymentKey다(DB 값이 아니다. 검증 실패는 토스가 다른 결제를 응답했을 수 있다는 뜻이다). 순서: ⓐ pg_call(kind=CANCEL, outcome=UNKNOWN, idempotency_key=cancel-{시도의 pg_order_id}) INSERT 커밋 → ⓑ 트랜잭션 밖에서 cancel(응답 paymentKey, "승인 응답 불일치", 키) → ⓒ 한 트랜잭션에서 pg_call 결과 + CANCELED(WHERE status IN ('APPROVING','UNKNOWN','CREATED'), 0행이면 상태는 그대로 두고 ERROR 로그). 시도의 pg_order_id는 ①에서 읽어 메모리에 들고 있는 값을 쓴다(DB 값은 이미 NULL일 수 있다). 분개는 쓰지 않는다(확정된 돈이 없다고 본다). 취소 결과가 불명이어도 CANCELED로 두고 ERROR 로그를 남긴다(감수, 거래 대사가 다시 잡는다).

8초 대기 (PAY-CONFIRM-11)

  • 요청 스레드는 ②③ 작업을 Executors.newVirtualThreadPerTaskExecutor()(Java 21)로 넘기고 future.get(8, SECONDS)로 기다린다.
  • 8초 안에 끝나면 ③의 응답을 준다. 넘으면 202 {paymentId, status: PENDING}과 헤더 Location: /v1/internal/payments/{orderRef}를 주고, 작업은 계속 돈다(결과는 이벤트로 나간다).
  • 설정: payment.approval.response-wait 기본 8s(제안).
  • 동시 실행 수 제한은 두지 않는다(벌크헤드 범위 밖). ADR 0337-5의 "크기를 제한한 별도 스레드 풀" 문장은 이 결정에 맞게 정정 메모를 단다(이 PR).

응답 예시

// 200
{ "success": true, "data": { "paymentId": 1001, "status": "APPROVED" }, "error": null }
// 202  (Location: /v1/internal/payments/OD-20261110-K7Q2M9XA)
{ "success": true, "data": { "paymentId": 1001, "status": "PENDING" }, "error": null }
// 422 — 요구사항 표의 {status, code, message}를 data에 그대로 담는다
{ "success": false,
  "data": { "status": "DECLINED", "code": "REJECT_CARD_PAYMENT", "message": "한도초과 혹은 잔액부족으로 결제에 실패했습니다." },

3. 원장 (ledger.service)

// 호출자 트랜잭션 필수 (Propagation.MANDATORY, LED-04). 새로 기록하면 true, 이미 있으면 false
boolean record(LedgerRefType refType, String refId, List<Journal.Line> lines)
record Line(LedgerAccount account, long debit, long credit, String sellerId) {}
  • Journal·Journal.Line 생성자가 줄 2개 이상, 각 줄 한쪽만 > 0(음수 거절), SELLER_PAYABLE 줄의 판매자 ID(LED-02), 차변 합 = 대변 합(Math.addExact로 넘침 거절)을 검사한다. 어기면 IllegalArgumentException, DB에 닿기 전이라 아무것도 저장하지 않는다(LED-01).
  • INSERT INTO ledger_journal … ON CONFLICT DO NOTHING(충돌 대상 생략. H2 PostgreSQL 모드에서 확인된 형태) → 0행이면 이미 기록된 사건이므로 줄을 넣지 않고 false로 끝낸다(LED-03). H2 create-drop이 같은 UNIQUE를 만들도록 LedgerJournal에 @UniqueConstraint를 둔다.
  • 수정·삭제 메서드를 만들지 않는다. 원장 리포지토리는 JpaRepository가 아닌 Repository로 좁혀 삭제 메서드를 물려받지 않는다(LED-05).
