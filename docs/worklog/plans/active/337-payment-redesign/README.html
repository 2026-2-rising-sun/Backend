#337 결제 서비스 재설계

상태: 진행 중 — Phase 1 완료. Phase 2·3의 남은 일을 서비스별 이슈로 마무리하는 중이다. 관련 이슈: #337 재설계(상위). 남은 이슈는 서비스별 표에 있다. 관련 요구사항: 결제 · 원장 · 환불 관련 결정: ADR 0337-1 · 0337-2 · 0337-3 · 0337-4 · 0337-5 Phase 1 구현 기록: 결제 1차 자료: 목표 설계와 작은 판단 · Payment 도메인 홈(새 설계와 현재 코드 문서 목록) · 목표 설계(그림·예시. 원본은 요구사항 MD와 ADR)

처음 읽는 사람을 위한 요약

Payment를 Mock에서 실제 토스 결제로 교체하고, 주문 서비스(CommerceCore)와 연결하는 작업이다. 결제와 환불의 정상 흐름은 이미 dev에서 동작한다. 남은 일은 장애가 났을 때 고객 돈과 주문이 어긋나지 않게 막고, 옛 코드를 지우고, 화면을 연결하는 것이다.

결제: 구매자 → Frontend → CommerceCore → (HTTP) → Payment → 토스
      HTTP 응답을 잃어도 Payment → payment.execution.results.v1 → CommerceCore 로 결과가 도착한다

환불: 구매자 → Frontend → CommerceCore → commerce.refund.requests.v1 → Payment → 토스 취소
      Payment → payment.refund.results.v1 → CommerceCore
지금 남은 문제 고객이나 운영에 생기는 일 이슈
토스 승인 요청이 429를 받으면 미처리로 간주한다 실제로 승인됐다면 이중 청구되거나 환불이 누락될 수 있다 #398
환불 하나가 미확정이면 같은 결제의 다른 상품을 환불할 수 없다 토스 장애가 길면 환불 기간을 놓칠 수 있다 #399, #401
Core가 처리 못 하는 메시지를 끝없이 재시도한다 뒤의 결제 결과가 모두 멈춘다 #389, Infra #64
보상 대기 주문이 있으면 새 구매가 막힌다 이전 결제 문제 때문에 고객이 구매하지 못한다 #377
오래 미확정인 건을 사람이 알 수 없다 고객 돈이 묶인 채 방치될 수 있다 #387, #369
옛 결제 경로와 계약이 남아 있다 호출하면 실패하고 새 경로와 헷갈린다 #384, #390, #402
화면이 새 상태를 모른다 처리 중인 주문이 오류처럼 보일 수 있다 Frontend #89

용어

  • UNKNOWN(결과 불명): 토스에서 돈이 처리됐는지 아직 모르는 상태. 실패로 단정하지 않고 조회로 확인한다.
  • 시스템 보상: 주문은 끝났는데 결제됐을 수 있을 때, 결제 여부를 확인해 결제됐으면 자동으로 환불하는 처리.
  • DLT: 소비자가 처리하지 못한 Kafka 메시지를 따로 모아 두는 토픽. 뒤 메시지가 막히지 않게 한다.
  • Outbox: DB 변경과 보낼 이벤트를 한 트랜잭션에 저장해 이벤트 유실을 막는 방식.

이번 범위에서 정한 것

  • 처리 못 한 메시지는 그 메시지를 소비하는 서비스 팀이 원인을 고치고 재처리한다. 판매자와 구매자에게 DLT를 노출하지 않는다.
  • 전용 재처리 도구, 관리자 화면, 알림 등급은 만들지 않는다. Kafka offset 되감기, Kafka UI, 기존 Slack 알림, 운영 절차 문서로 처리한다.
  • 공통화는 Kafka 소비 오류 처리기만 한다. 돈의 안전 경계가 숨겨지지 않도록 새 @Aspect는 만들지 않는다.
  • 서킷 브레이커는 Payment가 판단한다. Core는 Payment가 고른 PG를 전달만 하고, 환불은 항상 원래 PG로 보낸다(#400).

목표와 범위

Mock 중심의 Payment를 토스 기준으로 교체한다. 최소 기능부터 완성한다: 결제 1건이 끝까지 정확하게 끝나는 것이 먼저고, 대사·정산·지급은 후순위다. 기존 구현과 호환을 맞추지 않는다(ADR 0337-2).

  • 이 계획이 맡는 것: Payment 전체(Phase 1·3·후순위)와 결제에 연관된 주문 흐름(Phase 2 주문 연동). 결제와 주문이 겹치는 설계는 이 계획이 우선한다.
  • 도메인 분리: Phase 2는 #337의 하위 이슈로 두되 service:commercecore 라벨로 진행한다. 두 도메인은 계약(contracts/)과 ADR로만 잇는다.
  • CommerceCore 범위: 재고·쿠폰, 주문 모듈 구조(#331).
  • 서비스 소유: 서비스마다 독립 팀이 맡는다고 가정한다. 이슈 하나는 소유 서비스 하나의 구현만 요구하고, 서비스 사이의 약속은 contracts/와 ADR로 잇는다.
  • 범위 밖(만들지 않음, 필요하면 별도 요구사항): 토스 호출 동시 실행 수 제한(벌크헤드)·웹훅, 토스 지급대행 실연동·셀러 등록(지급은 Mock), 스케줄러 분산 락, Redis 등 경합 최적화.

이번 범위의 종료 기준:

  • 위 표의 이슈가 모두 닫힌다.
  • dev와 Infra main으로 주문 → 승인 → 부분·전체 환불 E2E가 통과한다.

문서를 나누는 기준

  • 이 README는 모든 Phase의 목표·범위·서비스 소유·순서·의존과 종료 기준을 맡는다. #337의 체크리스트는 진행 상태만 보여 주고 이 문서를 링크한다.
  • Phase 1은 처음 전체를 새로 만드는 작업이라 별도 구현 기록이 있다. 이 문서는 기록으로 유지하고 끝나면 계획과 함께 completed/로 옮긴다.
  • Phase 2·3은 별도 Phase 문서를 만들지 않는다. 동작은 요구사항과 이슈, 서비스 간 약속은 contracts/, 결정은 ADR, 흐름은 design-docs/flows/에 둔다.
  • 새 Phase 문서는 여러 이슈에 걸친 새 설계가 필요할 때만 착수 전에 쓴다. #400과 정산이 후보다.
  • 구현 PR 본문에는 그 PR의 요구사항 ID와 동작, 구현 방식, 아키텍처·성능 변경점, 학습 포인트(핵심 문법 예시)를 쓴다.

진행 방식 (SDD · TDD)

  1. 스펙 먼저: 동작이나 계약이 바뀌면 요구사항, 계약, ADR을 구현과 같은 PR 또는 앞선 PR에서 고친다.
  2. Red: 이슈 완료 조건과 요구사항 ID마다 실패하는 테스트를 쓴다. @DisplayName에 ID를 넣는다. 테스트만 먼저 커밋한다.
  3. Green: 구현한다. 이때 테스트를 고치지 않는다. 테스트가 틀렸으면 멈추고 PR 본문에 이유를 적은 뒤 고친다.
  4. Refactor → 검증 → 독립 리뷰: 아래 PR 게이트. 푸시는 Green 뒤에만 한다(자식 PR이 빨간 CI를 물려받지 않게).
  5. 기록: 요구사항 체크박스, 이슈 완료 조건, 워크로그 항목. 스펙이 바뀌면 요구사항 문서를 먼저 고친다. - 워크로그는 PR 하나에 항목 하나다(세션마다 쓰지 않는다). 팀 템플릿의 제목 ## #<이슈> <PR 제목>과 4항목(변경·판단 · 검증 · 미실행·한계 · 다음 작업)을 한 줄씩 쓰고 PR 링크를 단다. 자세한 내용은 PR 본문과 CI가 가진다. - Phase 상태는 이 계획, 이슈 상태는 GitHub가 가진다. 워크로그는 다시 읽지 않는 근거 기록이고, 요구사항 근거:에서 항목 제목 앵커로만 연결한다.

사소한 변경(이름, 설정 한 줄)은 1·2를 건너뛴다.

  5. 작성자가 아닌 리뷰어의 독립 리뷰. 질문: ID마다 테스트가 실제로 그 조건을 검사하나 / 돈이 두 번 움직이지 않나 / 모든 상태 변경이 이전 상태 조건부 UPDATE이고 0행을 처리하나 / 트랜잭션 안에서 토스를 부르지 않나 / 범위 밖을 구현하지 않았나.

스택 PR

  • PR base는 바로 앞 PR 브랜치, 첫 PR은 dev. 브랜치는 <type>/#<그 PR의 하위 이슈>-<slug>다.
  • 스택은 아래 PR부터 merge commit("Create a merge commit")으로 병합한다. squash·rebase 병합은 쓰지 않는다. 자식 브랜치가 부모 커밋을 그대로 가지고 있어 rebase·강제 푸시가 필요 없다.
  • 저장소는 병합 뒤 브랜치를 지우지 않아(delete_branch_on_merge: false) 자식 PR의 base가 자동으로 바뀌지 않는다. 부모가 병합되면 자식 base를 dev로 바꾼 뒤 병합한다.
gh pr edit <내-PR> --base dev && gh pr ready <내-PR>
