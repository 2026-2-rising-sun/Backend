목표 설계와 작은 판단

결제 재설계의 구현 전 목표다. 현재 코드 설명은 Payment 모듈 문서에 있고, PR이 병합될 때마다 해당 부분을 그쪽으로 옮긴다. 이 파일은 계획이 끝나면 계획 폴더와 함께 completed/로 간다. 표의 #앵커는 Payment 목표 설계의 절이다.

컨텍스트 (C4 L1)

flowchart LR
  buyer([구매자]) --> fe[Frontend]

  pay -- 승인·조회·취소 --> toss[(토스페이먼츠)]

응답 common-module ApiResponse. 인증 X-Service-Token #api

작은 판단

ADR로 올리기엔 작은 결정이다. 바뀌면 이 표를 고친다.

판단 이유 감수
원본에 없는 오류 코드 STALE_CHECKOUT, PG_UNAVAILABLE을 쓴다 예전 결제창·연결 실패를 Commerce가 구분해 안내해야 한다 설계 HTML과 다르다. 계약 YAML이 원본이 된다
승인 응답 검증 실패 뒤 보상 취소가 불명이어도 결제는 CANCELED 정상이면 생기지 않는 일이다. 상태를 늘리지 않는다 돈이 잡힌 채 CANCELED일 수 있다. 거래 대사를 만들기 전까지는 오류 로그로 수동 확인
토스 401과 설정 403 2개 코드는 "보내지 않음"(CREATED 유지, 503)으로 본다. 429(호출 제한)는 "불명"(UNKNOWN 유지, 조회로 확정)이다. 그 밖의 403은 거절 우리 키 설정 문제는 카드 거절이 아니다. 429는 토스가 처리했는지 알 수 없어 "보내지 않음"으로 보면 다시 결제할 때 이중 청구·미환불이 생길 수 있다(정정 2026-11-24, #398, PAY-PG-01). 카드 거절 대부분이 403이라 상태 코드만으로 나누면 안 된다(토스 오류 코드 문서, 2026-11-15 확인) 원본 #f4는 4xx를 모두 거절로 본다. 토스가 코드를 늘리면 분류표를 고친다
보상 취소 멱등 키 cancel-{pg_order_id}, 승인 API는 경로 orderRef로 결제를 찾고 pgOrderId의 마지막 - 앞부분이 같은지 확인한다 원본에 값이 없다 —
스케줄러에 분산 락을 두지 않는다 모든 전이가 이전 상태 조건부 UPDATE라 중복 실행이 무해하다 같은 결제를 두 인스턴스가 조회할 수 있다(토스 조회 1번 더)
원본 V7(정산·지급)을 V7 정산, V8 지급으로 나눈다 착수 시점이 다르다 정산 착수 때 확인
토스 호출 동시 실행 수 제한(벌크헤드)을 두지 않는다 정합성 문제가 아니다. 이중 승인·누락은 조건부 UPDATE와 멱등 키가 막는다. 남는 위험은 부하(느린 PG에 스레드가 묶임)다 부하 테스트나 운영 지표에서 문제가 보이면 도입
경로는 리소스로 쓴다. 결제는 {orderRef}로 가리키고 결제창은 /checkouts(201), 승인은 /approval이다 토스 모양을 따른 POST /payments/confirm만 결제 키가 경로에 없었다. 202에는 조회 위치 Location을 준다 본문 pgOrderId와 경로 orderRef가 다를 수 있어 400 검증을 하나 더 둔다
정체 해소는 주문 조회(GET /orders/{no}) 때 한다. 따로 스케줄러를 두지 않는다 아무도 조회하지 않는 주문은 만료 배치가 PAYMENT_CONFIRMING도 닫는다 조회가 없으면 만료(T + 3분)까지 확인 중에 머문다
주문 종료 통지 계약(#343의 order-closure·payment_order_control)을 쓰지 않는다 만료는 생성 때 받은 expiresAt으로 Payment가 닫고(PAY-EXPIRE-01), 늦은 승인은 RefundRequested(LATE_APPROVAL)로 환불한다(REF-LATE-01). 통지 없이 같은 안전성을 얻는다 #343에 Payment 부분 제거를 요청했다. 남으면 Phase 1 PR0·스키마에서 지운다
