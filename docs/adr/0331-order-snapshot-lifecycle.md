# ADR 0331: 주문서 생성 시점의 주문·스냅샷·재고 선점

결정 상태: 핵심 정책 및 후속 U2/U3 채택. U1도 단가 우선/남은 실결제액 상한으로 채택됐다. 물리 PK/테이블명 보존 확장안은 구현 착수 지시에서 채택됐다.

구현 상태: 확정 범위 구현 진행 중. [실행 계획](../exec-plans/active/331-order-module/README.md) · [상세설계](../design-docs/commercecore/order/설계.md) · [기록](../worklog/2026-11-13.md#331-order-설계-통합-검토-준비)

## 문제

현재는 구매 묶음 PaymentGroup과 Sales 한 건을 가리키는 Order를 사용한다. 새 설계에서는 한 주문번호가 여러 SKU 구매 항목을 포함하고, 상품·가격 변경 후에도 당시 구매 내역을 유지해야 한다. 결제 지연 때문에 주문 재고가 무기한 묶이거나 늦은 성공/중복 환불이 수량을 두 번 바꾸지 않아야 한다.

## 확정 결정과 근거

| 결정 | 사용자 답변·인계 근거 |
|---|---|
| 주문번호 1 : 여러 구매 항목, 거래 단위 SKU | “주문번호와 SKU또는 상품ID를 1대N 매핑”, 이후 Product–SKU 공통 맥락 |
| 주문서 화면 생성 요청에서 Pending·재고 선점·스냅샷 저장 | “일단 주문서 화면 생성 시 pending + 재고 선점”; SKU 추가 확정 인계도 동일 |
| 생성 시 서버 현재 가격을 저장하고 기존 주문은 유지 | “pending 할때 가격같은 그 당시 상품 정보를 저장 , 그 주문은 그것을 따른다” |
| Pending 10분 만료 시 실패/예약 해제, 늦은 성공으로 부활하지 않음 | “pending 10분이 만료되면 그 주문은 실패로 처리”, “결제 서버에도 실패한 주문이라는 이벤트나 요청” |
| 결제 후 환불 성공 확인 시 취소 확정·재고 복구 | “결제에서 환불이 정상적으로 되었단 이벤트나 응답이 오면을 직 후라고 한거임” |
| 부분 환불 지원·부분 환불 시 쿠폰 사용 유지·전체 환불 성공 시 복원 | “부분 환불도 지원”, “쿠폰을 사용한거로 처리”, “전체 환불이면 쿠폰을 되돌리긴 해야함” |
| 쿠폰은 주문서 안에서 변경, 상품/SKU 기준 대상 | “주문서 안에서 선택 변경”, “SKU별로 사용하게 만들거나 상품단위” |
| 별도 재고 예약 테이블 없이 Order 적용과 SKU 수량을 같은 DB 트랜잭션에 반영 | SKU 담당 사용자 확정 인계 `msg_95b1acb60e10`, 응답 `msg_90dc6ba5ff2d` |

## 이유와 대안

스냅샷은 상품 버전 이력·현재 상품 조회와 주문 이력을 분리한다. 결제 버튼 시점 생성은 홀딩 시간이 짧지만 사용자가 정한 주문서 생성 흐름과 다르므로 선택하지 않았다. 선점은 생성부터 10분이라는 비용이 있으며 서버 멱등성·기한 검사·만료 작업이 필요하다.

별도 예약 테이블 대신 주문 항목/상태를 수량 근거로 삼고 한 DB 트랜잭션으로 적용한다. 부분 환불에는 별도 환불 건 기록이 여전히 필요하며 기존 환불 저장소를 확장하는 안을 우선한다. Payment DB까지 같은 트랜잭션으로 묶는 대안은 서비스 경계에 맞지 않는다.

## 결정 범위와 남은 연결

후속 사용자 답변으로 쿠폰 단일 항목·누적 전량·원래 유효기간, 단가 우선 수량 환불, 결제 대기 중 즉시 취소 제한이 확정됐다. 코디네이터는 기존 PK·물리명 보존 확장, Core V104/Payment V4, 신규 경로와 기존 활성 주문의 정책 버전 분리를 배정했다. 옵션 JSON 공급과 공개 다중 SKU 표시 정책은 보류한다.

## 영향

Order #331은 사용자 환불 범위·업무 적용과 주문 경계를 맡고 SKU #334는 수량 변경을 맡는다. Cart #332와 Product #333의 입력·판매 가능 조건도 같은 생성 경로에 연결한다. 계약·DDL은 Product→SKU→Cart→Order 의존 순서로 통합한다. 독립 Payment 기능 전체·배송·정산·하네스 개편을 이번 결정에 포함하지 않는다.

## 구현 착수 후 후속 결정

사용자 U2 답변으로 주문당 쿠폰 한 장/선택 구매 항목 하나 적용, 누적 전량 성공 때 복원, 원래 유효기간 유지(연장·재발급 없음)가 확정됐다. U3는 결제 결과 대기 중 즉시 취소 제한을 유지한다. 뒤이은 U1 최종 답변으로 비례배분 제안은 폐기됐다. 아래 단가 우선 환불을 적용한다.

새 주문서 경로는 UUID 주문번호와 기존 payment_group/orders PK·물리명 보존, policy_version=1/DB 시각 10분을 사용한다. 기존 API/활성 구매의 policy_version=0과 과거 TTL은 유지한다. Core V104와 독립 Payment V4가 배정됐고 구현·실행 검증을 진행한다. Payment 종료/보상 최소 계약은 실행 계획의 별도 문서를 따른다.

### U1 최종 결정: 단가 우선 환불

사용자는 이전 비례배분 제안을 거절하고 4,000원×3개/쿠폰2,000원/실결제10,000원에서 순차 4,000·4,000·2,000원과 마지막 전량 성공 시 쿠폰 복원을 확정했다. 일반식은 `min(주문 단가×이번 수량, 항목 실결제액−이전 성공 환불액)`이다. 잔여 환불액이 0이어도 성공 수량·재고·전량 여부를 처리한다. 다른 주문항목이 남아 있으면 쿠폰을 복원하지 않으며 원래 유효기간을 유지한다.

[코디네이터의 공식 정책 조사 기록](../exec-plans/active/331-order-module/refund-policy-research.md)을 보존했다. 확인한 외부 정책의 범위·한계는 사용자 결정과 다르며 같은 알고리즘을 사용한다고 주장하지 않는다.

## 2026-11-14 후속 사용자 확정: 모든 신규 주문10분

사용자가 구 API 예외 없이 모든 새 주문10분, 이미 생성된 주문의 저장 기한 보존을 직접 확정했다. 기존 API 신규15분 선택은 폐기했다. 기존 행·기한을 소급 변경하지 않고 신규 구 API만 policy_version=2로 기록해 PAYMENT_CONFIRMING/UNKNOWN도 원래600초 기한을 판정한다. 버전1 주문서와 같은 종료/영속 보상 로직을 공유하되 기존 구 API의 결제확인 응답과 환불 계약은 유지한다. 기존 버전0/이미 저장된15분 기한·번호·금액·참조는 그대로다. 진행 환불1건 및 flag-off 보상 예외의 사용자 선택은 아직 없으며 변경하지 않는다.
