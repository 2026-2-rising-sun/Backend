# ADR 0331: 주문서 생성 시점의 주문·스냅샷·재고 선점

결정 상태: 핵심 정책 및 후속 U2/U3 채택. U1도 단가 우선/남은 실결제액 상한으로 채택됐다. 물리 PK/테이블명 보존 확장안은 구현 착수 지시에서 채택됐다.

구현 상태: Payment 담당범위 정정·독립 결함 보완 검증 중. 원래 설계 미충족·머지 불가. [실행 계획](../worklog/plans/completed/331-order-module/README.md) · [상세설계](../design-docs/services/commercecore/order/overview.md) · [기록](../worklog/2026-11-13.md#331-order-설계-통합-검토-준비)

아래 2026-11-14까지의 정책·구현 설명은 당시 기록이며 현재 PR의 제공 범위는 마지막 후속 정정과 현재 계획을 따른다.

## 문제

현재는 구매 묶음 PaymentGroup과 Sales 한 건을 가리키는 Order를 사용한다. 새 설계에서는 한 주문번호가 여러 SKU 구매 항목을 포함하고, 상품·가격 변경 후에도 당시 구매 내역을 유지해야 한다. 결제 지연 때문에 주문 재고가 무기한 묶이거나 늦은 성공/중복 환불이 수량을 두 번 바꾸지 않아야 한다.

## 확정 결정과 근거

| 결정 | 사용자 답변·인계 근거 |
|---|---|
| 주문번호 1 : 여러 구매 항목, 거래 단위 SKU | “주문번호와 SKU또는 상품ID를 1대N 매핑”, 이후 Product–SKU 공통 맥락 |
| 주문서 화면 생성 요청에서 Pending·재고 선점·스냅샷 저장 | “일단 주문서 화면 생성 시 pending + 재고 선점”; SKU 추가 확정 인계도 동일 |
| 생성 시 서버 현재 가격을 저장하고 기존 주문은 유지 | “pending 할때 가격같은 그 당시 상품 정보를 저장 , 그 주문은 그것을 따른다” |
| Pending 10분 만료 시 실패/예약 해제, 늦은 성공으로 부활하지 않음 | “pending 10분이 만료되면 그 주문은 실패로 처리”, “결제 서버에도 실패한 주문이라는 이벤트나 요청” |
| 결제 후 환불 성공 확인 시 취소 확정·재고 복구 | “결제에서 환불이 정상적으로 되었단 이벤트나 응답이 오면을 직 후라고 한거임” |
| 부분 환불 지원·부분 환불 시 쿠폰 사용 유지·전체 환불 성공 시 복원 | “부분 환불도 지원”, “쿠폰을 사용한거로 처리”, “전체 환불이면 쿠폰을 되돌리긴 해야함” |
| 쿠폰은 주문서 안에서 변경, 상품/SKU 기준 대상 | “주문서 안에서 선택 변경”, “SKU별로 사용하게 만들거나 상품단위” |
| 별도 재고 예약 테이블 없이 Order 적용과 SKU 수량을 같은 DB 트랜잭션에 반영 | SKU 담당 사용자 확정 인계 `msg_95b1acb60e10`, 응답 `msg_90dc6ba5ff2d` |

## 이유와 대안

스냅샷은 상품 버전 이력·현재 상품 조회와 주문 이력을 분리한다. 결제 버튼 시점 생성은 홀딩 시간이 짧지만 사용자가 정한 주문서 생성 흐름과 다르므로 선택하지 않았다. 선점은 생성부터 10분이라는 비용이 있으며 서버 멱등성·기한 검사·만료 작업이 필요하다.

별도 예약 테이블 대신 주문 항목/상태를 수량 근거로 삼고 한 DB 트랜잭션으로 적용한다. 부분 환불에는 별도 환불 건 기록이 여전히 필요하며 기존 환불 저장소를 확장하는 안을 우선한다. Payment DB까지 같은 트랜잭션으로 묶는 대안은 서비스 경계에 맞지 않는다.

## 결정 범위와 남은 연결

후속 사용자 답변으로 쿠폰 단일 항목·누적 전량·원래 유효기간, 단가 우선 수량 환불, 결제 대기 중 즉시 취소 제한이 확정됐다. 코디네이터는 기존 PK·물리명 보존 확장, Core V104/Payment V4, 신규 경로와 기존 활성 주문의 정책 버전 분리를 배정했다. 옵션 JSON 공급과 공개 다중 SKU 표시 정책은 보류한다.

## 영향

Order #331은 사용자 환불 범위·업무 적용과 주문 경계를 맡고 SKU #334는 수량 변경을 맡는다. Cart #332와 Product #333의 입력·판매 가능 조건도 같은 생성 경로에 연결한다. 계약·DDL은 Product→SKU→Cart→Order 의존 순서로 통합한다. 독립 Payment 기능 전체·배송·정산·하네스 개편을 이번 결정에 포함하지 않는다.

## 구현 착수 후 후속 결정

사용자 U2 답변으로 주문당 쿠폰 한 장/선택 구매 항목 하나 적용, 누적 전량 성공 때 복원, 원래 유효기간 유지(연장·재발급 없음)가 확정됐다. U3는 결제 결과 대기 중 즉시 취소 제한을 유지한다. 뒤이은 U1 최종 답변으로 비례배분 제안은 폐기됐다. 아래 단가 우선 환불을 적용한다.

새 주문서 경로는 UUID 주문번호와 기존 payment_group/orders PK·물리명 보존, policy_version=1/DB 시각 10분을 사용한다. 기존 API/활성 구매의 policy_version=0과 과거 TTL은 유지한다. Core V104와 독립 Payment V4가 배정됐고 구현·실행 검증을 진행한다. Payment 종료/보상 최소 계약은 실행 계획의 별도 문서를 따른다.

### U1 최종 결정: 단가 우선 환불

사용자는 이전 비례배분 제안을 거절하고 4,000원×3개/쿠폰2,000원/실결제10,000원에서 순차 4,000·4,000·2,000원과 마지막 전량 성공 시 쿠폰 복원을 확정했다. 일반식은 `min(주문 단가×이번 수량, 항목 실결제액−이전 성공 환불액)`이다. 잔여 환불액이 0이어도 성공 수량·재고·전량 여부를 처리한다. 다른 주문항목이 남아 있으면 쿠폰을 복원하지 않으며 원래 유효기간을 유지한다.

[코디네이터의 공식 정책 조사 기록](../worklog/plans/completed/331-order-module/refund-policy-research.md)을 보존했다. 확인한 외부 정책의 범위·한계는 사용자 결정과 다르며 같은 알고리즘을 사용한다고 주장하지 않는다.

## 2026-11-14 후속 사용자 확정: 모든 신규 주문10분

사용자가 구 API 예외 없이 모든 새 주문10분, 이미 생성된 주문의 저장 기한 보존을 직접 확정했다. 기존 API 신규15분 선택은 폐기했다. 기존 행·기한을 소급 변경하지 않고 신규 구 API만 policy_version=2로 기록해 PAYMENT_CONFIRMING/UNKNOWN도 원래600초 기한을 판정한다. 버전1 주문서와 같은 종료/영속 보상 로직을 공유하되 기존 구 API의 결제확인 응답과 환불 계약은 유지한다. 기존 버전0/이미 저장된15분 기한·번호·금액·참조는 그대로다. 진행 환불1건 및 flag-off 보상 예외의 사용자 선택은 아직 없으며 변경하지 않는다.

## 2026-11-14 기존 범위 마무리와 후속 보류

사용자는 기존 전체 통합·모든 새 주문10분 작업을 지금 마무리하고 [#345 동시 환불](https://github.com/2026-2-rising-sun/Backend/issues/345)·[#346 결제 준비/실행 기한 분리](https://github.com/2026-2-rising-sun/Backend/issues/346)는 나중에 전용 작업 공간에서 진행하도록 요청했다. 기존 완료조건과 실행 증거를 대조해 계획을 completed로 이동했다. 이는 현재1건 환불 제한·일반 환불off 보상 예외의 정책 전체 승인이 아니며 현재 동작은 바꾸지 않았다. 후속 모델·기한 기본값은 이 기록에서 채택하지 않는다.


## 2026-11-15 후속 사용자 확정과 감사 보완

사용자는 기존 선점 주문은 Product 판매중지·삭제 후에도 **원래 저장기한 안에서 결제 허용**, 새 주문만 차단하도록 직접 확정했다. 기한/환불 정책은 변경하지 않는다. Cart 담기 판매조건·재고0 판매시작·중지상품 공개노출은 아직 사용자 답변이 없으며 현재 동작을 승인으로 표시하지 않는다.

신규 구 API 단건·Cart 단건/묶음도 seller_id_snapshot을 주문 생성 시 저장한다. 환불은 저장된 product/seller 원본을 우선하며 과거 seller NULL 주문에 한해서 삭제행에 남은 생성 후 불변 seller_id만 내부 포트로 조회한다. 과거 주문/이미 완료된 환불행을 현재 상품명·금액·이미지·기한으로 일괄 재작성하지 않는다. 공개 상품 조회의 삭제 필터와 판매자 환불 권한은 유지한다. 이는 누락 결함의 기술적 보완이며 새 환불 정책을 채택하는 것이 아니다.

[#345](https://github.com/2026-2-rising-sun/Backend/issues/345)·[#346](https://github.com/2026-2-rising-sun/Backend/issues/346) 및 #340 보류는 유지한다. 검증 결과는 [2026-11-15 기록](../worklog/2026-11-15.md#331-삭제-상품-환불의-판매자-출처와-cart-선택-계약-보완)에서 기존 실행과 구분한다.

Payment 추가 변경과 종속 Core 연동은 사용자 범위 정정에 따라 제외 검토 중이다. 기존 검증은 보존된 Mock 구현의 당시 결과이며 채택된 ADR0337의 M2/M3 연동 완료가 아니다. 신규 실행 차단 여부는 사용자 결정 대기이며 승인 전 기한 완화·무보상 실행·임의503을 적용하지 않는다.

## 2026-11-15 최신 기한 요구와 미구현

사용자 직접 확정은 PENDING 생성부터600초, 실제 실행 진입부터 PAYMENT_PROCESSING 별도600초다. 준비데이터 생성/재전송으로 실행기한을 시작·연장하지 않는다. PROCESSING 만료가 PG실패확정·즉시해제 승인은 아니며 UNKNOWN의 종료/조회/보상계약은 별도 정의가 필요하다. 내부PENDING600초 외 새상태/실행타이머·공개금전연동·legacy기한확대는 현재 미충족이다. ## 2026-11-16 별도 처리 기한과 Commerce 소유 경계

결정 상태: 채택. 앞 절의 "PROCESSING 만료 시 해제 미확정"은 아래 사용자 확정으로 대체한다. 구현 전체 완료를 뜻하지 않는다.

- 공개·DB 상태명 `PENDING_PAYMENT`와 `PAYMENT_CONFIRMING`은 호환 보존하며 의미는 각각 PENDING과 PROCESSING이다. 새 enum 값이나 기존 상태 일괄 변환을 추가하지 않는다.
- 새 주문은 생성부터600초다. 저장된 `expires_at`은 유지한다. 실제 승인 실행을 처음 접수할 때 `processing_expires_at=DB시각+600초`와 HTTP 전달 원문을 같은 Core 트랜잭션에 저장한다. 재시도는 같은 requestId를 쓰며 기한을 연장하지 않는다.
- 준비 데이터 생성은 PENDING을 유지해야 한다. 현재 공개 legacy는 준비 API 없이 실행을 접수한다. 팀원 Payment 생성·승인 중계로 교체하는 작업은 미완이다.
- PROCESSING 기한 도달은 주문 EXPIRED와 재고·쿠폰 선점해제다. Payment 실패 확정은 아니다. 잠금 뒤 DB시각으로 판정하고, 스케줄러보다 승인 결과가 먼저 와도 만료를 먼저 적용한다.
- 만료·취소 뒤 성공은 주문을 복구하지 않는다. `late_approval_refund`에 `late-{paymentId}`로 환불 필요 사실을 결과와 함께 저장한다. 현재 REQUIRED는 환불 접수·Kafka 전달·환불 완료가 아니다.
- 목표는 환불 필요 사실과 `RefundRequested(LATE_APPROVAL)` outbox를 같은 트랜잭션에 저장하고 환불 결과를 소비하는 것이다. 팀원 실제 계약/소비자가 아직 없어 이번 독립 구현은 REQUIRED 기록까지만 제공한다. 주문 종료 API나 Payment 제어 행은 만들지 않는다.
- Core HTTP 전달 기록의 생성/재시도도 due 조회와 같은 DB시각을 쓴다. JVM시각을 섞지 않는다.
- V105는 컬럼과 Core 환불 필요 테이블만 추가한다. 기존 확인중 정책0/1/2의 시작시각을 추측하거나 타이머를 소급 적용하지 않는다. 해당 행의 운영 이행과 이미 다른 V104를 적용한 환경의 체크섬 문제는 미완이다.

## 2026-11-16 팀원 계약의 Commerce 중계 구현

후속 구현은 새 `/v1/order-sheets`에서 준비 성공 PENDING 유지와 인증 후 PROCESSING 진입을 분리한다. Core seller_order에 팀원 설계의 정렬 번호·할인 후 금액·commerce.commission-rate 설정을 생성 시 보존한다. 설정 숫자 기본값은 정하지 않는다. V106은 기존 V104/V105와 과거 데이터를 덮어쓰지 않는다.

PREPARE/APPROVAL 영속 원문을 기존 HTTP 전달표에 저장하고 legacy 전달기와 대상을 분리한다. 승인 접수 TX에 상태/600초 기한/전달 기록을 함께 저장하며 HTTP는 TX 밖이다. 새 이벤트 소비는 팀원 source/schema/key와 원결제/금액을 검증한다. 늦은 승인에는 새 원결제용 payment_relay_refund와 RefundRequested outbox를 같은 TX에 저장하며 환불 결과를 별도 확정한다. legacy REQUIRED를 임의 새 원결제 환불로 이관하지 않는다.

사용자600/600·확정 실패 FAILED를 적용한다. 팀원 목표의 Commerce T+3분/거절 후 PENDING 복귀 제안은 채택하지 않는다. Payment CREATED expiresAt은 원래 준비 기한이며 APPROVING/UNKNOWN 실패 기한이 아니다. 주문 만료 후에도 미확정 결제는 조회하고 실패를 추정하지 않는다.

앞 절의 "새 중계·outbox 미완"은 이전 축소 커밋의 상태다. 현재 Core 중계/계약 대역 검증과 실제 Payment 생성·조회·checkout 확인을 제공한다. 실제 승인·환불 endpoint/event와 운영 이행·호출자 전환은 남아 계획을 active로 유지한다. [현재 범위](../worklog/plans/active/331-order-audit-fixes/processing-deadline.md).
