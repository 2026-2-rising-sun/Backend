# ADR 0332: Cart의 SKU 조작 단위와 결제 성공 후 정리 경계

결정 상태: 업무 방향 채택 · 1차 기술 경계 고정 · 나머지 연결안 미결정

구현 상태: 사용자 착수 지시에 따라 진행 중. [실행 계획](../exec-plans/active/332-cart-module/README.md) · [설계](../design-docs/commercecore/cart/설계.md) · [Cart #332](https://github.com/2026-2-rising-sun/Backend/issues/332) · [정리 검토 #340](https://github.com/2026-2-rising-sun/Backend/issues/340)

## 문제

현재 Cart는 상품 하나당 한 항목이며 Order 패키지 안에 있다. Product–SKU 1:N과 SKU별 가격·재고로 바꾸려면 구매 단위를 구분해야 한다. 결제 성공 정리는 Order에 저장한 Cart ID·버전을 사용하고 선택 환불도 이 ID에 의존한다. 사용자는 Order가 Cart 정보를 많이 갖는 구조와 관리 비용을 지적했다.

## 결정과 이유

상품별로 묶어 표시하고 담긴 SKU별로 체크·수량 변경·삭제한다. 사용자는 해당 권장안에 “1번은 너가 권장한댈로”라고 답했다. 옵션별 판매 단위와 조작 단위를 일치시키되 화면의 상품 묶음을 유지한다.

담기와 조회는 재고를 예약하지 않는다. 가격·재고 원본은 SKU, 주문서 생성 시점의 가격 스냅샷과 예약의 트랜잭션은 Order·SKU가 맡는다. 별도 Price/Inventory·예약 테이블을 Cart에서 도입하지 않는다. 쿠폰은 이번 설계에서 보류한다.

사용자가 “장바구니는 결제 성공하면 정리해야함”이라고 확정했으므로 주문 생성 즉시 삭제안은 폐기한다. 자동 정리의 연결·동시 변경 정책은 사용자가 “피그마와 문서에 명시, 이슈까지 새로 생성 후 구현 계획 작성”을 요청해 #340으로 분리했다. Cart 쪽 주문 연결이나 편집 제한은 채택된 결정이 아니다.

## 대안과 남은 영향

현재 ID·버전 조건부 삭제를 호환 기간 유지하면 변경·재추가된 행을 구분하는 동작과 환불 참조를 보존할 수 있지만 Order의 Cart 의존은 남는다. Cart 쪽 주문 연결은 Order 필드를 줄일 수 있으나 연결 수명·실패 해제·복수 주문·편집 정책을 새로 관리해야 한다. SKU·수량만으로 정리하면 재추가된 같은 SKU를 구별하기 어려워 바로 채택하지 않는다.

초안 당시 보존안 채택 여부·ID·공유 편집 책임은 미결정이었다. 후속 1차 기술 결정으로 Product/Cart/SKU BIGINT·Long 유지, 기존 Sales ID의 기본 SKU 보존 우선, Core API YAML 최종 편집자 Order, #340 보류 중 Cart ID/version 정리·환불 참조 보존을 고정했다. Order 목표 저장 위치·재진입, 공통 잠금 순서·마이그레이션 번호/적용 순서·외부 응답은 계속 검토한다. #340 보류를 새 정리 정책이나 기존 참조 삭제의 승인으로 바꾸지 않는다.

## 후속 사용자 확정: 신규 판매 준비

2026-11-13 사용자가 “판매 준비 상태로 생성하고 판매자가 판매 시작을 선택”을 확정했다. 신규 Product는 sale_enabled=false, SKU는 READY로 생성하고 기존 상품 상태는 유지한다. 등록 직후 판매 여부(U1)는 해소됐으며 READY 수동 복귀 전이까지 추가하지 않는다. Product 전체 제어와 SKU 개별 상태를 분리하여 Cart가 생성만으로 구매 가능하다고 표시하지 않도록 한다. 준비 항목의 담기 허용 여부와 재고 0 판매 시작 응답은 이 결정으로 확정하지 않는다.

근거 원문은 `build/design-handoff/신규-판매준비-확정.md`와 `통합-경계-1차-결정.md`에 보존했다. 앞 문단의 ID·공유 편집자 결정은 코디네이터 기술 조정이고 신규 판매 준비는 사용자 업무 정책이라는 차이를 유지한다.

사용자 구현 착수와 코디네이터 배정으로 코드·테스트·로컬 MD/HTML 작성을 진행한다. 기존 설계 Task의 failed 판정은 과거 기록으로 보존하며 새 시작 지시를 무효화하지 않는다. 구현 단계 FigJam은 코디네이터가 맡는다.

## 구현 조정: 미매핑 항목의 보존

V103은 원본 product_id를 유지하고 sku_id를 nullable로 확장한다. 기존 Sales ID와 일치하는 기본 SKU만 연결하며 매핑 불가 행을 삭제하거나 임의 SKU를 만들지 않는다. 해당 행은 조회·수량 변경·사용자 삭제를 허용하고 주문 선택만 이용 불가로 거절한다. 새 SKU 담기는 실제 SKU ID를 저장하고 기존 productId 요청은 SKU가 정확히 하나일 때만 호환한다.

후속 쿠폰/환불/취소 U1/U2/U3 확정은 Order 범위에 반영한다. Cart에는 별도 쿠폰 계산·환불 상태·취소 상태를 추가하지 않는다. 상세 최신 동작과 실제 검증은 설계·실행 계획·워크로그를 원본으로 삼는다.
