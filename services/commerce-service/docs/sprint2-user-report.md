> 대상 독자: 기획·프론트·리뷰어·팀원. 코드를 안 열어도 "commerce-service 로 지금 뭐가 되는지" 5분에 파악.

> 아직 안 되는 것 (판매 1·주문 1·주문 2 · 방송 연동) 은 §6.

## 30초 요약

- **관리자** 는 상품에 판매정보(가격·재고·상태) 를 붙이고, 판매 상태를 조작한다. 재고를 직접 늘리거나 줄인다.
- **비회원 구매자** 는 주문번호와 비밀번호로 자기 주문을 확인하고, 결제 전 이면 취소할 수 있다. 결제를 시작하고 결과를 나중에 다시 확인한다.
- **시스템** 은 결제 없이 방치된 주문을 자동으로 만료시켜 재고를 되돌린다. 서버가 죽었다 살아나도 진행 중이던 결제는 이어서 확정된다.
- **개발자** 는 Mock 결제 시나리오(성공/실패/지연) 를 원하는 대로 미리 지정해 테스트한다.

**아직 안 되는 것:** 판매정보 최초 등록, 주문 생성 자체 (주문서 작성 → 재고 확보). 모두 정수가 월요일에 담당.

## 1. 관리자가 할 수 있는 것

관리자 개념은 아직 로그인·역할 구분이 없다 (P2 스코프). 이 API 들에 접근 가능한 사람이 관리자.

### 1.1 상품에 가격 매기기

"상품 A 를 15,000원에 판다" 를 등록. 

- 이 기능은 **아직 정수 몫** (판매 1, 월요일 예정). 지금 DB 에 SQL 로 직접 넣거나 정수 PR 이 병합될 때까지 대기.

### 1.2 가격 바꾸기

이미 팔고 있는 상품의 판매가를 조정. 

- **되는 것:** 10,000원 → 12,000원 반영. 관리자 화면에 바뀐 가격이 즉시 보임.
- **되는 것:** 이미 만들어진 주문(예: 홍길동이 10,000원에 산 주문) 은 그대로 유지. 나중에 결제하든 취소하든 10,000원 그대로.
- **막는 것:** 두 관리자가 동시에 서로 다른 가격을 저장하면, 나중에 저장한 쪽이 앞선 쪽을 덮어쓰지 않는다. 앞선 사람이 성공하면 뒷사람은 "다른 관리자가 먼저 바꿨어요. 최신 가격 확인 후 다시" 안내를 받는다.
- **막는 것:** 0원이나 음수는 저장 안 된다.

### 1.3 재고 조회

"이 상품 지금 몇 개 팔 수 있나" 를 확인.

- **되는 것:** 두 수치를 나눠서 보여준다.
  - **판매 가능 수량** — 지금 새로 주문받을 수 있는 개수
  - **배정 수량** — 이미 누군가 주문했는데 아직 결제 대기 중인 개수
- 왜 나누나? 관리자가 "재고 30개인데 왜 20개만 팔리지?" 라는 오해를 방지. 그중 10개는 이미 결제 대기 중.

### 1.4 재고 늘리기·줄이기

관리자가 창고에 물건이 들어오면 재고를 추가. 반품이나 재고 정리 때는 감소.

- **되는 것:** "+50" 이면 판매 가능 수량이 50 증가. "-10" 이면 10 감소.
- **막는 것:** 감소한 뒤 결과가 음수가 되지 않는다. 재고 5개인데 "-10" 하면 요청 실패 (그대로 5개).
- **막는 것:** 이미 결제 대기 중(배정된) 수량은 이 기능으로 못 건드린다. 관리자가 실수로 남의 주문을 앗아갈 수 없다.
- **되는 것:** 10명이 동시에 "-1" 을 눌러도 판매 가능 수량 5인 상태에선 최대 5명만 성공. 나머지 5명은 "재고 부족" 응답을 받는다. 초과 판매 원천 차단.

### 1.5 판매 상태 바꾸기 (판매 시작 · 중단 · 비공개)

상품 하나의 판매 상태는 네 가지: **판매 준비 · 판매 중 · 품절 · 비공개**.

- **되는 것:** 관리자가 판매 준비 → 판매 중 (판매 시작), 판매 중 → 비공개 (판매 숨김), 비공개 → 판매 재개 로 전환.
- **자동으로 되는 것:** 비공개에서 판매 재개할 때 재고가 0 이면 자동으로 품절 상태로 지정. 재고 있으면 판매 중.
- **막는 것:** 관리자가 직접 "품절" 을 지정할 수는 없다. 품절은 시스템이 재고 0 인 상황을 자동 판정.
- **막는 것:** 판매 준비 상태로 되돌리는 것도 불가 (한 번 판매 시작된 상품은 준비 상태로 회귀 안 함).
- **막는 것:** 두 관리자가 동시에 "판매 중" 과 "비공개" 를 지정하면 한 명만 성공. 다른 한 명은 "다른 관리자가 먼저 바꿨어요" 안내.
- **바뀌지 않는 것:** 상태 바꿨다고 이미 있는 주문의 확정 금액이나 확보된 재고가 사라지지 않는다. 비공개로 전환해도 결제 대기 중인 주문은 그대로 진행 가능.

## 2. 비회원 구매자가 할 수 있는 것

구매자는 회원가입 안 하고 주문한다 (P1 스코프). 주문할 때 **주문 조회 비밀번호** 를 설정하고, 이후 주문번호 + 비밀번호 로 자기 주문에 접근.

### 2.1 주문서 작성 · 주문 만들기

- 이 기능은 **아직 정수 몫** (주문 1·2, 월-화 예정).

### 2.2 주문 결과·상세 조회

주문번호 (예: `OD-20260920-000123`) 와 비밀번호로 자기 주문을 확인.

- **보이는 것:** 주문번호, 상품명, 수량, 단가, 총 금액, 주문 상태, 주문자 이름, 주문 일시, 만료 시각, 취소 시각.
- **안 보이는 것:** 연락처, 비밀번호 해시, 내부 식별자 등 민감·내부 필드는 응답에 포함 안 됨.
- **막는 것:** 주문번호만 알거나 비밀번호가 틀리면 "그런 주문 없음" 이라는 동일한 응답을 받는다. 주문번호 존재 여부를 캐낼 수 없다.
- **되는 것:** 주문 상태에 따라 앞으로 할 수 있는 다음 동작이 달라짐 (아래).

### 2.3 결제 전 주문 취소

주문을 만들었는데 마음이 바뀌어 취소.

- **되는 것:** 결제를 아직 시작하지 않은 주문은 언제든 취소. 취소 순간 재고가 자동으로 판매 가능 상태로 되돌아감.
- **막는 것:** 이미 결제 진행 중이거나 결제 완료된 주문은 이 기능으로 취소 못 함. P1 은 결제 후 취소/환불 없음 (P3 스코프).
- **막는 것:** 이미 취소된 주문을 또 취소 요청해도 재고가 두 번 되돌아가지 않음.
- **경쟁 안전:** 사용자가 "결제 시작" 을 누른 순간 "취소" 도 눌렀다면 정확히 한 쪽만 성공. 재고가 이상해지지 않음.

### 2.4 결제 시작 (Mock)

주문에 대해 결제를 시작. **P1 은 실제 카드·계좌 결제가 아닌 Mock (내부 가짜) 결제** 다. 성공·실패·지연 시나리오를 코드가 재현.

- **되는 것:** 결제를 시작하면 주문 상태가 "결제 확인 중" 으로 바뀐다. 결제 시도가 하나 생성되며 그 ID 를 응답으로 받는다.
- **되는 것:** 시나리오 4종:
  - **즉시 성공** — 몇 백 ms 안에 주문이 "결제 완료" 로 확정. 재고에서 실제로 차감 (더 이상 판매 대상 아님).
  - **즉시 실패** — 몇 백 ms 안에 주문이 "결제 실패" 로 확정. 재고가 판매 가능 상태로 되돌아감 (다른 사람이 살 수 있게).
  - **지연 성공** — 200ms 뒤에 성공 확정. 그동안 주문은 "결제 확인 중".
  - **지연 실패** — 200ms 뒤에 실패 확정.
- **막는 것:** 이미 결제 중이거나 완료·실패·취소·만료된 주문에는 새 결제를 시작 못 함.
- **막는 것:** 사용자가 화면에서 "이 금액으로 결제" 라며 다른 금액을 보내도 서버는 주문할 때 확정된 금액만 사용. 임의로 금액 낮춰 결제 못 함.
- **바뀌지 않는 것:** 결제 시작 자체로 재고는 건드리지 않음. 재고는 주문 만드는 시점에 이미 배정됨 (주문 2). 결제 성공이면 그 배정 수량이 실제 판매로 확정, 실패면 판매 가능 상태로 복구.

### 2.5 결제 결과 다시 확인

결제 화면이 응답을 놓쳤거나, 사용자가 페이지를 닫았다가 다시 열어서 결과를 다시 확인하고 싶을 때.

- **되는 것:** 주문번호·비밀번호·결제ID 로 결제 결과를 다시 조회. 몇 번을 눌러도 같은 결과가 나온다. 이 조회 자체가 새로운 결제를 만들거나 재고를 건드리지 않음.
- **보이는 것:** 결제 상태 (진행 중 · 성공 · 실패 · 타임아웃), 요청 시각, 확정 시각.
- **알 수 있는 것:** 확정 시각이 아직 비어있으면 "아직 처리 중" (특히 지연 시나리오). 확정 시각이 채워져 있으면 결과 확정.
- **막는 것:** 다른 사람의 결제ID 를 넣어도 자기 주문 소속이 아니면 "없음" 응답. 결제ID 를 통해 다른 주문 정보를 캐낼 수 없음.

## 3. 시스템이 자동으로 하는 것 (백그라운드)

관리자·구매자가 요청 안 해도 서버가 알아서 처리하는 일들.

### 3.1 미결제 주문 자동 만료

주문을 만들어놓고 결제 안 하고 방치하면 재고가 무한정 묶임. 시스템이 주기적으로 훑어서 자동 만료.

- **기본 유효 시간:** 15분 (설정 파일에서 조정 가능. 팀 합의 후 최종 결정)
- **되는 것:** 15분 지난 미결제 주문 → 자동으로 "만료" 상태. 그 주문에 잡혀 있던 재고가 판매 가능 상태로 되돌아옴.
- **막는 것:** 이미 결제 진행 중이거나 결제 완료된 주문은 시간이 얼마나 지났든 만료 안 됨.
- **막는 것:** 이미 취소·만료된 주문에서 재고를 두 번 회수하지 않음.
- **주기:** 서버 시작 후 1분 뒤부터 1분마다 스캔. 한 번에 최대 100건 처리.

### 3.2 지연 결제 자동 확정 (재기동 안전)

"지연 결제" 시나리오는 서버 안에서 200ms 짜리 타이머로 결과를 확정. 그런데 그 200ms 사이에 서버가 죽으면 (배포·크래시) 타이머가 사라지고 결제 상태는 영원히 "결제 확인 중" 이 될 수 있음. 이걸 방지.

- **되는 것:** 시스템이 10초마다 DB 를 훑어서 "확정 예정 시각이 지났는데 아직 처리 중" 인 결제를 찾아 강제로 확정 처리.
- **되는 것:** 서버 재기동 후에도 진행 중이던 결제가 이어서 결과 확정.
- **막는 것:** 두 경로 (원래 타이머 · 재확인 스캔) 가 같은 결제를 동시에 확정 시도해도 결과는 한 번만 반영. 재고 이중 복구·이중 판매 없음.

## 4. 개발자·QA 용 도구

프로덕션 배포에는 활성화 안 됨 (Prod 프로파일에서 자동 비활성).

### 4.1 Mock 결제 시나리오 사전 지정

특정 주문번호에 대해 "이 주문이 결제 시작하면 반드시 실패로 처리해라" 같은 지정.

- **되는 것:** 주문번호 하나에 시나리오 (즉시 성공·실패·지연 성공·지연 실패) 를 미리 지정.
- **되는 것:** 이후 그 주문의 결제 시작 요청이 오면, 요청 body 에 시나리오가 없어도 지정된 값으로 처리.
- **되는 것:** 같은 주문에 다시 지정하면 마지막 값으로 덮어씀. 지정 제거도 가능.
- **막는 것:** Prod 프로파일에서는 이 endpoint 자체가 노출 안 됨. 실수로 실 서비스에 남아있어도 접근 불가.

### 4.2 결제 시작 요청 body 로 시나리오 지정

개발·통합테스트 편의. 매 요청마다 시나리오를 명시.

- 시나리오 결정 우선순위: 요청 body > 사전 지정 > 기본값(즉시 성공)

## 5. 사용자가 마주칠 수 있는 응답

주요 상황별 서버 응답. 프론트가 이걸 보고 UI 를 그린다.

| 상황 | 응답 | 사용자가 봐야 할 화면 |
|---|---|---|
| 정상 처리 | 200 OK · 200 응답 body · 204 No Content | 성공 안내 |
| 요청 값 잘못 (음수 가격, 잘못된 상태 지정 등) | 400 Bad Request | "입력값 확인해주세요" |
| 주문/재고/판매정보 없음 · 비밀번호 불일치 | 404 Not Found | "주문번호 또는 비밀번호를 확인해주세요" (leak 방지 통합) |
| 상태 충돌 (이미 결제 중인데 취소 시도 등) · 재고 부족 · 동시 편집 감지 | 409 Conflict | "이미 다른 처리가 진행되었어요. 새로고침 후 다시 시도" |

**404 통합 정책:** "주문번호 자체가 없음" 과 "주문번호는 있는데 비밀번호가 틀림" 을 응답에서 구분 안 함. 존재 여부를 캐낼 수 없게 하기 위함.

## 6. 아직 안 되는 것

Sprint 2 안에 완결 예정이지만 정 담당이 아닌 것.

### 6.1 정수가 월요일에 이어받는 것

**판매 1 · 판매정보 최초 등록**
- 관리자가 Shopping 서비스에 이미 등록된 상품을 골라 "이 상품 얼마에 팔지" 를 설정.
- 상품 존재 확인은 Shopping 서비스에 물어봐야 함. 지금은 "가짜 stub" 이 있어서 실제 shopping 없이 개발 가능.

**주문 1 · 주문서 확인·입력**
- 구매자가 상품 상세에서 "구매하기" 눌렀을 때 주문서를 조합 (상품명·단가·수량·주문자 정보 입력). 이 단계에선 재고 안 잡음.

**주문 2 · 주문 만들기**
- 주문자가 "주문하기" 확정. 이 순간 재고가 실제로 배정 (지금 있는 판매 가능 수량에서 빠져 배정 수량으로 이동). 주문번호가 발급됨.
- 재고 부족이면 "이미 다른 사람이 채갔어요" 안내.
- 같은 주문서를 여러 번 눌러도 중복 주문 안 만듦 (멱등 처리).

### 6.2 준제와 화요일 오전 페어링

**실제 Shopping 서비스 호출로 교체**
- 지금은 개발용 in-memory stub. 화요일 준제와 페어링해서 실제 shopping-service 를 REST 로 부르는 구현으로 교체.
- Circuit breaker · Retry · Timeout 등 회복 탄력성 설정 포함.

### 6.3 종민 · IVS 방송 연동 (화요일 저녁)

**방송 상품 조회**
- 방송 화면에서 방송에 연결된 상품의 판매 정보(가격·재고·상태) 를 실시간에 가까운 값으로 조회.
- Commerce 는 이미 판매정보 조회 API 를 갖고 있음. Live 서비스가 이를 소비만 하면 됨.

### 6.4 P1 밖 · 이번 스프린트에 없음

- 로그인 · 회원 정보 (P2 Sprint 3)
- 장바구니 (P2)
- 결제 후 환불 · 부분 취소 (P3)
- 실제 PG (외부 결제 게이트웨이) 연동
- 배송 · 알림 · 쿠폰 · 랭킹

## 7. 흐름 그림 · 한 눈에 보기

정상 구매 흐름 (관리자가 판매정보 준비 → 구매자가 주문 → 결제 성공):

```
[관리자]                             [구매자]                        [시스템]

판매정보 등록 (판매 1 · 정수 몫)
  · 상품 존재 확인 (Shopping stub)
  · 가격 · 초기 재고 설정
  ↓
판매 시작 (판매 4 · ON_SALE 전이)
  ↓
                                     상품 상세 확인 (Shopping 몫)
                                       ↓
                                     주문서 작성 (주문 1 · 정수 몫)
                                       · 수량 · 이름 · 연락처 · 조회 비밀번호
                                       ↓
                                     주문 확정 (주문 2 · 정수 몫)
                                       · 재고 배정 (5 → 4, reserved 0 → 1)
                                       · 주문번호 발급
                                       ↓
                                     결제 시작 (결제 1)
                                       · 주문 상태: 결제 확인 중
                                       · 시나리오 지정 or 기본값
                                       ↓
                                                                    Mock 엔진: delay 후 확정
                                                                     ↓ (200ms · 재기동 시 Reconciler 대체)
                                                                    결제 성공/실패 확정 (결제 2)
                                                                     · 주문 상태: 결제 완료 or 실패
                                                                     · 재고: 성공이면 배정 소진, 실패면 판매 가능 복구
                                     결과 재확인 (결제 3)
                                       · 화면 놓쳤을 때
                                       ↓
                                     주문 상세 조회 (주문 3)
                                       · 최종 상태 확인
```

취소 흐름:

```
[구매자]
주문 확정
  ↓
"결제 안 할래" 취소 (주문 4)
  · 주문 상태: 취소
  · 재고: 배정 → 판매 가능 복구
```

만료 흐름:

```
주문 확정
  ↓
15분 방치
  ↓
[시스템] 만료 스캐너
  · 주문 상태: 만료
  · 재고: 배정 → 판매 가능 복구
```
